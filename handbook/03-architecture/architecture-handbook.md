# FDE 架构手册

版本10.15.4 · 试行。阅读入口见[架构设计手册](README.md)。

## 0 适用范围

本手册承接已有需求与现场调研，说明如何形成解决方案、提出技术可行性、完成方案审核与开发审核。项目架构师负责问题定义、产品定义、解决方案、报价依据及技术可行性判断；PM带入客户事实与资源条件，FDE协作设计、验证并落实开发计划。

工作主线：**真实业务与场景基线 → 定义问题 → 定义产品及价值、范围与报价 → 方案审核 → 技术架构与开发计划 → 开发审核 → 实施与场景结果核对**。

方案与技术材料可以并行准备。审核顺序固定为先方案、后开发；并行材料注明所依据的方案版本和待确认项，方案审核后核对差异，开发审核通过后进入实施。

已有产物继续使用：问题回答句、场景量表与基线、产品目标、A组材料、范围分期与报价、技术可行性结论、B组九份spec及独立开发计划。模板统一从[项目管理模板目录](../02-project-management/templates/README.md)进入。

## 1 基础模型

**现状链。** 从客户经营目标到部门、岗位、动作、系统及表单，说明每一层怎样服务上层。环是一段能说明输入、判断、输出和交接的业务闭环，格是其中可单独观察和改善的量；沿用环R1、格R1-a等编号定位材料。

**判断与执行。** 判断写清依据、选择及后续动作；执行留下实际结果，供下一轮判断。

**四维表。** 用“决策／执行 × 速度／精度”检查问题和产品价值，选择本场景实际要改善的项。

| | 速度 | 精度 |
|---|---|---|
| 决策 | 从取得必要信息到作出判断的时间 | 判断质量、正确性或可核对的有效程度 |
| 执行 | 完成指定任务的时间、单位时间处理量 | 一次通过率、差错率或任务结果的准确程度 |

具体量名、统计口径和样本按场景确定。成本作为相关效果核算，口径有据后记录；场景量的改进支撑价值判断，不能直接替代客户经营结果。

## 2 架构工作总表

| 步 | 动作 | 产物与判断 | 衔接 |
|---|---|---|---|
| 1 | 梳理现状链、取得基线 | 业务流、真实样本、现状量及计算口径 | PM与客户核实，架构师用Meta Workflow整理 |
| 2 | 陈述问题 | 客户原话、现场事实及其所在业务环节 | 区分事实、意向和待核实内容 |
| 3 | 定义问题 | 一至两句话说明卡点及其经营意义，场景量表 | 项目架构师判断，PM代表客户核对 |
| 4 | 定义产品 | 产品如何改善问题、目标水平、A组材料、范围及报价依据 | 方案审核：商业可行性 |
| 5 | 提出技术可行性 | 数据结构、数据流、信息流、可行性结论和B组九份spec | 项目架构师提出，FDE参与核查 |
| 6 | 排序与迭代 | 任务依赖、实施路线及独立开发计划 | FDE编制计划，架构师核对技术依赖，PM落实资源；开发审核 |

两次审核均由总架构师进行。技术准备可以与方案准备并行；正式开发审核须对应已通过方案审核的版本。方案未定时保留候选状态，先消除影响技术设计的分歧。

## 3 梳理现状链与取得基线

**目标与产出**：还原客户当前怎样工作，取得业务流、样本、现状量及来源，供问题和产品定义使用。

**策略**：用真实案例与取样描述现状。Meta Workflow沿现有Meta Skill和Meta Orchestrator方法组织流程；现场取证继续使用袁黎明当前现场手册。

**行动**
1. PM协调业务人员、资料、系统权限和样本。架构师与团队顺着一件真实业务，从触发到结束核对动作、判断、交接和异常。
2. 从经营目标向下梳理到岗位与表单，用环、格编号标明本项目关注的位置；绘图方法见[开发手册§2—3](../04-development/development-handbook.md#2-使用-meta-workflow-拆解业务流形成-a-的流程部分)。
3. 在访谈、观察和取样中找到场景基线。客户没有现成统计时，PM组织取样和计算，与客户确认“是否这样算”。未知数值保留待取数，写清所缺样本和接续人。
4. 记录量名、单位、计算方法、样本范围与时间窗、数据来源和客户核对结果。基线取现状，产品目标由后续方案提出。

**已有工具**：[现场调研表单](../02-project-management/templates/02-research/README.md)、[通用调研输入](../02-project-management/templates/02-research/通用调研输入文档_10.06.md)、[基线与试点记录](../02-project-management/templates/02-research/基线与试点对比记录表.md)。

## 4 陈述问题

记录客户原话、现场事实、业务环节和现状值，分别标明来源与确认状态。例如：“研发进展的信息不透明”，先说明实际缺少哪些信息、由谁产生、谁需要，以及现场能观察到的后果。

陈述问题为后续判断提供依据。进入定义问题时继续追问业务价值和隐性卡点，不能仅以客户说出的表面诉求决定交付上限。

**产物**：已有调研材料中的问题陈述与事实依据。

## 5 定义问题

### 5.1 上溯经营意义

追问：**这条业务链怎样帮助客户挣钱？当前环节通过什么影响客户的收入、成本或竞争力？**

从客户原话和现场事实出发，辨别表面症状与值得解决的问题。隐性需求的判断依赖业务经验、事实对照及与客户交流；AI可协助整理和提出候选，项目架构师承担判断，PM代表客户核对。

上溯也可能缩小或淘汰一个问题。找不到与客户价值的关系时，继续核实其成立依据，保留未确认状态。

### 5.2 定格定水平

按决策／执行、速度／精度找到场景中的可测量变化，沿已有场景量表填写：

| 格 | 场景量、单位与测法 | 现状值及来源 | 目标水平 |
|---|---|---|---|
| | | | |

现状值来自现场观察、取样和计算；PM与客户核对测法及现状。目标水平由方案提出并核对实现条件。没有现成数据时组织取得基线，不能用期望数字填写现状。

取样条件与计算口径随基线保存，后续效果核对使用可比条件。业务结果用于上溯和观察；承诺与验收采用本场景可判定、可控制的结果。

### 5.3 明确回答

用一至两句话说明：
> 客户在什么业务环节遇到什么卡点；这一卡点为何影响其经营。我们需要改善哪些场景量，现状是什么，希望达到什么水平。

问题回答句指向应解决的卡点及目标。产品定义随后回答“通过什么产品能力和工作方式实现改善”。

### 5.4 用研发场景理解问题定义

以下为脱敏讲解示例，不是任何客户的已确认方案或效果承诺。

研发进展透明可以提供基础信息。继续上溯，要判断客户依靠怎样的技术竞争力获得价值：研发方向是否选得准、验证是否足够快、文献与报告是否支持有效决策。

因此候选问题可以落在研发方向的判断精度与验证速度。是否采用这一判断，要回到客户业务和样本核实。信息整理可以成为基础层，产品需要说明它如何支持后续判断与执行。

**产物**：问题回答句与场景量表，进入方案审核。

## 6 定义产品、价值与报价

**目标**：说明产品怎样解决已定义的问题，以及客户使用后在场景中的变化。

**行动**
1. 逐个问题说明拟采用的产品能力和工作方式。工作台、助手、工具或嵌入既有系统是实现形态，选择需回到问题及实际条件。
2. 对每项能力说明它改善哪个场景量、从怎样的基线达到怎样的目标；用业务流和体验流表达谁在何处使用、得到什么结果。
3. 用Meta Workflow整理目标业务流、整体架构及graph，形成A组材料。图和说明引用调研事实、问题定义及产品选择。
4. 核对本期范围、分期、客户配合与报价依据。产品带来的可解释改善支撑价值与报价判断；不把场景改善直接换算成未经确认的营收承诺或固定报价公式。
5. PM从客户需求出发追问方案价值，落实配合与投入条件，组织方案送审。

沿研发示例，可分别考虑方向验证、文献检索、报告生成如何支持研发速度和决策精度。每项候选能力都要核对现状耗时、质量及目标效果；课堂设想不能直接写成客户承诺。

**产物**：产品目标与改善说明、A组材料，以及已有[范围分期与报价](../02-project-management/templates/03-solution/范围分期与报价.md)中的对应内容。送审格式见[两次送审邮件](../02-project-management/templates/03-solution/送审邮件.md)。

## 7 技术可行性（项目架构师提出）

**目标**：判断方案能否开发和实施，说明关键技术条件。项目架构师提出判断，FDE参与样本验证、设计与实现条件核查；PM协调所需资源和客户配合。

先核对三个层面：
- **业务流**：业务从触发到结果怎样完成。
- **数据流**：业务对象、单据、表和字段怎样产生、关联、计算、传递、保存与更新。
- **信息流**：数据承载的业务含义如何汇总到决策层，决策、目标和安排如何传递到执行层；谁在何处看到什么并采取什么行动。

例如，工作记录经过员工入口、数据表到看板是数据流；工作进展汇总到管理者，以及管理决定分发给执行者，是对应的信息流。该例只解释设计层次，不证明具体平台功能已验证。

逐项核查：
1. 数据可取：字段、计算口径、权限、历史跨度与样本。
2. 系统可改：接口、能力、身份、权限、并发及既有系统约束。
3. 人力可支撑：谁做、多久、技术支持与依赖。
4. 客户能配合的时间窗和现场条件。

以明确版本的A和技术约束使用Meta Spec形成B组九份spec，逐份检查设计与方案一致性。并行起草时注明方案待审；正式开发审核前核对方案审核结果和全部差异。技术发现改变问题、产品或承诺水平时，按第11章返回方案。

**产物**：可行性结论、B组九份spec、数据流与信息流的设计说明；已有文件承载这些内容，文件名和技术写法见[开发手册§3—5](../04-development/development-handbook.md#3-补齐整体架构图和-graph交付完整文件组-a)。

## 8 排序与迭代

根据已定产品目标、技术依赖和资源条件安排实现顺序。需要数据底座支持辅助决策时先补相应底座，每轮说明怎样接近本期场景目标。

FDE编制独立开发计划，项目架构师核对可行性和技术依赖，PM落实人员、排期及客户配合。开发计划列任务、负责人、时间、工具、用量、依赖及验证安排，沿[现有计划模板](../02-project-management/templates/04-development/开发计划模板_10.08.md)填写。

**产物**：实施路线与独立开发计划，随开发架构A+B进入开发审核。

## 9 合同验收与结果核对

场景基线与改善效果采用同类样本和可比条件，记录实际结果、差异及限制。场景量可以承载可判、可控的功能验收；客户营收、利润等经营结果用于观察和价值讨论。

启动会形成一个客户签字的《验收标准及验收清单》，之后确认版本固定。最终验收逐项对应这一文件，并取得客户签字。具体操作及待补模板见[PM手册启动会](../02-project-management/project-management-handbook.md#stage-48)和[验收](../02-project-management/project-management-handbook.md#stage-412)。

## 10 审核清单

### 10.1 闸1：方案审核（商业可行性）

| 检查项 | 要回答的问题 | 架构师自查 | 总架构师复核 |
|---|---|---|---|
| 问题定义 | 卡点是什么，怎样影响客户价值，现场依据是什么 | | |
| 产品定义 | 产品通过什么能力和工作方式解决问题，客户使用后有什么变化 | | |
| 场景基线与目标 | 现状、测法、来源、客户核对及目标水平是否清楚，改善落在哪个场景量 | | |
| A组材料 | 业务流、体验及整体架构是否表达了上述方案，是否有无依据的扩展 | | |
| 范围与报价 | 本期范围、分期、客户配合、价值及报价依据是否相互匹配 | | |
| 未决判断 | 经验判断、假设及待补事实是否可辨，哪些会影响方案成立 | | |

PM核对材料入口与客户确认情况，向总架构师提交明确版本。方案审核通过后，技术材料以该版本及审核条件为依据。

### 10.2 闸2：开发审核（技术可行性）

| 检查项 | 要回答的问题 |
|---|---|
| 方案依据 | 是否对应已通过的方案版本，后续改动是否已处理 |
| 项目架构师的可行性判断 | 数据、系统、人力及客户时间窗是否支持方案；证据和未验证项是什么 |
| 数据结构与数据流 | 对象、字段、来源、流转、保存、权限和接口能否支撑业务 |
| 信息流 | 业务信息如何支持决策，决策如何传递并落实到执行 |
| A+B一致性 | 九份spec是否覆盖方案，范围、角色、规则、页面、接口及测试是否对应 |
| 独立开发计划 | 任务、时间、人员、工具、用量、依赖及完成要求是否可执行 |

总架构师给出具体版本、范围、条件及结论。开发审核通过后，按PM手册落实启动与开工条件，再由FDE实施。

## 11 回边与方案修订

**启动签字前**：问题或产品定义不成立，返回方案；技术条件不足，由项目架构师提出依据及处理意见。影响问题、产品、目标、范围或报价时，回方案审核，再进入开发审核。仅技术实现发生调整时，核对方案保持一致后重提开发审核。

沿用每轮补充新事实、只处理受影响内容并记录版本的要求。两轮仍无法达到目标时交PM组织商务处理，调整待确认方案和范围报价，再取得对应审核及客户确认。

**启动签字后**：已签确认版本固定。技术调整应服务于原签字范围和标准；新增诉求、能力缺口或客户配合变化按[PM异常处理](../02-project-management/project-management-handbook.md#exceptions)处理，不能通过降低原签字标准替代交付。

单场景绘图如何简化、C类一次进场与两次审核及启动签字的具体排期仍待讨论，沿现有要求记录待定项。

## 12 使用与反馈

手册和工具问题通过[仓库反馈入口](../../feedback/README.md)提交；项目正式送审采用PM组织的邮件。真实项目的使用结果用于检验和修订本手册。缺失工具按节点、输入、输出及判断要求提出，文档Skill与缺失模板按已确认材料逐步补齐。
