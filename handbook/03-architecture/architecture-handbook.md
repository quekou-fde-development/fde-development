# FDE 架构手册

版本10.16 · 试行。阅读入口见[架构设计手册](README.md)。

## 0 适用范围

本手册承接咨询与现场调研，说明怎样定义问题、定义产品，并把产品设计展开为技术架构。咨询提供事实与baseline；定义问题讲清客户问题及解决它的意义；定义产品以target和baseline之间的改善明确产品价值，形成产品设计、信息流和客户体验流。客户体验流将前述设计汇聚为客户实际完成任务、获得结果的过程，据此检查产品定义是否完整；技术架构说明怎样开发实现。

方案文档按“定义问题、定义产品”两部分组织，进入方案审核。技术架构与独立开发计划进入开发审核。材料可以并行准备，正式开发审核须对应已通过的方案版本。

方案文档保存在知识库「FDE全链」对应项目；技术架构资料与独立开发计划保存在已登记私有GitHub仓库，项目记录关联版本及审核原文。填写格式从[项目管理模板目录](../02-project-management/templates/README.md)进入。

## 1 基础模型

**现状链。** 从客户经营目标到部门、岗位、动作、系统及表单，说明每一层怎样服务上层。环是一段能说明输入、判断、输出和交接的业务闭环，格是其中可单独观察和改善的量；沿用环R1、格R1-a等编号定位材料。

**判断与执行。** 判断写清依据、选择及后续动作；执行留下实际结果，供下一轮判断。

**四维表。** 用“决策／执行 × 速度／精度”检查问题和产品价值，选择本场景实际要改善的项。

| | 速度 | 精度 |
|---|---|---|
| 决策 | 从取得必要信息到作出判断的时间 | 判断质量、正确性或可核对的有效程度 |
| 执行 | 完成指定任务的时间、单位时间处理量 | 一次通过率、差错率或任务结果的准确程度 |

具体量名、统计口径和样本按场景确定。成本作为相关效果核算，口径有据后记录；场景量的改进支撑价值判断，不能直接替代客户经营结果。

## 2 架构工作总表

| 工作 | 方法重点 | 产出与接续 |
|---|---|---|
| 梳理现状链、陈述问题 | 沿真实案例取得事实、样本与baseline | 调研依据和问题陈述，供问题判断使用 |
| 定义问题 | 说明客户有什么问题、选择解决哪个问题，以及解决它的意义 | 方案文档的问题部分 |
| 定义产品 | 确定target，以baseline对照产品价值，从价值出发设计产品、信息流和客户体验流，说明AI采用依据及贡献 | 方案文档的产品部分，关联范围报价；方案审核 |
| 技术架构与可行性 | 把产品转为技术流程、系统与数据设计，核查实现条件 | 技术架构资料、九份spec及项目架构师的可行性判断 |
| 排序与计划 | 按目标、技术依赖和资源条件编制实施顺序 | 独立开发计划，随技术材料进入开发审核 |

两次审核均由总架构师进行，PM组织提交；方案与技术材料可并行准备，正式审核先方案、后开发。

## 3 梳理现状链与取得基线

**目标与产出**：还原客户当前怎样工作，取得业务流、样本、现状量及来源，供问题和产品定义使用。

**策略**：用真实案例与取样描述现状。Meta Workflow沿现有Meta Skill和Meta Orchestrator方法组织流程；现场取证继续使用袁黎明当前现场手册。

**行动**
1. PM协调业务人员、资料、系统权限和样本。架构师与团队顺着一件真实业务，从触发到结束核对动作、判断、交接和异常。
2. 从经营目标向下梳理到岗位与表单，用环、格编号标明本项目关注的位置；绘图方法见[开发手册§2—3](../04-development/development-handbook.md#2-使用-meta-workflow-拆解业务流形成-a-的流程部分)。
3. 在访谈、观察和取样中找到场景基线。客户没有现成统计时，PM组织取样和计算，与客户确认“是否这样算”。未知数值保留待取数，写清所缺样本和接续人。
4. 记录量名、单位、计算方法、样本范围与时间窗、数据来源和客户核对结果。基线取现状，产品目标由后续方案提出。

**已有工具**：[现场调研表单](../02-project-management/templates/02-research/README.md)、[通用调研输入](../02-project-management/templates/02-research/通用调研输入文档_10.06.md)、[基线与试点记录](../02-project-management/templates/02-research/基线与试点对比记录表.md)。

## 4 陈述问题

记录客户原话、现场事实、业务环节和现状值，分别标明来源与确认状态。例如：“研发进展的信息不透明”，先说明实际缺少哪些信息、由谁产生、谁需要，以及现场能观察到的后果。

陈述问题为后续判断提供依据。进入定义问题时继续追问业务价值和隐性卡点，不能仅以客户说出的表面诉求决定交付上限。

**产物**：已有调研材料中的问题陈述与事实依据。

<a id="problem-definition"></a>

## 5 定义问题

**目标与产出**：形成清楚的问题定义，说明我们为客户解决什么问题，以及解决它的意义。内容写入方案文档的第一部分。

**策略**：以调研事实为依据，辨明客户表达的诉求、业务中实际存在的问题及其经营联系。沿客户业务理解问题，核对所选问题是否值得解决。

**行动**

1. 读取客户原话、业务流程、真实案例和现状数据。说明什么人在什么环节遇到什么问题，现有办法如何工作，出现了什么实际后果。
2. 根据这些事实，明确本项目选择解决的问题。把判断理由和事实来源写出来，保留尚需核实的内容。
3. 说明解决这个问题对客户有什么意义，沿业务关系解释它怎样影响收入、成本、效率或竞争力。按本项目事实选择相关内容。
4. 将问题与意义写成可以独立阅读的说明，供PM代表客户核对。

定义问题的结束点是：读者能够说明“客户的问题是什么，我们解决什么，为什么值得解决”。产品的target和实现这份改善的办法在下一节展开。

<a id="product-definition"></a>

## 6 定义产品、价值与报价

**目标与产出**：定义解决上述问题的产品，写清它创造的价值、工作方式、信息流和客户体验流。信息流沿业务步骤写清最初输入、拆解、逐步处理、中间产出、后续去向及最终反馈。体验设计须具体到客户何时使用、怎样进入、看到什么、如何逐步操作与查看信息、怎样获得结果，以及首次使用和日常操作的负担。内容写入方案文档的第二部分，关联范围、分期与报价。

**策略**：以终为始。先确定使用产品后要达到的target，以咨询取得的baseline说明需要实现的gap，再由产品价值推导产品设计。以完整的客户任务检查这份价值如何通过使用过程实现；体验中缺少的能力、信息或条件返回对应设计补齐。

**行动一：确定目标与产品价值。** 针对已定义的问题，写清希望达到的场景结果及其量化口径。引用咨询取得的baseline，对照target，说明变化方向和改善量。需要比较的量沿用决策／执行、速度／精度的已有模型选择，测法和样本条件保持可比。baseline、target及后续实测结果分别记录。

**行动二：设计产品。** 围绕这份价值，说明产品提供哪些能力、怎样改变客户的工作、各项设计怎样促成目标。产品形态随这些判断确定。每项产品设计都能关联它解决的问题和创造的改善。

设计AI产品时，在这一行动内逐项回答：

1. **AI在哪里、智能在哪里？** 指出具体业务环节、输入、AI承担的处理或判断、输出，以及输出如何改变后续行动。
2. **普通工程为什么不够？** 对照同一目标和项目条件下可行的固定规则、既有系统或其他工程办法，说明能做到什么、还缺什么及判断依据。工程足以达到目标的部分采用工程实现。
3. **为什么需要AI、它贡献什么？** 说明AI怎样弥补上述缺口，去掉AI会影响哪项目标，以及相对可行工程方案的改善。产品从baseline到target的整体价值中，分别说明流程调整、普通工程和AI的作用。
4. **凭什么相信这份贡献？** 列明已有依据及待验证判断，明确比较任务、样本和业务口径。按目标考虑复核、返工和运行投入的影响，把关键能力与贡献交技术准备验证。

只有“接入模型”“增加对话入口”等描述，采用依据仍不完整。尚未验证的AI贡献写为待验证判断；验证发现工程方案已足够或AI贡献缺乏支持时，调整产品设计。

<a id="information-flow"></a>

**行动三：沿业务流设计信息流。** 先明确本产品要支撑的业务任务、起止位置和步骤顺序，再从最初进入的信息开始，逐步展开信息怎样被拆解、处理和传递。现状引用调研依据，本期拟调整的业务安排注明为方案设计。

- **最初输入**：业务从什么事件开始，进来什么材料或信息，包含哪些实际内容，由谁或哪个系统提供，以什么形式、在什么时点进入。
- **信息拆解**：原始内容怎样拆成后续业务能使用的信息项，各项的业务含义、拆解依据及原始来源是什么；需要补充或合并的信息从哪里来，原样传递的内容交往哪里。
- **逐步处理**：每个业务节点分别接收上一步哪些产出、增加哪些新信息，由谁或什么产品能力按何种规则处理，得到什么中间结果。写清输入怎样变成输出；AI参与时对应已明确的采用理由，说明它具体读取、处理和产出的内容。
- **继续传递**：每项产出交给哪个后续业务节点、谁或哪个系统，用于什么判断或行动，在什么时点或条件下交接。按实际业务说明分支、多个来源汇合及缺信息后的补充或退回，保留同一业务事项的对应关系。
- **最终结果与反馈**：信息最后支持什么判断、安排或执行，客户得到什么结果；结果记录或反馈到哪里，怎样更新前面的信息与业务状态。

拿一条实际业务样本从头走到尾。每个下游输入都要找到上游产出或明确的新增来源，每项输出都要写出内容和用途，沿实际分支和反馈检查能否接续。信息流图的节点对应业务步骤，连线注明具体传递的信息。客户体验中出现的信息对应这些节点的产出；客户填写、确认及操作产生的信息回到相应节点继续处理。格式见[方案模板§信息流](../02-project-management/templates/03-solution/解决方案.md#information-flow)。

<a id="customer-experience"></a>

**行动四：设计完整的客户体验流。** 按实际使用者和任务，把产品价值、能力与信息流展开为从开始使用到完成事情的过程。每条关键路径写清以下内容：

- **使用情境与入口**：客户在什么时候、什么工作条件下需要使用，是什么触发这次任务；从哪里找到产品，怎样打开，首次进入要完成什么准备，到达哪个页面或状态。
- **首屏与所得信息**：打开后先看到什么、由此知道什么，怎样辨认当前任务、状态和下一步；信息的优先级由当前要完成的任务决定。
- **逐步操作与反馈**：每一步有哪些操作、在哪里操作、怎样输入或选择、操作顺序是什么；执行中及完成后看到什么反馈，下一步去哪里。常见分支、缺信息、无结果或中断的处理沿真实业务需要设计。
- **信息层次与下沉**：当前层呈现哪些信息，何时需要进一步展开，通过什么操作进入明细或依据，怎样返回并继续原任务。按实际需要确定层数；不同使用者所需信息存在差异时分别说明。
- **上手难度与操作负担**：客户原有知识和使用条件是什么，第一次能否理解页面并找到下一步，需要哪些提示、示例或默认安排；日常任务要付出哪些查找、填写、切换和记忆成本，设计怎样减少这些负担。
- **结果与价值**：客户怎样知道事情已经完成，获得什么结果，结果怎样保存、继续使用或交给下一人。每项产品价值对应到客户实际获得的结果；AI在后台工作的，也写清它怎样改善客户收到的信息或任务结果。

在方案正文中按需要使用步骤图、页面简图和逐步说明，让读者能够沿一项真实任务从入口走到完成。对照检查每步的信息、操作、反馈与去向，以及信息下沉、常见分支和首次上手；把发现的缺口返回产品或信息流设计。文字与简图走查、客户核对和实际使用验证分别保留其状态。上手难度属于本节产品设计；客户培训安排仍沿既有暂缓状态。

**行动五：衔接范围与报价。** 在已有范围分期与报价文件中引用方案结论，明确本期产品内容、客户配合和报价依据。方案文档、范围报价及待确认条件一起进入方案审核。

产出格式见[方案模板](../02-project-management/templates/03-solution/解决方案.md)。项目目标和方案设计处于拟议状态时如实注明；客户确认与审核结论引用实际记录。

## 7 技术架构与可行性（项目架构师提出）

**目标与产出**：形成能够指导开发的技术架构，说明产品怎样实现及实现条件。项目架构师提出可行性判断，FDE协作验证和设计，PM协调资源。

**策略**：以明确版本的方案为输入，沿产品的信息流与客户体验逐项展开技术结构。方案尚在准备时，技术候选保留其依据和待审状态。

**行动**

1. 读取方案中的问题、target、产品价值、产品设计及AI采用依据、信息流、体验流及范围，记录所依据的方案版本和审核状态。
2. 将产品工作方式展开为技术流程和系统结构。把信息流各节点的输入、拆解与处理、产出、去向及反馈对应到业务对象、数据结构、处理逻辑、接口和运行关系，承接体验中的入口、页面、信息层次、操作及反馈状态，并明确权限。说明人、现有系统、新建应用及工具如何配合。业务处理规则、流向或产品交互尚未确定时，返回产品设计补齐。具体文件写法沿开发手册。
3. 核对数据可取、系统可接入或修改、人力支持及客户配合时间窗。验证产品设计中AI承担的关键能力及预期贡献，对照可行工程方案，保留可比较的任务、样本、口径、结果及相关投入。可行性判断写清依据、已验证内容、待验证条件及影响。
4. 使用明确的技术流程与整体架构、方案依据和约束形成九份spec，逐份核对与产品定义的一致性。
5. FDE编制独立开发计划，项目架构师核对技术依赖，PM落实人员、权限、资源和客户配合，组织开发审核。

技术设计影响已定问题、target、产品、范围或报价时，说明影响并返回方案处理。正式开发审核前，对齐已通过的方案及条件。启动签字后按固定标准和已有异常流程执行。

文件写法见[开发手册§2—5](../04-development/development-handbook.md#2-使用-meta-workflow-拆解业务流形成-a-的流程部分)，技术参照见[项目管理区技术架构参照](../02-project-management/templates/04-development/architecture-reference/README.md)。

## 8 排序与迭代

根据已定产品目标、技术依赖和资源条件安排实现顺序。需要数据底座支持辅助决策时先补相应底座，每轮说明怎样接近本期场景目标。

FDE编制独立开发计划，项目架构师核对可行性和技术依赖，PM落实人员、排期及客户配合。开发计划列任务、负责人、时间、工具、用量、依赖及验证安排，沿[现有计划模板](../02-project-management/templates/04-development/开发计划模板_10.08.md)填写。

**产物**：实施路线与独立开发计划，随技术架构资料（A+B）进入开发审核。

## 9 合同验收与结果核对

场景基线与改善效果采用同类样本和可比条件，记录实际结果、差异及限制。场景量可以承载可判、可控的功能验收；客户营收、利润等经营结果用于观察和价值讨论。

启动会形成一个客户签字的《验收标准及验收清单》，之后确认版本固定。最终验收逐项对应这一文件，并取得客户签字。具体操作及待补模板见[PM手册启动会](../02-project-management/project-management-handbook.md#stage-48)和[验收](../02-project-management/project-management-handbook.md#stage-412)。

## 10 审核清单

### 10.1 闸1：方案审核（商业可行性）

| 方案审核 | 要判断的内容 |
|---|---|
| 定义问题 | 客户的问题是否讲清，判断依据是否成立，解决它有什么意义 |
| 目标与价值 | baseline是否有来源与测法，target是什么，两者之间的gap如何构成产品价值 |
| 产品设计 | 产品怎样解决问题、实现改善，各项能力与目标是否对应 |
| AI采用依据与贡献 | AI作用在哪个环节，普通工程为何不够，AI如何贡献目标；整体产品价值与AI贡献是否区分，依据及待验证项是否清楚 |
| 信息流 | 沿业务流的最初输入、信息拆解、各步处理、中间产出、后续去向及最终反馈是否清楚；下游输入能否接上上游产出或新增来源，实际分支及汇合是否可接续 |
| 客户体验流 | 何时使用、怎样进入、首屏看什么；每步的具体操作、反馈和去向是否明确，信息怎样下沉，常见分支怎样继续，上手负担是否合理，最终怎样获得产品价值 |
| 范围报价与条件 | 本期内容、分期、价值依据、报价和客户投入是否对应；未决项如何影响方案 |

### 10.2 闸2：开发审核（技术可行性）

| 开发审核 | 要判断的内容 |
|---|---|
| 方案依据 | 对应哪个已通过的方案版本及条件，并行准备后的差异是否处理 |
| 技术实现 | 系统、数据、接口、权限和运行关系能否支撑产品目标，以及体验中的入口、页面、操作、反馈、信息下沉和完成结果 |
| AI能力与贡献验证 | 关键能力及其相对工程方案的贡献有什么验证依据；任务、样本、口径和相关投入是否可比，结果支持哪些判断、还留下哪些限制 |
| 技术资料一致性 | 技术流程、整体架构、九份spec之间的对象、规则和实现安排是否一致；是否覆盖业务信息流的输入、拆解、处理、产出、转交与反馈 |
| 可行性判断 | 项目架构师的判断有什么依据，数据、系统、人力、时间窗及未验证条件是否清楚 |
| 独立开发计划 | 任务、人员、时间、工具与用量、依赖和验证安排是否可执行 |

总架构师对明确版本给出审核结论、范围及条件，PM保留原文并组织后续动作。所有客户类型沿用两次审核要求。

## 11 回边与方案修订

**启动签字前**：问题或产品定义不成立，返回方案；技术条件不足，由项目架构师提出依据及处理意见。影响问题、产品、目标、范围或报价时，回方案审核，再进入开发审核。仅技术实现发生调整时，核对方案保持一致后重提开发审核。

沿用每轮补充新事实、只处理受影响内容并记录版本的要求。两轮仍无法达到目标时交PM组织商务处理，调整待确认方案和范围报价，再取得对应审核及客户确认。

**启动签字后**：已签确认版本固定。技术调整应服务于原签字范围和标准；新增诉求、能力缺口或客户配合变化按[PM异常处理](../02-project-management/project-management-handbook.md#exceptions)处理，不能通过降低原签字标准替代交付。

单场景绘图如何简化、C类一次进场与两次审核及启动签字的具体排期仍待讨论，沿现有要求记录待定项。
