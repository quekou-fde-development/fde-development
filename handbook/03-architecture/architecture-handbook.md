# FDE 架构手册

版本 10.14.1 · 试行。与开发技术手册的阅读衔接见[架构设计手册入口](README.md)。

## 0 适用范围

本手册覆盖客户签约之后、进场调研到方案送审通过这一段，主体是项目架构师。

产出物四件：回答句、产品目标、A 组材料（目标业务流 + 体验流 + 整体架构）、调研基线。

上游输入是袁黎明现场手册 ①②③（背景收集、建联、需求确认）的产出与第三次需求确认记录。下游承接是 FDE 的 B 组九份 spec 与独立开发计划，写法见 [开发技术手册](../04-development/development-handbook.md)。

铁三角分工：项目经理管现场组织与客户关系；项目架构师出解决方案（本手册）；FDE 出开发架构。前半段之后是闸 1，后半段之后是闸 2，两次都由总架构师审。

## 1 基础模型

**现状链。** 从客户经营目标往下画到岗位动作与系统表单，逐层标出这一层替上一层保证什么。环 = 链上一段业务闭环，格 = 环里可以单独变化的一个量。编号格式：环 R1 / R2…，格 R1-a / R1-b…。本手册后面所有定位都用这套编号。

**判断/执行循环。** 每处改动都是先判断后执行，执行结果回到判断。判断写明依据，执行留痕。

**四维表。** 决策/执行 × 精度/速度。定义问题时当检查表逐格过，复盘时当分类坐标。

**成本。** 导出量：单次通过成本 ≈ 执行单价 × 每次工时 ÷ 一次通过率 + 漏检损失。它是一把量尺——同一个格，精度要求和速度要求各要怎么变、成本跟着怎么动——本身不占维度位。

|---|---|---|---|---|

## 3 梳理现状链

**做三步。**

1. 画出客户当前怎么干：从经营目标往下，到部门、到岗位、到动作、到系统与表单。每一层标出它替上一层保证什么。
2. 切环。环 = 一段能独立说清"输入什么、谁判断、产出什么、交给谁"的业务闭环。环的数量控制在能指出我们动哪一环，不为完整而补环。
3. 编格。格 = 环里一个可以单独变化的量（耗时、口径、通过率、依据来源、判断人……）。四维表在这步先粗过一遍，把明显会动业务结果的格标出来。

**产物**：现状链图 + 环/格编号表。环编号后，后续所有讨论、材料、变更账本都用它定位。

## 4 陈述问题

**一句话，客户原话，挂到环和格，带现状值。**

格式：`<客户>的<R?><格?>：<原话>`，后面跟现场看到的现状值。

示例（逻辑形式）：某制造企业的 R1-报价查询：报一次价要查很久，平均 X 分钟。

陈述与定义的分界：这里只记录客户自己说的问题和现场看到的现状，不上溯，不设目标，不问该不该解决。

**产物**：问题陈述一行。

## 5 定义问题

三步：上溯 → 定格定水平 → 明确回答。

### 5.1 上溯

问一句：这一环在客户生意里决定什么？

示例（逻辑形式）：报价决定某制造企业每单赚多少、成不成交。

上溯有两个出口：格进定义，或者格被淘汰。某一格上溯后不影响生意，它就不进定义。上溯也可能把整个问题缩小甚至杀掉——做完上溯先看回答句还立不立得住。

**产物**：每个候选格一句业务结果归属。

### 5.2 定格定水平

拿四维表逐格过。判据一条：这一格变化时，业务结果跟着变，它就进定义。

每一格写成三段：

| 格 | 场景量 | 现状值 | 目标水平 |
|---|---|---|---|
| R1-a | 从查询到出价的耗时 | 访谈现场取 | 几分钟内 |
| R1-b | 报价带原始数据依据的比例 | 访谈现场取 | 全量 |
| R1-c | 首次被客户接受的比例 / 对可比历史成交价的偏离度 | 访谈现场取 | 不低于历史 |

**量必须可测，测法先定、水平后定。** 现状值是当趟访谈取样算出来的，不是拍的。取样条件（哪类样本、哪个时间窗、哪些字段、谁给导出权限）当场登记，复测时用同一条件。

问题类型在这一步定：发生型（现状偏离了本来该有的样子）还是设定型（现状没坏，要拉到另一个水平）。类型写进回答句的定语。

### 5.3 明确回答

固定句式：

> 我们解决的问题：<客户>的<环>决定<业务结果>；现在是<现状>。我们要让<格1>到<水平1>，<格2>到<水平2>，……

示例（逻辑示例）：

> 我们解决的问题：某制造企业每一单赚多少、成不成交由报价决定，现在报一次价要查很久。我们要让每次报价在几分钟内给出，价格有原始数据依据，对公司最好，客户也能接受。

回答句里不出现产品形态——产品是下一步的第一个决定。把回答句倒读一遍就是产品目标。

### 5.4 规则与反例

- 验收人当场否掉某个扩进来的格 → 该格降为护栏（guardrail），不占场景量名额。
- 原始数据拿不拿得到属可行性，这一步只问该不该有这一格。
- 业务结果进上溯、进观察，不写成量、不设百分比。
- 回答句要验收人当场认可。认可不等于签字；签字在功能层。
- 回边：新格冒出来 → 回现状链取数；两句都要复核（客户说的痛、上溯出的业务结果）。

**产物**：回答句 + 场景量表。这是闸 1 的第 1、2 条判据。

## 6 定义产品

- **回答句倒读 = 产品目标。**
- **产品形态**是这一步的第一个决定（工作台 / 助手 / 嵌入现役系统 / 独立工具）。
- **目标业务流**：逐段回溯到格。回溯不上的段落标观察项，不进范围。
- **体验流**：谁在哪个节点看到什么、点什么、留什么痕。
- **数据流**：标注哪一段需要什么数据，可取性留到第 7 章判。
- **牵连**：改一环带出的旁环登记进变更账本，不擅自扩范围。
- **Target First**：先定目标状态（哪一格到哪一水平），再谈手段。

**产物**：产品目标 + A 组材料（目标业务流、体验流、整体架构图）。这是闸 1 的第 4 条判据。

## 7 技术可行性（FDE）

**四层判据，逐格过。**

1. 数据可取：字段在不在、口径清不清、权限有没有、历史跨度够不够；
2. 系统可改：接口、并发、与现役系统的耦合；
3. 人力可支撑：谁做、多久、依赖谁；
4. 客户能配合的时间窗。

逐格出结论。任一层判死 → 走第 11 章回边，不就地改回答句。

**产物**：逐格可行性结论 + B 组九份 spec。

## 8 排序与迭代

先建数据底座，再上辅助决策。每轮迭代设场景量验收点。业务结果留观察，不进承诺。

**产物**：迭代计划 + 独立开发计划。

## 9 合同验收与结果核对

- **合同验收走功能层**：可判、可控的行为义务。场景量是功能层的量化形态，可以进验收。
- **业务结果不作承诺、不设百分比。** 它进结果核对，供迭代判断。
- **取样条件一致**：复测与基线用同类样本、同一时间窗；条件变化登记在案。
- 验收标准只到功能层；场景量可验收，业务结果只观察。

## 11 回边与降级 loop

```
闸1 回答句 + 场景量表 + 基线
   ↓
闸2 FDE 可行性
   ↓ 目标水平够不着（数据不可取 / 系统改不动 / 配合窗口不够）
重开触发的格 → 改水平或改手段 → 回闸1 差量审 → 再送闸2
   ↓ 全判据通过 = 达成 → 开发
```

**四条约束，缺一条就变成空转或无限循环。**

1. **只动触发的格**，回答句版本递增，回闸 1 走差量审（只看改过的格），不整体重审。
2. **每轮必须产出一个新事实**（某个字段确认取不到 / 某个接口确认改不动）。产不出新事实 = 原地打转，停。
3. **记录进变更账本**。
4. **两轮还到不了目标水平 → 降级谈判**：该格从目标降为护栏，或从范围里拿掉，范围与报价重谈。上限设在两轮，再往上属商务层，不在现场磨。

## 12 外部依据

- TOGAF ADM 的 Target First 触发条件：先定目标状态再谈手段；技术推动型方案在现状不清时设拉伸目标是红旗。
- 丰田 TBP 八步的问题解决序：明确问题 → 分解 → 设目标（说清是什么、多少、何时）→ 把握真因 → 对策 → 实施 → 评价 → 巩固。本手册第 5 章的三步与其中第 1、3 步对应。
- 楼宇节能测量与验证（IPMVP）的基线调整模型挂在业务结果——它把不同期的条件调平再比，服务的是"省了多少"这类结果判定。本手册量化落在场景层（时间、比例、偏离度），不引入该模型；只在第 9 章保留"复测与基线条件一致、条件变化登记"这一条纪律。
