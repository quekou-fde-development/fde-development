# FDE 开发技术手册

## 如何使用

先看 [FDE 总流程图（内部执行版）](<FDE_流程图_内部执行版.html>)，了解项目整体阶段、角色、决策和交接，再按本手册展开技术开发环节。总流程图与本手册 HTML 同目录保存时，该链接可离线打开。

本手册面向项目经理、承担方案设计与开发的架构师、FDE 和开发 AI。项目经理将 Arcubase 母项目与按项目编号命名的 GitHub 仓库关联；团队基于前置检索与调研语料形成开发文档和开发计划，开发文档包含业务流程与 spec 两个部分，上传仓库后由项目经理通过邮件异步送审。获批后实施、测试、发布，并将问题送回仓库反馈入口。开发是 FDE 全流程内部的一段 loop；商务、调研、客户培训、最终客户验收和维护按上层 FDE 流程衔接。

全文分为两个大部分。第一部分先用 **Meta Workflow（暂名）**，基于 Meta Skill 与 Meta Orchestrator 的理论结构，将调研材料整理为业务流程及其中的业务架构、系统分工；再用 **Meta Spec**，依据这些成果编写九份开发规格 Markdown。项目经理将包含“业务流程 + spec”的开发文档，以及按统一模板填写的独立开发计划，一并交总架构师夏洛克审核。第二部分在取得对应版本的审核通过记录后，在原项目仓库继续实施 Arcubase、数字员工、技能和工作台，完成联调、发布与上线测试。

> **当前版本：10.08。** 实际项目的架构批准、真实数据写入和发布授权，分别按项目记录执行。

统一发布入口是 [quekou-fde-development/fde-development](https://github.com/quekou-fde-development/fde-development)，主要目录为 `handbook/`（开发手册）、`tools/`（开发工具）和 `feedback/`（反馈）。仓库 Markdown 与 HTML 阅读版来自同一份正文；离线使用时一同下载 HTML 与[配套资源总 ZIP](<FDE开发配套资源包_10.06.zip>)，按文末资源索引选择小包。

整条开发链基于 **Octopus + Arcubase**：Workbench 承载页面与可信会话，Octopus 提供组织及 Host 能力，Arcubase 保存共享持久业务数据。工具包的“候选”“方法参考”“文件快照”状态见资源索引，项目采用前核对版本及目标环境证据。

**Arcubase 管理母项目及其子项目（场景），保存项目核心内容、关键决定和实际推进记录。GitHub 保存开发文档、代码、测试与发布版本等开发记录。** 两边以母项目编号、场景编号和对应链接关联；项目经理、场景负责人、当前阶段、卡点、支持事项及验收结果以 Arcubase 为准。业务流程文档表达待开发业务的设计；日常沟通、补料、阶段流转等项目过程记录在 Arcubase 维护。

| 工作位置 | 怎样做、需要填写什么 | 工具与输出 | 进入下一段的依据 |
|---|---|---|---|
| Arcubase 登记与建库 | 项目经理确认母项目及所属子项目（场景），按系统项目编号建库，按场景编号关联开发目录 | Arcubase 母项目与场景记录、固定名称的项目仓库、开发索引 | 母项目—场景关系明确，仓库和开发材料均可回到对应记录 |
| 前置检索与调研 | 收集访谈、观察、样本、规则、接口证据；填写通用输入的已知项和来源 | 项目已有检索与调研工具 → 输入文档、原件索引与缺件 | 来源可读，事实和未确认项有区分 |
| 业务流程与业务架构 | 用 Meta Workflow（暂名）梳理完整业务、执行与判断、交接及系统分工，集中澄清关键问题 | `workflow/` 正式业务流程材料 | 业务路径、规则、职责、系统分工及未决事项可审阅 |
| 开发 spec | Meta Spec 读取业务流程成果，按开发九步写规格 | `design/` 九份 spec Markdown | 与业务流程对应，设计关键问题已回答，跨文件含义一致 |
| 开发计划 | 按统一模板编写范围、任务依赖、负责人、时间、资源及验证安排，与业务流程和 spec 版本对应 | 独立的 `plan/开发计划.md` | 开发文档与计划两项交付物齐备 |

| 获批开发 | 在同一项目仓库按批准版实施，持续 push 实现及验证材料 | Meta Skill、Meta Agent、Meta Orchestrator、Workbench 及专项工具 → 代码、资源与运行证据 | 用例及权限等验证通过，具备发布条件 |
| 发布、试运行与反馈 | 按授权发布，正式入口复测；提交问题及证据 | 部署回执、测试记录、仓库 Issue | 反馈有归属、处理记录和结果回写 |

总架构师负责架构合理性、商务策略匹配性、开发周期和难度、可实现性的审核。PM 统筹范围、资源和客户配合，负责母项目与场景登记、仓库管理、正式邮件送审，并在 Arcubase 留存审核与推进结果；架构师负责方案及架构变更，FDE 负责按计划开发和提供实测证据，二者配合技术答疑。正式送审由 Arcubase 母项目记录中的项目经理发起。开发 AI 在指定文件和工具边界内执行。

### 产出格式与填写规则

开发文档由业务流程和 spec 两个部分组成。业务流程保存在 `workflow/`，包含完整流程、执行与判断说明、规则依据、交接、业务架构和系统分工。spec 保存在 `design/`，由 Meta Spec 基于业务流程成果编写九份 Markdown；沿用现有九份文件名及写作参照。王磊八份原设计作为写作参照，独立数据结构为第 3 份。案例中的业务、登录、技术栈与接口须按本项目和 Octopus / Arcubase 边界重新设计。

- 填写通用调研输入的已知事实、客户意向、约束及来源。未知项写“未确认＋向谁或取什么材料确认”；没有该场景时写“不适用＋理由”。已有原件能够回答的内容直接附材料位置。
- 业务流程和规格设计中的关键问题分别集中澄清。Meta Spec 发现业务目标、规则、职责或流程仍有缺口时，返回业务流程环节补齐；九份规格引用明确的业务流程版本。能力未实测和上线前验证要求写为限制，保留负责人和下一步。
- 需求、流程、用例、数据、角色、页面、调用和测试使用稳定编号；业务流程、九份 spec 和开发计划中的同一对象保持一致。
- 设计、实际实现、测试结果与审核决定分别记录。总架构师审核由夏洛克进行，工具检查通过只说明其覆盖的检查项。

来源快照、草稿和澄清过程在 `working/` 中保留；收束后的业务流程、业务架构和系统图进入 `workflow/`，作为正式开发文档的一部分，与 `design/` 下九份 spec 一起送审。开发计划按[统一模板](<inputs/开发计划模板_10.08.md>)填写，独立保存在 `plan/开发计划.md`。实施后的 Schema、typed SDK、员工配置、Skill 包、代码及部署回执按相应工具原生格式保存；在项目内登记版本、实际 ID、证据位置与限制。

上述 `workflow/`、`design/`、`plan/` 均归属明确的场景开发目录。覆盖多个场景的共享开发内容须列出涉及的场景编号及各自范围。Arcubase 保存原始业务资料的权威入口、关键澄清与决定；GitHub 中的正式开发文档引用这些记录。`working/` 的运行草稿与取源快照按工作区和资料权限保留，不要求作为项目过程档案上传 GitHub。

## 第一部分 形成业务流程、spec 与开发计划

### 1 整理检索与调研输入，启动业务流程设计

架构负责人先收集并核对前置检索结果、调研原件和已经确认的需求，建立同一项目的材料入口。填写现有[通用调研输入文档](<inputs/通用调研输入文档_10.06.md>)的项目副本；资源总包的 `inputs/` 中也提供同一空表。至少能找到：业务目标与交付范围、参与角色、关键场景、真实样本、当前规则与异常、既有系统和可用接口、验收范围与验收标准，以及客户必要的授权和配合事项。

把事实、已确认规则、待核实假设分开标注，并为每条重要结论附原件位置。遇到缺样本、规则冲突、关键接口未知，登记具体缺件与负责人；由 PM 协调补齐。影响范围或技术路线的缺件在架构送审时明示，不交给开发 AI 自行补成事实。

材料索引分别记录两种状态：原件是否取得并实际读取；相关能力处于文档说明、源码核对、样例验证还是目标环境实测。来源未取得正文、现场尚未验证等情况随送审包保留。

**工具路线：** Meta Workflow（暂名）负责业务流程，采用 Meta Skill 与 Meta Orchestrator 的理论结构；Meta Spec 读取业务流程成果并编写九份 spec。工具拆分与现有源码入口见文末资源索引。

**怎样启动：** 把填过的输入副本、原件位置和本次工作目录交给业务流程设计环节。输入允许部分填写；先取源、梳理流程与业务架构，再集中澄清。将可审阅成果保存到 `workflow/`，标明版本和来源，随后交给 Meta Spec。九份规格中的设计选择应能回到业务流程或有权人的明确决定。

**填写重点：** 调研范围和角色、真实作业路径、异常与决定权、单据和样本、现有系统、目标与交付范围、验收依据、Octopus / Arcubase / Workbench 已知环境及授权。既有 App 记录真实 ID 与 Schema；拟新建 App 写计划与依据。

**产出：** 通用输入项目副本、来源快照与缺件记录，进入本次运行的 `input/`、`working/`；正式业务流程材料进入 `workflow/`。沿用已有调研成果，只针对业务流程与架构缺口补证。

```text
先按 Meta Workflow 的职责处理本项目，再将结果交给 Meta Spec。
输入文档与原件位置：<填写可访问的文件或链接>
本次工作目录：<填写输出目录>
先读取来源，梳理完整业务流程、执行与判断、业务架构及系统分工；
关键问题集中确认，形成 workflow/ 下可审阅的正式成果。
随后基于明确版本的业务流程编写 design/ 下九份 spec。
开发文档的业务流程和 spec 两部分共同保持“待总架构师审核”，
并按模板准备独立的开发计划，报告未决事项和未验证能力。
```

### 2 拆解业务流

Meta Workflow（暂名）以 Meta Orchestrator 的目标分解、流程结构与依赖分析，以及 Meta Skill 的目标、执行段、判断段和判据分析为理论基础。本节与 §3 共同形成开发文档的“业务流程”部分，包含业务架构与系统分工；正式的员工、Skill 包编译在第二部分执行。

完成时序流程后，再按 Orchestrator 判断工作形态：单条线性的工作，直接展开其执行与判断段；涉及多个主体、时间跨度、独立触发或独立完成核验的工作，再建立跨段网络。每次拆分要写出理由，避免仅按职能名称或页面数量增加节点。

#### 2.1 从结果倒推完整任务

为选定业务写清最终结果、成功与失败条件、谁使用结果、谁有权作决定。再用一条真实案例，从触发开始顺着信息与动作走到结果：谁发起，拿到什么，做了什么，交给谁，如何知道已完成。

把规则表和职责表还原为“何时、满足什么条件、做什么”的时序事实。流程图标出持续等待或中断、需要裁决的分叉、同时开展的分叉；由材料推断出的关系单独标注。保留事实清单，检查每项必要事实和动作在流程中的归宿。

保留人工环节、系统外环节和异常分支。例如，业务员确认异常原因、负责人批准处理、客户补充资料，都应有输入和输出。自动化范围由任务需要和实际能力决定。

#### 2.2 逐段区分执行与判断

执行段是按明确规则完成操作、留下可观察成果的部分；判断段根据证据作出选择，并改变后续走向。为段落编号，写明正常顺序、分支、汇合、等待、失败返回和结束条件。并行段需要说明启动前提、共同依赖、合流条件和失败接手人。

为执行段填清下面内容。此时描述业务与系统所需能力；进入 Skill 蒸馏时，再按现役 Meta Skill 补齐其机器契约和验证要求。

| 执行段字段 | 必须回答 |
|---|---|
| 动作与对象 | 谁对哪个对象做什么 |
| 输入与依据 | 读取什么材料或数据，遵循哪条规则 |
| 可达入口 | 经哪个系统、工具、接口或人工交接完成；可用性是否已确认 |
| 产出与位置 | 形成什么记录或状态，保存在哪里，交给哪一段 |
| 合法结果与核对 | 哪些值或状态才成立，怎样核对操作产生的结果 |
| 影响与失败 | 是否改业务数据、发消息或触发后续动作；失败、重复、状态未知时怎样处理 |

#### 2.3 展开判断过程

每个判断段按四个相位追问：检索需要什么证据；整合时如何处理来源冲突；形成哪些候选解释或方案；审核时依据什么标准选定，并转向哪一段。

最终留下三件事：**判断标准、触发条件、逐分支去向**。标准已有权威来源时直接引用；需要从案例提炼时同时看成功、失败和边界案例。证据不足的判断标明假设、适用条件和待补项，保留有权人员的判断位置。不得用模型生成的数字补业务阈值。

每个判断段都应覆盖信息不足的情况：需要补什么、交给谁、何时重新判断。禁止把“视情况处理”作为流程终点。

多段协作时，逐条检查交接：下游启动所需数据和授权是否齐备，交接者是否有权作该决定，等待是否有负责人、期限与兜底。需要独立确认完成的段，定义完成凭据；需要跨时段存活的工作，定义中断后的接手或重启条件。关键事实与必要动作都应有明确归宿。

#### 2.4 用样本推演并收束

至少推演一条主流程和项目最重要的异常路径。逐段检查上游产物能否作为下游输入、对象与状态是否一致、每个分支有没有接手者和终点。发现缺口回到对应段修订；推演只说明设计的连贯性，实际运行效果在开发后验证。

**产出：** `workflow/` 中可审阅的业务流程图、段落说明、规则来源、正常及异常案例、未决事项。读者应能沿着编号复述一件业务如何完成。

### 3 完成业务流程中的业务架构与系统分工

沿业务流逐段决定由人、既有系统、新建应用、数字员工或 Skill 承担。先确认每一段需要的能力、身份、数据和动作，再划分模块与角色。一个员工可以调用多个 Skill，一个 Skill 可以服务多个用例；是否拆分依据职责、复用、权限和运行依赖。

系统架构至少说明下列关系：

| 设计面 | 应表达的内容 |
|---|---|
| 系统边界 | 项目交付到哪里；客户既有系统、平台能力和人工工作各承担什么 |
| 模块职责 | 每个模块负责哪些流程段、产出什么、由谁维护与接手失败 |
| 数据流 | 数据从哪来、以哪份记录为准、如何流转与更新、哪些只是展示或缓存 |
| 控制流 | 谁触发员工或任务，谁批准有影响的动作，谁可以中止，结果返回哪里 |
| 能力与入口 | 数据表、Workbench 页面、员工、Skill、API 或其他工具如何连接；哪些能力已经核实 |
| 关键约束 | 身份与权限、业务时效、数据量、运行成本、重复执行与恢复等会改变方案的条件 |

统一画出整体系统图，并附“业务段 → 承担方 → 数据 → 工具入口 → 结果接收方”对应表。系统图中的每条调用和数据连接，都要在表中找到依据。

出现技术缺口时，先区分参数、版本、身份、权限、环境与能力缺失。记录需要支持的用例、预期能力、已核查证据和替代方案，交架构负责人判断；涉及对外承诺或客户投入变化时，由 PM 接回上层决策。

**产出：** `workflow/` 中的正式业务流程材料，包含流程、判断与执行说明、业务架构、系统图、职责、数据流、依赖和未决事项，并提供统一阅读入口。与 §2 的成果一起交给 Meta Spec，保留流程编号、来源和决定依据；业务流程部分与后续九份 spec 共同送审。

对照 Orchestrator 原规格，审核前使用其 Step 0—3 的事实清单、流程判别、切段和边约束方法。此时的系统图属于架构设计；依赖实际 Skill 包的最终网络声明、版本核对和运行测试，留在审核通过后的编译与联调中完成。

### 4 基于业务流程编写九份 spec

以下九步说明 Meta Spec 每份文档应怎样形成、填写什么及怎样核对。起草前读取明确版本的 `workflow/` 成果、相关来源与同编号写作参照，将业务流程和业务架构落实为开发所需的具体规格。按下列顺序起草，发现冲突时返回关联项修订；需要改变业务范围、规则或职责的事项，回到业务流程环节澄清并同步两个部分。安全约束贯穿各项，数据模型与权限、页面与接口需要往返核对。

#### 第 1 步 概念梳理

从流程和真实样本提取业务对象、角色、术语与关系。对容易混淆的词写清含义、范围、唯一标识和边界；区分业务名称、系统内部名称及外部系统名称。把业务规则挂在对应概念上。

**交出 `01-concept.md`：** 术语表、角色与对象关系、关键约束、原始样本指针。后续用例、表格、页面和接口沿用同一含义。

**完成检查：** 同一对象跨文件可识别，关键名词有定义；未知关系明示，未被 AI 补造。

#### 第 2 步 用例

按真实角色和目标写编号用例。每条用例包括发起者、触发条件、前提、输入、主流程、成功结果、失败及异常、权限要求和对应验收项。把前段业务流程编号关联进来。

**交出 `02-use-cases.md`：** 用例及验收对应表、主流程和异常样本。页面点击、员工触发和定时任务都应追到用例。

**完成检查：** 已确认的验收范围有覆盖；每条用例能说明业务完成后会留下什么可检查结果。

#### 第 3 步 数据建模

架构负责人结合用例与样本，与 AI 逐项讨论表格结构。先确定一行代表什么，再确定唯一键、字段、关系、状态及转换、约束、来源、写入者和读取者。记录计算值的规则，区分主数据、业务事件、当前状态和派生展示。

将设计落实到 Arcubase 的计划结构：App 采用既有还是新建、表与字段的稳定 key、类型、必填及合法值、关联、业务编号、访问范围和可调用入口。复用已有 App 时先回读其真实 Schema，列明保留、扩展和迁移内容。尚未创建的资源只写计划名称与 key，实际 ID 留待获批实施后回填。

**交出 `03-data-model.md`：** 表与字段字典、关系及状态图、数据来源与权威位置、样例映射、拟采用的 Arcubase 结构和待核实能力。

**完成检查：** 用例需要保存和读取的事实都有位置；重复、历史、状态变化和授权关系能表达。第三步完成后，后续建表以该版结构为依据。

#### 第 4 步 权限与安全

按“角色 × 对象 × 动作 × 数据范围”定义授权。区分可信登录身份、应用业务角色、对象归属与项目成员关系，明确它们的映射和唯一维护入口。敏感动作标明批准者、批准记录和审计要求。

**交出 `04-security-privacy.md`：** 权限矩阵、身份映射、授权维护方式、后端执行位置、敏感数据规则、重复操作和失败处理要求。

**完成检查：** 允许与拒绝路径都能说明；页面隐藏按钮以外，后端或数据层有对应约束；没有需要人工长期维护的多套角色名单。

#### 第 5 步 站点架构

沿整体系统架构，为不同角色安排工作台入口、菜单、路由和任务之间的转场。列清哪些任务由页面完成，哪些进入员工会话、人工审批或外部系统。各页面注明对应的用例、对象与权限。

**交出 `05-site-architecture.md`：** 站点结构图、路由与页面清单、角色入口和跨系统交接。整体模块职责和数据流引用前面的系统架构总结。

**完成检查：** 核心用例有可达入口和返回位置；没有脱离业务与后端能力的孤立页面。

#### 第 6 步 页面布局与视觉交互

逐页确定主任务、信息层级、主要操作、字段与数据来源。把加载、空、错误、成功、无权限和等待人工处理等状态画出来。按项目选定的视觉参考包，明确布局、组件、颜色、字体、密度与适配要求，并标注引用了哪个参考页面。

本手册的前端基线为 **`quekou-工作台前端共享包-1.0.0.zip`**。按包内 `START_HERE.md`、`design/style-spec.md`、`design/page-recipes.md` 和组件说明读取。第 6 步写清所选风格：6 号 Bento、7 号 Glass 或 10 号 Ambient，以及 `accentHue / density / radiusScale / surfaceMode` 四项参数；未另行选择时沿包的 6 号与缺口品牌色起草，随架构送审。

页面采用包内 Overview、List、Detail、Settings 配方与标准区块；每个页面选择适合其用例的配方。正式配方顺序以 `design/page-recipes.md` 为准，样品页仅作相应视觉参考。超出现有配方或参数范围的需要，先说明业务理由和视觉扩展方案，随设计审阅。

**交出 `06-page-layout.md` 及必要原型：** 关键页面布局、状态与动作说明、视觉参考、组件约定。演示数据应明确标识，不进入正式业务运行逻辑。

**完成检查：** 使用者能找到任务和操作；按钮对应真实动作；真实长文本、空数据、错误和权限状态有表达。视觉参考的业务结构须经本项目用例筛选。

#### 第 7 步 API 与调用契约

按用例列出页面、员工、Skill 和既有系统实际使用的调用入口。每项写清提供方与调用方、输入输出、身份权限、错误语义、分页或批量、幂等与重复处理、超时和结果回读方式。

**交出 `07-api.md`：** 调用契约及能力映射。采用 Arcubase 时包括 typed ingress 的计划；采用平台现成客户端时引用其真实契约；需要自建接口时说明理由、责任模块与生成方式。

**完成检查：** 页面动作和技能执行都有可达入口，调用双方理解一致。接口变更需要同时追踪数据模型、调用代码及测试。

#### 第 8 步 技术选型与目录

为已确认架构选择实施工具，写明采用、复用与新增的依据。数字员工使用 Meta Agent，技能使用 Meta Skill，Workbench 工作台使用 `workbench-app-development`。结构化业务数据按第 3 步落到选定 Arcubase App；其他系统接入沿第 7 步契约实施。

**交出 `08-tech-stack-and-directory.md`：** 工具与 Skill 的精确入口、实读版本或提交、项目代码与文档目录、认证方式、环境、依赖及锁文件、生成代码位置、部署目标和运行责任。

**完成检查：** 开发 AI 找得到全部指定文件，工具路线与平台能力相符。涉及排产、图纸识别、爆品识别时，按文末“专项任务与工具”确定入口，并将项目采用的工具、接口验证状态和验收方法写回本步骤。

#### 第 9 步 实施与验证路线

把用例拆为任务，注明输入、产物、前置依赖、负责人和完成条件。先安排一条覆盖真实数据、身份、业务动作、保存与回读的完整链路，再扩展其余用例。只有共享数据、权限和调用契约已经明确的任务，才安排并行。

**交出 `09-implementation-roadmap.md`：** 依赖顺序、阶段目标、难度与周期估算依据、关键风险、联调与测试计划、上线条件和恢复准备。

**完成检查：** 能说明先做什么、为什么、如何知道做完。该文件表达架构内的实施与验证路线，并与 §5.1 独立提交的开发计划保持一致。

### 5 汇总业务流程与 spec，准备送审

开发文档以统一阅读入口组织两个部分：`workflow/` 保存业务流程，`design/` 保存 spec。Meta Spec 输出以下九份规格文件，第 7 份的文件名为 `07-api.md`，按同一清单提交和核对：

```text
design/
├── 01-concept.md
├── 02-use-cases.md
├── 03-data-model.md
├── 04-security-privacy.md
├── 05-site-architecture.md
├── 06-page-layout.md
├── 07-api.md
├── 08-tech-stack-and-directory.md
└── 09-implementation-roadmap.md
```

执行人员检查业务流程、九份 spec 与开发计划中的范围、对象、角色、状态、权限、入口、契约、依赖及完成要求是否一致。三者使用明确的项目、版本和输出位置；来源与澄清过程可从本次 `input/`、`working/` 回查。Skill 的文件核验只证明其覆盖的机械条件，业务与技术设计的合理性由总架构师审核。

#### 5.1 两项送审交付物：开发文档与开发计划

每次正式送审必须同时包含以下两项独立交付物，由项目经理核对齐备后统一提交：

| 交付物 | 保存位置 | 必须包含的内容 |
|---|---|---|
| 开发文档 | `workflow/` + `design/`，提供统一阅读入口 | **业务流程**和 **spec** 两个部分。业务流程包含流程图、执行与判断、规则依据、交接、业务架构及系统分工；spec 为基于这些成果编写的九份开发规格 Markdown |
| 开发计划 | `plan/开发计划.md` | 按统一模板填写本次范围、任务与依赖、负责人、时间安排、资源及客户配合、完成与验证要求、未决事项；标明所依据的业务流程和 spec 版本 |

**九份 Markdown 共同组成 spec 部分。业务流程和 spec 均为正式送审内容。** 开发文档的阅读入口应先展示业务流程，再链接到九份规格；开发计划单独成文、单独提供链接。spec 中的 `09-implementation-roadmap.md` 与开发计划保持一致，开发计划进一步落实项目执行安排。

本仓库提供[开发计划模板](<inputs/开发计划模板_10.08.md>)。项目经理组织填写，保存到对应场景开发目录的 `plan/开发计划.md`；送审前补齐任务、负责人、依赖和完成要求。尚未确认的日期、资源或客户配合事项须说明影响、确认责任人及下一步。计划保存本次开发安排的版本，实际进度、卡点、支持请求和关键决定在 Arcubase 持续维护。开发文档与计划提供相关 Arcubase 资料和决定的链接，并注明未验证限制。

架构师与 FDE 负责准备、修订材料和技术答疑；**Arcubase 母项目记录中的项目经理负责正式送审**，对材料齐备、版本一致、链接可访问及意见落实负责。

#### 5.2 项目登记、固定命名建库与邮件异步送审

**一、先在 Arcubase 确认母项目及子项目（场景）。** 母项目登记所属客户、期数、承接团队、项目经理、项目成员与角色及本期交付范围；每个子项目以独立场景记录关联所属母项目，分别维护场景编号、说明、负责人和当前阶段。场景的阶段流转、卡点、支持事项和完成证据按实际发生情况登记，母项目汇总所属场景的进展。送审范围必须明确落到一个或多个场景。母项目编号和场景编号以 Arcubase 实际记录为准，后续文档、仓库和邮件统一引用。

**二、按母项目编号建立唯一仓库。** 每个 Arcubase 母项目对应 `quekou-fde-development` 组织下的一个项目仓库，客户交付项目默认设为 private。仓库名必须与母项目编号完全一致，例如 `QK-2026-001`；本例仅说明命名形式，实际建库必须读取真实编号。各子项目沿用 Arcubase 场景编号，例如 `QK-2026-001-S01`，在同一仓库中对应各自开发目录；共享模块在项目层维护，并说明服务哪些场景。已有对应仓库时核对后沿用；项目经理缺少建库权限时，由组织管理员协助。

**仓库名一经确定保持不变。** 项目显示名称、人员、阶段和版本变化均沿用原仓库；项目结束后按管理要求归档。遇到编号与仓库对应异常，由项目经理登记并核实，禁止私自改名或删除重建。

**三、关联开发入口，先 push 开发材料。** Arcubase 母项目的“项目资料链接”保留项目资料总入口的用途，在该资料索引中登记 GitHub 仓库、各场景的开发目录及送审版本链接。仓库 README 保存母项目编号、Arcubase 母项目链接，以及“场景编号 → Arcubase 场景记录 → 开发目录”的对应索引，并提供开发文档、开发计划、代码、测试和发布版本入口。正式项目资料、关键决定和过程记录在 Arcubase 维护，GitHub 引用对应记录。首次送审前，将对应场景的 `workflow/`、`design/`、`plan/开发计划.md` push 到仓库，检查审核人能够访问，并记录本次提交的 commit。实现代码、技术变更与测试记录随获批开发持续 push。

**四、由项目经理发邮件异步送审。** 邮件发给总架构师夏洛克，分别列出开发文档和开发计划的阅读链接，两个链接均指向本次送审的固定 commit；开发文档入口须能访问同一版本的业务流程与 spec。正文写明项目与场景范围、需要审核的具体事项、本次变更和未决事项，采用以下格式：

```text
主题：【项目编号】【架构送审】【版本】项目简称

项目：项目编号、客户、期数
范围：场景编号与名称
Arcubase：母项目记录链接、各送审场景记录链接
GitHub 仓库：仓库链接
送审版本：commit
开发文档：该 commit 下的入口，包含业务流程与 spec
开发计划：该 commit 下的阅读链接
请求审核：需要确认的具体事项
本次变更／未决事项：……
项目经理：姓名
```

**送审采用异步方式，不要求总架构师即时响应。** 项目经理发出邮件后等待异步审核意见，并安排团队继续推进不依赖该审核决定的准备工作。IM 发包、聊天中询问“是否可以开发”或临时要求同步审阅，均不作为正式送审方式。材料需让审核人按自己的时间独立读取、判断和回复；技术答疑及修订由项目经理统一组织。

**五、在 Arcubase 留存审核与推进结果。** 项目经理将夏洛克本人对明确开发版本的审核结论及意见来源关联到对应母项目和场景，记录审核人、时间、送审 commit、各场景获批范围、决定和条件。GitHub 保留被审核的开发版本及对应 Arcubase 记录链接。实施人员依据各场景的通过记录领取批准文件和条件；退回时由项目经理在 Arcubase 组织补料与问题处理，架构师修订开发文档，push 新 commit 后由项目经理重新发邮件送审。

邮件已发送只表示完成送审。尚未取得通过记录的场景范围继续保持待审；按审核结论和实际推进情况更新 Arcubase 场景阶段，阶段流转记录写明变更原因和影响，“新版本／依据链接”关联相应审核依据与开发版本。母项目的“项目交付流程”维护整体交付环节，场景进展按所属关系汇总。AI 可整理材料与检查引用，审核决定由夏洛克作出。

## 第二部分 审核通过后开发

### 6 领取批准文件，在原项目仓库开发

FDE 核对审核通过版本、本次实施范围、条件与实际环境。PM 按 §5.1 已提交的开发计划统筹资源、客户配合和交付安排，并落实审核附带的条件。

开发继续使用 §5.2 已建立并与 Arcubase 母项目关联的仓库，名称和项目编号保持不变。对应场景的 `workflow/`、`design/`、`plan/`、实现代码、资源映射、技术变更及测试发布版本持续维护在 GitHub，并引用 Arcubase 中相应的批准依据。项目核心内容、日常推进、审核与验收结论由 Arcubase 维护；仓库记录采用的通用手册与工具版本。项目材料按对应访问权限保存，凭据按环境配置管理。公共规范仓库集中承载共用手册、工具与可公开的反馈。

把批准的业务流程、spec 与开发计划交给开发 AI，要求实际读取本任务指定的 Toolkit、Skill 和 references，回报已读文件、采用版本、输入和输出。开发任务写清：批准版本、用例、允许修改的目录和资源、指定工具、真实样本或授权测试记录、预期结果、完成条件和阻塞接手人。实现、实际测试和未验证项分别报告。

### 7 按依赖安排开发

| 对象 | 必须使用的路径 | 直接输入 | 应交出的结果 |
|---|---|---|---|
| Arcubase 数据结构 | 按 Workbench Skill 的 Arcubase 合同调用官方工具 | 第 3、4、7 步及已选 App | 实际 Schema、资源 ID、权限与 typed ingress 回读 |
| 数字员工 | Meta Agent | 业务目标、角色职责、权限、协作与用例 | 员工产物、能力与工具绑定、测试和待确认项 |
| 跨段协作分析 | Meta Orchestrator | 目标、业务时序、段落与交接关系 | 架构分析及依赖说明；完整编译和运行能力以工具包状态为准 |
| 技能 | Meta Skill | 流程段、规则、样本、调用契约和结果要求 | Skill 包及相应检验、运行证据 |
| Workbench 工作台 | `workbench-app-development` | 第 3—8 步、视觉参考和真实资源 | 官方脚手架上的应用、本地可操作链路和验证证据 |

业务事实、判断规则、数据 Schema 分别明确权威位置：事实来自相应业务记录，规则进入获批设计或知识来源，Schema 定义字段与关系；修改其中一类时追踪其对其余两类的影响。Taskboard 用于任务和项目跟踪；自动化由实际员工、Skill 与触发机制执行，审批以有权人员的真实决定记录为准。

先确认身份、资源和共同契约，再启动依赖它们的实现。员工与 Skill 的设计可以依据批准文件协同推进；需要实际数据表或工具 ID 的绑定，等资源落地回读后完成。按照第 9 步先跑通一条完整用例，再展开更多功能。

### 8 落实 Arcubase 表格结构

1. 读取批准的 `03-data-model.md`、权限设计和调用契约，明确本次使用既有 App 还是新建 App。审核材料已明确选择的，沿用该选择；多个候选无法区分时补齐准确 ID 后再操作。
2. 按 Workbench Skill 核对 `profile / host / account / team`。团队资源查询及每次外部写入前使用 `octopus-cli auth whoami --json` 核验上下文。
3. 读取目标 App 当前 Schema，把批准结构与实际表、字段、稳定 key、关系、入口和权限逐项比对。只实施已授权的新增或变更，保留现有业务数据及不相关结构。
4. 使用官方 `octopus-cli arcubase-admin` 合同建表或调整 Schema，保存真实返回 ID，立即回读核对。未知参数先读该命令当前 `--help`。
5. 生成 typed ingress 代码。具备相应管理权限和正确团队上下文时，使用 `octopus-cli arcubase-admin dev sdk-gen --app-id <appId> --out src/arcubase`。官方本地应用已声明 `arcubase:codegen` 时，先读脚本帮助，使用 JCode 路径：`npm run arcubase:codegen -- --app-id <appId> --team-id <teamId> --out src/arcubase`；包管理器依项目确定。该本地路径不用旧 `--web-url` 参数，未知参数不猜测。Schema 或策略变化后重新生成。
6. 在已授权的测试记录上核对读、写、关系、规则和拒权，写后回读。将逻辑设计与实际资源的对应更新到项目资源记录中。

**交出：** Schema 回读、App/表/字段/入口映射、生成代码、权限及样例验证记录。Arcubase `appId` 与 Workbench 发布 `projectId` 各自保留。

开发时需要改表含义、状态、关系或授权模型，先定位受影响用例和设计文件，交架构负责人处理；涉及已批准架构的变更，重新取得相应审核决定后实施。

**数据写入注意：** 真实环境测试默认只读；写测试须有对应 App、操作和测试记录的授权。日期时间及业务编号字段先读现役 `arcubase-runtime-gotchas.md`，首条写入立即回读核对。不得自行换掉已批准的编号规则。

### 9 用 Meta Agent 制作数字员工

把获批的业务目标、职责、用例、协作关系、知识来源、权限、工具入口、人工决定点和失败接手要求交给 Meta Agent。按实际安装版本的入口读取和执行，输出位置保存在所属项目。

使用前取得项目指定的 Meta Agent 包，核对入口、目标宿主、依赖和验证状态。包尚未接入时，先完成工具准备；员工制作继续遵循 Meta Agent 路线。

组织内数字员工按 FDE Meta Agent 路径准备五块规格：身份、职能、权限、面孔、环境。环境中列出实际团队、员工目录、模型与技能目录、知识库路径、工作区和所需表格。所需工作区、知识库、Arcubase 和触发任务按各自工具预先落实或另行安排；Meta Agent 负责员工构造及配置。

依据指定包完成环境连通、规格校验、身份与目录解析、提示词与简介编译、形象生成与核对、员工创建或更新、配置逐项写入与回读、最终完整回读。原规格列出的九类配置和十六项回读按包内清单逐项完成，保存期望配置、实际配置、证据和交付清单。需要对外发布市场产品时，另按 Meta Agent 的 Builder 路径及其发布授权处理。

员工设计要能说明：接什么任务、负责什么结果、何时调用哪个 Skill、怎样获取授权数据、哪些动作要等待人工决定、怎样报告完成或失败。选择已有员工复用或新建员工时，依据批准的系统架构，避免出现重叠职责和多套规则来源。

员工产物生成后，完成工具与 Skill 的实际绑定，并在目标宿主验证。至少覆盖正常任务、材料不足、无权访问、执行失败、需要人工决定及越出职责的输入。报告所用身份、实际触发、工具动作、保存结果、接手人和未覆盖项。

工具必须安装或接入到员工实际可访问的设备或云端环境。记录宿主、执行身份和真实工具路径，Skill 使用该路径，测试从员工侧触发并回读结果。开发者自己能调用工具，不构成员工可调用的证据。

需要人工决定的动作，只读取相应对象、版本和有权人员的真实决定。未回复时等待或按已定规则升级，拒绝时进入拒绝分支；员工和 Skill 不得代替人作批准，也不得继续执行依赖该批准的动作。

**交出：** Meta Agent 生成的员工文件与配置、实际绑定、测试记录及运行边界。员工岗位正文或头像已存在，只能说明相应配置已经形成；可交付状态以实际任务结果为依据。

### 10 用 Meta Skill 蒸馏技能

按批准的技能划分，把业务流中的执行段、判断段、权威规则、正反样本、接口契约、输出位置和权限交给 Meta Skill。所有本项目技能蒸馏统一经 Meta Skill 入口处理。

蒸馏依次完成目标与边界、段落切分、判断与执行展开、判据来源和缺料处理，再编码并检验 Skill 包。现役 Meta Skill 的机器契约、触发检验、独立检验和回流要求随包执行；手册只规定业务输入和交付要求。

审核前形成的分析材料作为正式蒸馏的输入。正式制作仍走 Meta Skill 完整流程，核对输入与批准版本，并保留该次编译的实际产物与检验记录。

涉及写业务数据、发消息、启动任务等副作用时，按 Meta Skill 的 stateful 工作流要求，明确重复执行、未知状态、失败恢复和人工接手。没有核清外部结果前，不直接重试同一写入。

把检验通过的包部署或绑定到目标员工后，再在该宿主运行授权用例：确认 Skill 被实际触发，读取了指定规则与真实数据，执行了获准动作，结果可回读，人工决定有真实记录。定时或事件业务先明确执行员工、目标与范围、时区和业务日历、触发方式及重复执行规则，再验证真实触发、执行和结果保存的整条路径。

**交出：** Skill 包、版本、评测与运行记录、宿主绑定、未验证范围和失败回流位置。技能问题回到对应步骤或判据修订；涉及业务规则、权限或架构的改变，先进入项目变更路径。

### 11 用 Workbench Skill 开发工作台

开发 AI 必须读取 `workbench-app-development/SKILL.md` 及相关 references。新应用使用官方 Workbench React 脚手架和 `octopus-cli`；已有应用先检查目录、依赖和生成 facade，保留现有代码。认证沿用 `@syngy/workbench-auth`。

前端同时读取已归档共享包的 `AGENTS.md`、`.agents/skills/quekou-workbench/SKILL.md`、主题和组件 README。该包提供视觉与组件能力；正式项目的创建、认证、数据与部署遵循 Workbench Skill。包内 `scripts/create-client.mjs` 创建独立前端客户项目；本手册的正式 Workbench 应用保留官方脚手架和既有认证，以消费主题与组件包的方式接入视觉层。

在官方应用内消费归档包 `artifacts/quekou-theme-1.0.0.tgz` 和 `artifacts/quekou-ui-1.0.0.tgz`；本版以本地包交付。按要求先导入 `@quekou/theme/tokens.css`，再导入 `@quekou/ui/styles.css`，由 `ThemeProvider` 承载所选风格和四参数。UI 包声明 React / React DOM `^18.3.1`，接入前核对目标应用的实际依赖与锁文件。使用 Tailwind preset 时核对其 Tailwind 3.4 要求；纯 CSS 消费可不引入该 preset。其他版本的兼容性缺口交架构负责人明确处理，不擅自更换已批准技术路线。

使用包内组件、标准区块和四种页面配方。颜色和尺寸引用相应 token；保留状态文字、键盘焦点和交互语义。组件中不另写字面量色值或内联样式。表格使用稳定行 ID，区分本地计算与服务端分页、排序、授权；后端能力由业务应用接入。演示页中的金额、AI 摘要和内存保存示例不能代替真实接入。

视觉数值的唯一可编辑来源为 `design/tokens.json`，生成的 CSS/TypeScript 不手改。正式 List 配方按筛选、排序、分页的次序组织数据；当前页全选的含义与跨页批量操作明确区分。主题切换保留当前对象、筛选和选择；设置页区分草稿与已保存状态。

按获批需求选择能力：仅认证页面无需额外业务客户端；使用 Host 资源选 `octopus`；任务与项目选 `taskboard`；共享持久业务数据选 `arcubase`。按 Skill 的选择规则安装与使用官方客户端，记录实际依赖和锁文件。

逐条用例实现页面与动作：从目标 App 或平台获取真实数据，按第 6 步落页面，按第 7 步接生成接口。每个主要按钮必须执行它所声称的动作，展示处理中与错误，成功后回读并刷新结果。真实空数据展示空状态。

权限同时验证界面和后端。前端消费当前会话的有效授权，后端约束读取和写入；平台管理员身份、团队成员身份与本应用业务权限分别核对。权限变更与撤销沿批准的唯一维护路径验证。

按项目实际声明的命令启动本地开发，使用官方本地登录/JCode 流程。记录实际 URL、身份与团队、selected features、App ID 和真实数据证据。不得只凭编译成功、SDK 生成或管理员 CLI 调用成功宣布页面可用。

**视觉复核：** 对照第 6 步批准的参考与布局，在真实数据下检查信息层级、内容密度、主操作、长文本、空错状态、权限状态以及约定屏宽。遵循包内正文及辅助文字至少 4.5:1 的对比度要求，核对键盘与焦点、明暗和密度、弹窗取消与失败、手机页面无整体横向溢出。表格在自己的容器内滚动。原型图和实际页面并排检查，并保留关键页面截图。

按包内 `docs/上线验收.md` 补验真实对象和指标口径，未知值不显示为零；保存后刷新并按权限换会话核对结果。危险操作等待真实异步结果，失败保留错误和可恢复状态。包的既有前端测试只覆盖其声明范围，目标客户浏览器、真实权限和业务运行按本项目继续验证。

**交出：** 可操作的本地应用、代码与依赖版本、真实用例证据、视觉复核结果和未完成项。

### 12 接入既有系统与工具

专项任务使用文末“专项任务与工具”的指定入口：排产采用 OctoPlanner，图纸识别采用老马 drawings，爆品识别采用 SKU Radar。选定后先完成真实样本验证，再将输入输出映射到 Arcubase、员工、Skill 与 Workbench。

按第 7 步调用契约实施企业系统接入。对每个接口或网页操作，先核对实际环境、网络、身份、凭据、工具所在设备及必要权限，再验证参数、返回值和业务口径。只读用例维持只读权限；写入动作使用已批准的对象和范围。

优先沿已确认的 API 或工具入口实现；需要网页操作时保存可复查的定位与流程依据，页面结构变化导致定位不明就停止该动作并报告。凭据由受控环境提供，管理员密钥不得写入前端或业务文档。

先完成一条可回读的操作，再扩到批量。超时、断连或返回不明时查询实际状态；未核清结果前不重复写入。接入依赖、失败点、实测结果和限制分别挂回对应用例与资源记录。

**交出：** 可达工具入口、运行环境与权限记录、字段映射、实际调用或操作证据、结果回读和失败处理。

### 13 联调与技术完成复核

先选择一条编号用例，从真实身份进入，读取目标数据，触发业务操作，经过员工、Skill 或人工处理，保存结果并刷新回读。让另一位执行者按同一用例复做，核对材料是否足够、链路是否连贯。

随后按项目适用面扩展测试：

| 测试面 | 应验证什么 |
|---|---|
| 业务规则 | 主流程、边界、异常和判断分支符合已确认规则 |
| 数据 | 正常、空、缺失、错误、来源变化和历史口径 |
| 权限 | 获准读写、拒权、角色变化与撤销，含可直接访问的后端入口 |
| 重复与并发 | 重复提交、重试、并发以及外部结果未知时的处理 |
| 批量 | 部分成功与失败的区分、回读和后续补偿 |
| 人工决定 | 同意、拒绝、未回复及决定人与对象的对应 |
| 员工与任务 | 实际触发、职责边界、工具失败、超时、中止与接手 |
| 环境与展示 | 登录过期、错误团队、断连、跨日，以及约定页面和屏宽 |

每条测试保存：用例与测试编号、代码/Schema/Skill 版本、环境与身份、对象或测试记录、操作、预期、实际、证据位置、缺陷、修复与复测结果。未测项标明原因和对交付的影响。

发布前进行总架构师的技术完成复核。FDE 提交设计一致性、真实数据、权限、失败处理和测试证据，由总架构师作出结论。实现缺陷修复后复测；架构问题回到架构负责人并更新相关设计。技术复核结果随发布材料保留。

### 14 发布与上线测试

Workbench 发布按现役 Skill 执行：先完成本地实际验证，提供本地 URL 和证据，取得发布批准；开发者明确免除交互式本地验收时，保留该授权，并完成代理侧验证。架构审核通过与上线发布批准分别记录。

发布前固定代码、依赖、Schema 和 Skill 版本，核对部署目标，准备需要的数据迁移、上一可用版本和实际可执行的恢复方式。新建远程项目之前先按现役 CLI 的 `list/show` 合同排查已有项目，确认目标与复用范围。恢复方案同时核对旧页面、代码与当前数据 Schema 是否兼容。只运行项目声明的相关检查与生产构建，检查 `dist/index.html`。

按官方 `coding projects list/show/create/publish/watch` 路径发布。首次创建远程项目的结果不明时，先查询已有项目。发布返回中的 `deployment.taskId` 用于跟踪任务，`deployment.id` 不作替代。`queued / processing` 时继续查询同一任务，默认每 5 秒一次、最多 10 分钟；执行时以指定 Skill 的有界跟踪合同为准。`failed` 时记录错误并停止本次发布推进；结果未知或超时时先核查实际状态。`active` 和可用 `workbenchUrl` 确认部署完成，业务完成还需下一步正式入口测试。

打开正式入口，用目标身份和约定测试数据重新走核心用例，核对团队、真实读取、获准写入、写后回读、权限拒绝及视觉。员工或定时任务还需在目标宿主验证触发、执行和结果位置。发现线上错误数据时先停住受影响动作，核清范围后修复并复测；需要恢复时按已核实的恢复路径执行。

**最终交出：** 正式入口、代码/依赖/Schema/员工/Skill 版本，部署 `projectId / taskId / status / workbenchUrl`，已核验环境，上线测试与缺陷复测结果，限制、接手人及恢复资料。技术交付随后接入上层 FDE 的真实业务试运行、培训和客户验收安排；重合的试运行测试共用证据。

### 15 变更与阻塞怎样返回

| 发现的问题 | 执行人员下一步 |
|---|---|
| 实现偏离已批准设计 | 定位缺陷，按设计修复，复测受影响用例 |
| 设计缺漏、关键能力不可用、数据或权限结构需改变 | 停住受影响实现，整理事实与影响交架构负责人，修订设计并取得相应审核决定 |
| 需求变化或客户延迟配合 | PM 整理事实与影响，提交上层商务负责人决策，按决定返回指定节点 |
| 工具版本或参数与材料不同 | 查项目文件、当前 Skill 和命令帮助，记录差异；涉及路线改变交架构负责人 |
| 写入或发布结果未知 | 先查询和回读实际状态，确认后再决定重试、补偿或人工接手 |
| 测试依赖缺失或未授权 | 记录未测项及影响，交明确负责人补齐；完成结论保留该限制 |

变更记录至少保留：触发事实、影响用例、受影响文件和资源、决定人、处理决定、实施版本与复测证据。更新文件后检查跨文件对应关系，继续使用同一套架构入口。

### 16 提交反馈并跟踪处理

使用统一仓库的 [反馈入口](https://github.com/quekou-fde-development/fde-development/issues/new?template=feedback.yml) 提交问题，先在[已有反馈](https://github.com/quekou-fde-development/fde-development/issues)中检索同类记录。入口说明与收集规则在仓库 `feedback/`；本轮先由人收集和处理，数字员工自动协同挂起。

选择反馈分类，填写受影响路径与版本、问题描述与步骤、期望结果；在描述中补充环境、实际结果与影响，证据栏附可公开的截图或日志。项目问题带项目关联；含客户资料的细节留在受控项目仓库，公共反馈只放脱敏描述和可授权访问的证据位置。

维护者在同一 Issue 中指定 Assignee，并使用“待处理 → 处理中 → 关闭”记录进展；补料、处理决定、修订提交与验证结果均留在原 Issue。涉及架构、权限或已批准范围时，按 §15 返回相应审核。修复后由报告者或指定复核人验证，再记录结果并关闭；未解决的限制与下一步继续留在原 Issue。手册或工具更新后，标明影响版本与项目是否需要重新验证。

**产出：** 可回查的 Issue 链接、责任人、处理提交和复核结果。工具候选的反馈应保留其当前状态，单项测试通过不能改写为生产验收完成。

### 排产：OctoPlanner

OctoPlanner 是 Bun-first TypeScript 命令行工具。先读取官方 README、`package.json` 与命令帮助，记录采用的提交或版本。仓库给出的准备入口为 `npm install`，工作区初始化为 `npm run octoplanner -- workspace init`；按所选版本核对 Bun、Node 和依赖要求。

通过适配层把 ERP、MES 或 Excel 数据转换为 requirements、items、routings、resources JSON，检查稳定 ID 与引用关系，再加载规则并创建计划。情景调整沿 `plan load → plan revise --from-plan → plan diff` 的真实命令合同实施；Excel 回写用 `externalRef` 对齐原始行和基线，核对 diff 后按授权写入。

业务建模先确定变量、硬约束、优化目标和可行性判据。用人工可核对的小样本，再用真实样本检查资源冲突、工序顺序、停机、断料和不可行情形。每次读取命令返回的 `ok / data / warnings / notModeled`，解释未排程原因与未建模范围，并保存计划、差异和异常报告。排程结果经业务人员审核后，按批准规则写回系统或触发后续任务。

### 图纸：老马 drawings

站点页面标题为“老码识图”。公开前端列出 DWG、DXF、PDF、PNG、JPG/JPEG 输入，提供图纸库、解析、分类、参数检索和修订版本功能。使用前确认团队会话与权限，以目标账号核对支持格式和上传限制。

围绕实际业务要用到的参数设计识别任务，保留文件、图号、修订版和提取结果的对应关系。关键尺寸、单位、公差、材料等仅在项目需要且工具实际支持时接入；模糊、缺项、冲突或低可靠结果交人工复核。识别参数通过核对后，再验证报价、工艺或采购等后续业务动作的正确性。

### 选品：SKU Radar

SKU Radar 用于收集站点与商品变化信号，辅助爆品判断和选品。公开前端可见新商品、价格变化、促销页及图片/标题变化等监测项，以及站点、商品、报告和 URL 快照/差异入口。目标项目中先核对实际账号权限与支持范围。

Web 入口使用上表网址；公开前端给出的 CLI 入口为 `npm install -g skuradar-cli`，认证命令为 `skuradar-cli auth login` 与 `skuradar-cli auth whoami`。安装或运行前核对包来源、版本和当前命令帮助；本版未安装、登录或执行站点任务。

把业务目标转为筛选条件，记录目标站点/商品、时间窗和信号定义。用已知变化样本核对覆盖、误报/漏报、时间与来源，再由业务人员判断是否进入采购、试销或后续分析。页面操作、查询、导出和自动化接口分别核验，只把已验证的操作写进 Skill。

### 网站与系统接入

本版核验范围：OctoPlanner 已读取公开 README；老马 drawings 与 SKU Radar 已核对公开页面入口及前端能力线索。三个工具均未在本次手册编写中完成目标客户环境实测。

网站通过以上链接使用。登录权限、支持格式、导出方式及 API 可用性在目标项目中验证；入口 URL 本身不证明存在可调用的 API。已确认 API 时按其实际合同接入；采用网页或人工导出时，明确操作人、文件格式、保存位置和导入映射。涉及客户图纸或商品资料的上传，沿项目已有授权范围执行。

ERP 接入按实际 ERP 接口实施，分别核对网络、身份、数据口径和动作权限；直接写生产数据库按专项审核执行。每项专项接入均留下输入、调用或操作、产出、回读与失败处理证据。
