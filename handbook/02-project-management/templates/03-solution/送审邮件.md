# 整套方案送审邮件

[返回项目管理手册](../../project-management-handbook.md#stage-46) · [全部模板](../README.md)

先形成解决方案，再用Meta Spec生成技术架构，补齐独立计划与技术可行性评估、核对范围报价，由项目经理向总架构师夏洛克以一封邮件一次送审。所有客户类别采用同一格式。各文件保留现有结构、保存位置与明确版本，邮件提供完整阅读入口。手册和工具反馈使用[GitHub反馈入口](../../../../feedback/README.md)。

## 整套方案送审邮件

```text
主题：【项目编号】【整套方案审核】【版本】项目简称

项目与场景、客户类别（A/B/C）：
项目记录链接：
本次整套材料版本、范围与当前状态：

一、客户分析与解决方案
客户分析A：业务流、整体架构图及graph的知识库入口和版本；附开发仓库的同版引用。
baseline与调研依据：来源、测法及记录入口。
解决方案：明确版本与知识库阅读入口。
问题与价值：客户有什么问题，为什么值得解决，baseline、target及产品价值是什么。
产品设计：怎样实现改善；AI作用环节、工程替代比较、贡献依据及待验证项。
信息流：最初输入、拆解、逐步处理、中间产出、去向与最终反馈的阅读入口。
体验流：使用情境、入口、首屏、逐步操作、信息下沉、反馈与完成结果的阅读入口。
范围、分期与报价：明确版本、文件链接及依据。
客户核对与配合：已确认事实和测法、需要的投入及待落实条件。

二、技术架构与实施计划
技术送审commit：
技术架构B：九份spec阅读入口；与A及解决方案版本的对应关系。
产品到技术：对象与角色、信息流各节点、体验步骤分别由哪些概念、用例、数据、权限、页面和接口支撑。
技术可行性：项目架构师的判断与依据；数据、系统、人力、时间窗及未验证条件。
AI验证：关键能力与贡献的实际验证结果、工程对照、比较条件及限制。
独立开发计划：同一commit下的文件链接；时间、人员、工具、预计用量费用、依赖与验证安排。
整套一致性：方案、技术设计、范围报价与计划的差异及处理结果。

三、本次审核请求
请对以上整套材料的商业可行性、技术可行性与整体一致性给出通过／退回／暂缓结论，并明确范围和条件。
需要裁定的具体事项、未决事项及影响：
本次变更（修订送审时填写）：

项目架构师：
项目经理：
```

知识库「FDE全链」对应项目保存客户分析A、解决方案、范围报价及审核原文；技术材料提供同一固定commit的A引用、B与独立计划。项目记录关联所有入口、整套版本、实际结论、范围和条件。

邮件发出后记为待审。退回时同步受影响材料，核对整套一致性后重新送审；商业或技术部分未通过时，不能记为整体通过。取得整体审核通过结论，并落实启动与开工条件后进入开发。邮件发送、模型建议及机械检查结果均不能替代总架构师本人审核。
