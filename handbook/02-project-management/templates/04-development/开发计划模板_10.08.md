# 项目开发计划

项目经理组织架构师与 FDE 填写本模板，先完成 Arcubase 登记和母项目仓库建立，再保存到该仓库下 `<场景编号>/plan/开发计划.md`。先由 Meta Workflow 形成 A（业务流程、整体架构图及 graph），再由 Meta Spec 基于 A 形成 B（九份 spec），最后依据同版 A+B 编制本计划。正式送审提供两个大部分：**开发架构（A+B）和独立开发计划**。

送审时只需 `workflow/`、`design/` 和 `plan/`。本计划提前安排获批后的顺序：先建立 `releases/` 并开发，形成可测试版本后再建立 `tests/`，开展测试、修复与复测；技术复核与发布批准完成后上线并交接。实现目录按实际开发方式确定，不统一要求建立 `src/`。

本计划须能回答：具体做什么、谁做、何时开始和完成、用什么方式与工具做、预计消耗多少 token、依赖什么、怎样确认完成。各表通过任务编号对应；小项目可合并表格，保留所需信息即可。跨场景任务逐项标明涉及的场景。

Arcubase 管理母项目、场景以及完整的客户背景、业务内容、调研、沟通解释、实际推进和审核验收依据。GitHub 项目仓库用作内部开发协作台，只保存开发架构、计划、实现、技术变更和测试发布记录。计划中的业务依据与管理事项引用 Arcubase 链接，正文填写执行开发所需的信息。

日期使用 `YYYY-MM-DD`，工时注明人时、AI 执行时长或工作日；外部等待单列。未知项写影响、确认人和确认时间，不填 0 表示未知。审核采用邮件异步方式，开工须满足对应版本获批及资源到位等实际前提。

## 6. 预计 token 消耗与费用

### 6.1 估算范围与依据

开发预算覆盖审核通过后的开发、联调、测试和预计返工。形成 A、B 和计划已发生的 token 单列。上线后系统运行消耗另列统计周期和业务量，分别汇总。

按“任务 × 模型”估算，优先采用类似任务历史记录或小样试跑，保存调用次数、输入输出用量及任务结果。无可读取的 usage 时，注明可观测范围与估算方法，保留待校准项。

| 任务编号／模型 | 估算来源、样本量及证据 | 预计调用次数与迭代安排 | 单次输入／输出假设 | 测试、重试与上下文增长假设 | 校准负责人和时间 |
|---|---|---|---|---|---|
| T-01／《模型及版本》 | 《历史记录／试跑／初步估计》 | 《次数及其依据》 | 《平均 token 或有依据的区间》 | 《计入哪些调用，避免重复》 | 《负责人、试跑或回读时间》 |

### 6.2 用量预算

同一模型的输入 token = 各任务预计调用次数 × 单次平均输入 token，再求和；输出同理。历史上下文、工具返回和重复发送的材料按实际进入模型的次数计入输入。多个 agent 或模型分别估算后求和，并行不减少累计用量。

| 任务编号／模型 | 输入 token（含缓存） | 其中缓存输入 token | 输出 token | 总 token：低／基准／高 | 区间依据与估算状态 |
|---|---|---|---|---|---|
| T-01／《模型》 | 《基准值》 | 《输入中的子集》 | 《基准值》 | 《三档数值，单位 token》 | 《各档调用次数、上下文和返工假设；待校准／已校准》 |
| 开发阶段合计 | 《求和》 | 《求和》 | 《求和》 | 《逐档求和》 | 《主要不确定性》 |

**总 token = 输入 token + 输出 token。缓存输入属于输入的一部分，不再加一次。** 根据实际供应商 usage 的定义处理推理 token、缓存读写等分类；已包含在输出或输入的细项不重复加总。尚无缓存命中依据时，费用估算可先按未缓存输入计算，并写明假设。

| 预算类别 | 已发生或预计 token | 统计范围与期间 | 依据及说明 |
|---|---|---|---|
| 送审前形成 A+B 和计划 | 《已发生；未知写待核对》 | 《起止时间》 | 《可取得的 usage 或估算依据》 |
| 本次开发 | 《上述开发合计，低／基准／高》 | 《从获批开工到本次交付》 | 《包含的测试及返工范围》 |
| 上线后运行 | 《按调用量另估；不适用注明原因》 | 《如每月业务量、每次调用量》 | 《与开发用量分列》 |

### 6.3 费用与预算管理

| 供应商／模型或工具 | 实际计费方式 | 单价、币种与计量单位 | 价格来源及查询日期 | 预计费用：低／基准／高 |
|---|---|---|---|---|
| 《待填写》 | 《API／订阅／用量附加费／其他》 | 《按实际合同或价格页填写》 | 《链接与 YYYY-MM-DD》 | 《与 token 预算对应；无法换算注明原因》 |

适用“未缓存输入、缓存输入、输出”三类计费的文本 API，可按下式估算：

```text
单模型费用 = [未缓存输入 token × 未缓存输入单价
             + 缓存读取 token × 缓存读取单价
             + 输出 token × 输出单价] ÷ 单价计量单位
开发费用合计 = 各模型费用之和 + 按实际单位计算的工具等附加费
```

单价按每百万 token 给出时，分母为 1,000,000；其他单位按供应商定义换算。各 token 计费类别采用供应商定义的互斥口径；缓存写入若独立计价，应从总输入中划出该部分，按对应费率单列，避免再次按未缓存输入全额计费。工具调用或存储费按各自实际单位单列。订阅产品填写订阅成本、项目分摊依据与额度限制；API 参考单价不能直接充当订阅账单。

token 预算上限：《按任务或模型填写》；费用预算上限：《金额、币种及批准人》；缓冲依据：《针对哪些风险，是否已计入高值预算》。

预算复核触发条件：《预计超限、范围变更、模型切换或试跑与假设偏差等具体条件》；处理人及动作：《何时重新估算、在 Arcubase 登记及提交变更审核》。实际用量取得后校准剩余开发预算，避免重复计入已发生用量。

## 11. 送审前核对

- A 含业务流程、整体架构图及 graph；B 的九份 spec 齐备；二者有统一开发架构阅读入口。
- 母项目仓库按“母项目编码＋客户名称＋期号”命名并已登记；所有开发文件放入对应场景文件夹。
- 本计划每个任务有负责人、明确开发方式、时间安排、依赖与可核对的交付标准。
- token 按任务与模型估算，有区间、来源、校准安排及预算上限；费用符合实际计费方式。
- 项目、场景、固定仓库、A/B 和计划版本一致；两个送审链接均指向同一 commit 且可访问。
- 由 Arcubase 登记的项目经理发送异步邮件，说明开发架构与计划两个部分、需审核事项及未决条件。
