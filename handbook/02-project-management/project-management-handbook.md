## 1. 接手项目

### 1.1 确认项目负责人

项目经理对项目整体负责，组织客户沟通、人员与资源协调、进度跟进和各阶段交接。接手时明确本项目的项目经理、架构师、FDE及具体分工，使用已有项目记录中的人员安排。

项目经理代表客户需求，深入实际业务，核对客户要解决的问题及方案价值，组织基线取数并与客户确认计算口径；同时统筹技术、人力、资金、外部支持和客户配合。架构师定义问题、产品、解决方案及报价依据，并提出技术可行性；FDE协作设计、验证、编制开发计划及实施。项目经理组织方案审核和开发审核，总架构师夏洛克分别审核。

当前接入通常已有前期商务、销售线索及需求材料，项目经理先完成接手；独立带队承担商务属于后续能力要求。人员可兼任，按本项目记录明确实际承担者。B/C类两人、A类约3—5人的作战单元为组织建设目标，具体安排依据项目条件。

合同、报价、回款及原流程规定的商务决定，项目经理按已有商务流程提交并落实结果。

### 1.2 接手时先对齐已有信息

[打开项目交接资料包模板](templates/01-handover/项目交接资料包.md)。

项目经理接手时，与原负责人核对项目编号、客户及期数、ABC分类、项目参与人员及分工、当前节点、已有需求和验收标准、合同承诺、最近进展、未结束事项及资料入口。先取得已有商务沟通和调研材料，再安排下一步。

客户侧分别明确：**1号位、业务负责人、资源协调人、授权验收人**。一个人兼任时写明其承担的角色；客户联系人是否有权确认范围或验收，按实际授权核对。

项目经理指定替补。离岗或换人前，交接群和资料权限、未结束事项、最近承诺与风险；接手人核对能访问材料，在客户群说明接续安排。

<a id="groups"></a>

### 1.3 内部群和客户群

[群公告模板](templates/05-communication/群公告.md) · [项目事项表](templates/05-communication/项目事项表.md)。

- **内部项目指挥群**：按已有建群要求，包含袁黎明、夏洛克、项目经理和在场FDE，用于资料交互、策略讨论及内部会议。项目经理在群中同步工作、问题和支持请求，需要谁处理时点名对应人员；项目架构工作沿已确定的人员分工衔接。
- **客户项目群**：项目经理任群主，按“客户简称｜项目编号｜阶段”命名。入群时介绍双方人员；公告保留项目经理及替补、升级联系人、服务时段、当前阶段、下一节点和本项目事项表链接。
- 客户群发布进展、安排和配合事项；内部成本、报价底线及内部评价保留在内部资料中。替补具备接续所需权限。

## 2. 产出格式、文件位置与已有工具

<a id="locations"></a>

### 2.1 文件与项目记录放在哪里

| 位置 | 保存内容 | 项目经理的动作 |
|---|---|---|
| 知识库「FDE全链」对应项目 | 背景与调研原件、需求、方案文件、会议文件、启动会签字文件及最终签字验收文件 | 按本项目保存文件和原件，核对项目归属、有效版本和访问权限 |
| Arcubase／Work OS项目管理中的母项目与场景记录 | 当前节点、负责人、进展、卡点、审核及验收状态、对应文件链接 | 沿现有项目记录更新，文件链接指向知识库对应项目及技术版本 |
| 对应私有GitHub仓库 | 开发架构A+B、独立开发计划、实现、测试和发布记录 | 按开发手册核对母项目及场景对应关系，保留固定commit和阅读入口 |
| 客户可见的项目事项表 | 执行事项、关键节点、问题及客户配合 | 维护跟进人、约定日期、下次反馈时间、状态和结果依据 |

文件类产物归知识库「FDE全链」对应项目；开发协作使用的A+B、计划及实现版本继续沿开发手册在GitHub维护，通过项目记录关联。知识库的具体上传、读取和关联操作，以及历史数据清洗、吴老狗能力调整，由Work OS统筹接续，实际入口尚待核实。飞书录音保留原链接还是转存尚待讨论，当前沿已有原件位置引用，不能据此声称已完成归档。

新项目先在现有系统登记母项目与场景，再按开发手册§0建立对应私有仓库；已有项目沿用已登记的项目编号、仓库及场景目录。

客户事项表沿用原群规范的八项：**事项名称、事项编号（自动编号）、类别、缺口跟进人、约定完成日期、下次反馈时间、状态、最新进展与结果依据**。每个项目使用独立文件；客户只读，项目经理及替补核对访问权限。未结束事项保留下次反馈时间，客户需执行的动作也指定缺口跟进人。

状态沿用待评估、待处理、进行中、待客户、待验收、已完成、已关闭。待客户时继续跟进。内部系统与客户事项表由项目经理核对；保存、同步和提醒以实际回读结果为准。

**需求状态**：1次需求为需求假设；2次需求为已核实问题及调研前置信息；3次需求为双方确认的范围、验收标准和配合事项。调研期间继续核实，启动会形成客户签字的《验收标准及验收清单》。启动会后该确认版本固定，后续交付和验收据此执行。

## 3. 每天怎样协作和维护客户群

### 3.1 每日时间与动作

| 时间或触发         | 内部工作                                           | 客户群动作                             |
| ------------- | ---------------------------------------------- | --------------------------------- |
| 服务时段开始时       | 项目经理查看今日承诺、待客户事项和下一节点，与架构师、FDE核对当天安排           | 回应到时应反馈的事项，确认已约定的访谈、会议或客户配合       |
| 到约定反馈时间或出现阻塞时 | 负责人员说明实际情况、影响和需要的支持，项目经理协调处理                   | 项目经理或跟进人说明进展、下一步和下次反馈时间           |
| 当日内部日报；固定钟点待核 | 执行人员提供当日事实，项目经理整理项目日报，写完成、未完成、明日安排、风险及应对，格式见I1 | 以核实后的项目事实准备每日简报                   |
| 服务日17:30      | 提醒项目经理检查到期、待客户、待验收事项；服务时间不同则改为下班前半小时           | 由项目经理核对需要同步的内容                    |
| 服务日下班前        | 更新项目记录及事项表                                     | 项目经理或替补从同一份事项表整理一条简报，按当前阶段选用C1—[C7](templates/05-communication/C7.md) |

17:30是原群规范中的**检查提醒时间**。内部日报固定钟点在已取得的材料中未见明确规定，沿用公司或项目已确认安排。

项目经理每天整理项目日报；执行人员提供当日完成结果、未完成原因和问题。内部群保留摘要与已有项目记录链接。现有公司汇报安排为：个人工作报尹新月，项目进度报吴老狗；沿用同一批已核对事实。保存状态不明时保留原文和报错，核对记录后补齐。

已建立客户群的活跃项目，每个服务日维护客户群。等待客户配合时，写清等待谁、什么事项、已做的跟进和下次反馈时间；维保、暂停及结束后的沟通按已有服务约定。

### 3.2 不同阶段汇报的重点

客户群反馈服务于推进项目：让客户知道今天做了什么，以及下一步需要客户协调什么。下一步工作与所需支持写在一起，明确对象、动作、时间及影响；内部可解决的阻塞由PM协调内部支持。等待配合时持续跟进并给出下次反馈时间。

| 当前阶段               | 客户每天需要知道什么                | 格式 |
| ------------------ | ------------------------- | -- |
| ①背景收集，形成1次需求       | 已了解的信息、需求假设、待核实问题         | [C1](templates/05-communication/C1.md) |
| ②建联，形成2次需求         | 已核实的业务问题、真实案例、还缺什么信息      | [C2](templates/05-communication/C2.md) |
| ③沟通，形成3次需求         | 本期范围、验收标准和配合事项的确认进展       | [C3](templates/05-communication/C3.md) |
| ④深调、架构审核、⑤计划及⑥启动准备 | 调研结果、方案与计划状态、下一节点、客户需准备什么 | [C4](templates/05-communication/C4.md) |
| 启动后实施、开发、测试与上线           | 对照确认计划的交付进展、偏差、下一里程碑      | [C5](templates/05-communication/C5.md) |
| 试运行、验收          | 实际使用或验证结果、问题处理、待客户确认的内容   | [C6](templates/05-communication/C6.md) |
| 交接、⑦维保             | 已交接或处理事项、遗留安排、后续服务        | [C7](templates/05-communication/C7.md) |

启动前按C1—C4说明需求核实及准备情况；启动后按C5—C7对照已签文件汇报实施与验收结果。消息中的结果、日期和确认状态以当前记录为依据。

### 3.3 客户回应时限

沿用《缺口FDE项目群管理规范》V1.1，项目经理核对合同及专项服务约定后写入群公告：

- 默认服务时段：公司工作日 **09:00—12:00、13:00—18:00**。
- 普通事项：累计 **2个服务小时内**有效回应，说明跟进人、下一步、下次反馈时间。
- 阻塞当天实施、测试或验收：**30个服务分钟内**由项目经理或替补接手，同时电话联系；仍无人接手时找公告中的升级联系人。
- 非服务时段普通事项顺延至下一服务时段；上线保障和生产事故按专项约定。到了已承诺的反馈时间，尚未解决也更新进展。

## 4. 按已有FDE流程推进

主线为：**①背景收集 → ②建联 → ABC分类 → ③初次见面或远程沟通 → ④进场调研、方案形成 → 方案审核 → 技术架构与计划 → 开发审核 → ⑤实施计划 → ⑥启动会 → 开发 → 试运行 → 验收 → 交接回款 → ⑦维保或项目完成**。培训暂缓。架构阶段先做方案审核（商业可行性），再做开发审核（技术可行性）；材料可以并行准备，正式开发审核依据已通过的方案版本，开发须取得开发审核通过记录；C类一次进场与启动签字的具体时序见§4.8待补项。

项目经理承接①②和ABC分类形成的前期资料，组织③及后续工作。每到下一节点，交清已有材料、当前结论、未结束事项和接下来的安排，记录在现有项目资料中。

<a id="stage-41"></a>

### 4.1 商机、①背景信息收集：形成1次需求

**模板与工具**：现行1次需求模板留空；群消息使用[C1](templates/05-communication/C1.md)。

**目标与产出**：形成1次需求：背景材料、需求假设和待核实问题。

**策略**：从已有AI规划、客户需求及公开资料形成初步判断，将待核实内容交给后续建联。

**行动**

前期背景收集按原流程研究客户已有AI规划、需求及公开资料，形成初步业务判断；需求记录包含初步验收范围和标准，尚未核实的内容注明待核实，产出**1次需求：需求假设**。

项目经理接手时读取已有背景材料及需求假设，核对信息来源和待核实问题，供后续建联与调研使用。已建客户群时，当前对客负责人可按C1反馈；未建群时保留已有内部记录。

<a id="stage-42"></a>

### 4.2 ②建联：形成2次需求

**模板与工具**：现行2次需求模板留空；群消息使用[C2](templates/05-communication/C2.md)。

**目标与产出**：形成2次需求：已核实业务问题及可用于安排调研的前置信息。

**策略**：用具体案例核对初步需求，分别保留已核实内容和缺失信息。

**行动**

建联阶段核实真实业务问题、具体案例及当前表现，收集联系人、公司地址和客户角色，预约见面时间、人员及材料，更新验收范围和标准，产出**2次需求：已核实问题与调研前置信息**。

项目经理接手时核对这些结果，区分已核实与待核实内容，并与原对接人确认后续沟通安排。前置信息沿已有项目材料读取；原流程提到的独立模板原件尚未取得。已有客户群的更新按C2。

<a id="stage-43"></a>

### 4.3 ABC分类与人员安排

**模板与工具**：沿已有项目记录登记分类与人员；[项目交接资料包](templates/01-handover/项目交接资料包.md)。

**目标与产出**：取得已确认的ABC分类、投入及人员安排，进入相应沟通分支。

**策略**：沿已有商务判断匹配投入，项目经理核对依据和可用资源后落实。

**行动**

项目经理接收原商务流程作出的ABC分类及投入安排，核对其需求、企业规模与支付能力、1号位对接和投入产出依据，再落实后续工作：

- **A类**：客户经营最大化开发。
- **B类**：正常交付，关注次年续费。
- **C类**：完成交付、取得验收单，控制出差成本；沿原流程的一次进场安排准备调研、架构和客户对接；启动时序见§4.8待补项。

按已有安排确认项目人员。A/B进入初次见面，C进入远程沟通。问题不成立、必要条件无法补齐、客户不愿承担必要投入或放弃时，项目经理整理事实，按§5提交处理。

### 4.5 ④进场调研与架构设计

**模板与工具**：[现场调研表单目录](templates/02-research/README.md) · [基线记录](templates/02-research/基线与试点对比记录表.md) · [调研输入空表](templates/02-research/通用调研输入文档_10.06.md) · [范围分期与报价](templates/03-solution/范围分期与报价.md) · [九份spec参照](templates/03-solution/architecture-reference/README.md) · [C4](templates/05-communication/C4.md)。

**目标与产出**：取得现场证据与场景基线，形成可解释客户价值的解决方案和报价依据，再形成可实施的技术架构、可行性结论及开发计划。

**策略**：按当前现场手册取证，沿架构设计手册分两段形成方案与实施依据。

**行动**

**已有材料**：§2.2现场调研手册、客户版调研计划及《通用调研输入文档》。现场访谈、流程走查和样本验证采用袁黎明当前现场手册；方案方法沿架构设计手册。

1. 项目经理落实访谈对象、现场日程、业务样本、系统入口及权限，深入客户实际业务，核对问题、现状及客户配合。取得场景基线；客户没有现成统计时组织取样与计算，确认量名、单位、算法、样本和来源，并与客户核对计算口径。
2. 架构师从业务链的经营意义定义问题，说明产品通过什么能力改善哪个场景量，形成回答句、基线与目标、产品说明、A组材料及范围报价依据。PM代表客户核对价值与配合条件，组织方案审核（闸1）。
3. 项目架构师提出技术可行性，FDE协作核查数据、系统、人力及客户时间窗，形成B组九份spec和独立开发计划，说明数据流与信息流。材料可并行起草并注明待审状态；正式开发审核（闸2）须对应已通过的方案版本及条件。
4. 项目经理整理业务依据、现场原件及客户确认记录，将对应资料交给下一步使用者。A/B按已约定日程完成；C类沿一次进场安排准备人员与材料，启动时序保留§4.8待补项。

项目经理核对事实、方案及计划的阅读入口和当前审核状态。客户群用C4。

### 4.6 总架构师审核

**模板与工具**：[送审邮件](templates/03-solution/送审邮件.md) · [开发计划](templates/04-development/开发计划模板_10.08.md) · [两闸审核清单](../03-architecture/architecture-handbook.md#10-审核清单) · [C4](templates/05-communication/C4.md)。

**目标与产出**：取得明确到场景、版本、范围和条件的两道审核结论。

**策略**：每次提交固定版本和阅读入口，按对应闸口核对材料，保留意见及落实结果。

**行动**

两道审核按[架构设计手册](../03-architecture/architecture-handbook.md)§10执行。架构师提出解决方案和技术可行性判断，组织对应设计；FDE协作提供规格、验证及开发计划。项目经理核对材料、客户确认和资源条件，组织正式送审。

1. **方案审核／闸1（商业可行性）**：提交问题定义、产品定义、场景基线与目标、A组材料、范围分期及价值报价依据。核对客户认可和未决项，取得总架构师对明确方案版本的结论。
2. **开发审核／闸2（技术可行性）**：提交项目架构师的可行性判断、开发架构A+B和独立开发计划，重点核对数据结构、数据流、信息流及实现条件。关联已通过的方案版本，核对并行准备及方案审核后的差异。技术材料push到已登记私有仓库，保留固定commit和两个阅读入口。
3. **项目经理发邮件给总架构师夏洛克，异步送审**：写明当前审核环节、场景范围、商务投入边界、请求审核事项、未决问题和固定版本链接。两次送审分别使用[对应邮件格式](templates/03-solution/送审邮件.md)，开发计划内容沿开发手册§5。
4. 将审核原文、版本、结论、获批范围及附带条件关联到项目记录；文件保存在知识库对应项目，技术版本留在GitHub。退回时按具体意见补业务资料、修方案或调整计划，再送审。

闸2通过的场景进入⑤；待审场景保留实际状态。本节方案修订用于启动会签字前；启动后以已签文件为固定依据，异常按§5处理。客户群用C4。

### 4.9 开发、测试、上线与技术交接

**模板与工具**：[开发计划](templates/04-development/开发计划模板_10.08.md) · [FDE开发手册](../04-development/development-handbook.md) · [C5群消息](templates/05-communication/C5.md)。

**目标与产出**：按获批安排形成可核验的开发、测试及正式运行结果，准备客户试运行。

**策略**：沿开发手册的开发、测试、复核、批准、发布顺序执行；项目经理据实际证据跟进。

**行动**

FDE按开发手册§6—§14执行，项目经理跟进资源、客户配合和进度，架构师处理设计问题。

1. **领取批准版本**：项目经理核对对应场景的审核结论、获批范围和附带条件，落实人员、数据、权限及环境；FDE读取获批架构与计划。
2. **开发**：FDE按计划完成任务，保存开发版本及实际结果。项目经理核对进展和里程碑，协调卡点。
3. **测试与修复**：形成可测试版本后，FDE按用例测试，记录结果；失败后修复并复测。对照已签启动文件检查范围和标准，技术问题按§5处理。
4. **技术完成复核与发布批准**：FDE提交材料，由总架构师进行技术完成复核；按开发手册取得对应发布批准，项目经理协调上线安排。
5. **发布与正式环境验证**：FDE发布后核对正式入口和实际运行结果，保存部署及验证记录；验证中的问题按开发手册处理。
6. **技术交接**：FDE交出正式入口、版本、测试结果、已知限制及恢复资料，项目经理保存链接和当前状态，组织客户真实业务试运行。

客户群用C5，按实际结果说明开发、待测试、测试通过或已上线。后续客户验收按§4.12取得客户授权验收人的结论。

## 5. 异常、客户配合与商务决定

### 5.1 整理事实与影响

[历史延期回复函栏目](examples/延期回复函.md) · [项目事项表](templates/05-communication/项目事项表.md)。

**启动会后已签确认版本固定。** 项目经理对照该版本整理实际问题及影响，跟进处理结果。

| 情况 | 处理动作 |
|---|---|
| 实现缺陷、测试失败 | FDE记录并修复复测；架构师处理技术判断；项目经理跟进进度与客户影响 |
| 架构缺漏、能力不可用、数据或权限条件变化 | 架构师和FDE核对是否仍能满足已签标准，记录原因、影响及技术处理意见，项目经理组织相应技术审核和商务处理；原签字版本保留 |
| 写入或发布结果不明 | FDE先查询回读实际状态，再决定重试、补偿或人工接手；项目经理跟进交付影响 |
| 测试条件缺失或未授权 | FDE保留未测项、原因及影响，项目经理协调补齐条件；完成状态以实际结果为准 |
| 新增诉求、客户迟交资料或延迟配合 | 项目经理记录与原约定的关系，架构师和FDE评估影响，提交原流程规定的商务负责人处理；新增诉求不并入本期已签版本 |
| 验收不通过、交接回款争议、项目终止 | 项目经理汇总事实和处理选项，取得原流程要求的决定后组织执行 |

技术问题在项目仓库Issue中记录，修复后由报告者或指定复核人验证关闭。业务事实和决定回到项目记录，文件归知识库对应项目；保留原始问题及后续处理依据。

### 5.2 取得决定，接续执行

项目经理将事实、原约定、影响和需决定事项提交原流程规定的商务负责人，记录**决定内容、影响场景、继续条件**并组织执行。

启动会签字前，按决定补资料、修订待确认方案或计划，再取得对应审核及客户确认。启动会后，对照固定的签字版本处理实施问题和客户配合事项；未完成项按实际状态跟进，不能以修改原签字范围或标准替代交付。具体处理结果、反馈日期及客户确认保留在项目记录中。

### 5.3 终止

取得终止决定后，项目经理确认生效范围和时间，通知客户及项目团队，组织已完成、未完成、资料权限、费用和后续责任的处理；FDE交接实际产物与遗留技术事项。项目记录保留终止原因、决定及处理结果。
