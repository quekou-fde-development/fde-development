如何使用

先看 FDE 总流程图（内部执行版），了解项目整体阶段、角色、决策和交接，再按本手册展开技术开发环节。总流程图与本手册 HTML 同目录保存时，该链接可离线打开。

本手册面向项目经理、承担方案设计与开发的架构师、FDE 和开发 AI。项目经理先在 Arcubase 登记母项目与场景，再建立对应的内部开发仓库及场景目录。团队按以下顺序工作，由项目经理统一送审：

  1. 先登记，再建库和场景目录。 在 Arcubase 确认母项目编码、客户名称、期号及所属场景；在 quekou-fde-development 组织新建该母项目的 private 开发仓库，仓库名由“母项目编码＋客户名称＋期号”组成。仓库根目录承载母项目，每个场景建立独立文件夹，具体命名与结构见 §0。
  2. 使用 Meta Workflow 拆解业务，形成文件组 A。 A 包含业务流程、整体业务与系统架构图，以及表达节点、依赖、触发、交接和异常回流的 graph。
  3. 再使用 Meta Spec，以明确版本的 A 为输入，形成文件组 B。 B 是九份开发规格 Markdown；每份规格须对应 A 中的流程、角色、规则或架构关系。
  4. 基于 A+B 编制独立开发计划。 逐项写明开发任务、负责人、开发时间、开发方式与所用工具、预计 token 消耗、依赖、交付物和验收安排。
  5. 提交两个大部分：开发架构（A+B）和开发计划。 项目经理先将两部分 push 到前面已建好的母项目仓库及对应场景目录，再通过邮件向总架构师夏洛克异步送审，分别提供这两个部分的固定版本阅读链接。
  6. 审核通过后先开发，再测试。 FDE 领取获批的 A+B 和计划，在对应场景下先建立 releases/，保存开发版本及其产物；形成可测试版本后再建立 tests/，记录测试、缺陷和复测结果。测试通过并取得发布批准后上线，正式环境验证及交接继续关联同一开发版本。具体步骤见 §6、§13—14。

开发架构 = 文件组 A（业务流程、整体架构图及 graph）+ 文件组 B（九份 spec）。开发计划独立成文。 A、B 和开发计划属于同一次送审版本；审核人从两个入口即可读全本次材料。

手册第一部分说明上述材料怎样形成与送审，第二部分说明获批后的开发、测试、发布和反馈。开发是 FDE 全流程内部的一段 loop；商务、调研、客户培训、最终客户验收和维护按上层 FDE 流程衔接。

当前版本：10.09.2。 实际项目的架构批准、真实数据写入和发布授权，分别按项目记录执行。

共用规范与工具从 quekou-fde-development/fde-development 获取，主要目录为 handbook/（开发手册）、tools/（开发工具）和 feedback/（共用工具反馈）。每个母项目的开发交互使用 §0 新建并登记的独立仓库。手册 Markdown 与 HTML 阅读版来自同一份正文；离线使用时一同下载 HTML 与配套资源总 ZIP，按文末资源索引选择小包。

整条开发链基于 Octopus + Arcubase：Workbench 承载页面与可信会话，Octopus 提供组织及 Host 能力，Arcubase 保存共享持久业务数据。工具包的“候选”“方法参考”“文件快照”状态见资源索引，项目采用前核对版本及目标环境证据。

GitHub 项目仓库定位为内部开发协作台。 仓库只维护开发架构（A+B）、开发计划、实现代码及配置、测试与发布记录、技术变更和开发问题。客户背景、业务说明、调研原件、沟通解释、经营资料、项目推进、关键决定及验收依据保存在 Arcubase；开发文件按需引用对应链接。

两边以母项目编码、场景编号、固定仓库名和目录链接关联。GitHub 中的 A+B 只表达开发所需的流程结构、规则、职责、数据、接口和验收要求；项目事实、背景解释和决定原文从 Arcubase 读取。项目经理、场景负责人、当前阶段、卡点和支持事项以 Arcubase 为准。仓库 README 限于标识、关联链接、场景目录和开发文件入口。

产出格式与填写规则

开发架构由文件组 A 和文件组 B 共同组成。A 保存在 workflow/，按 §2—3 交付业务流程、整体业务与系统架构图及 graph；B 保存在 design/，由 Meta Spec 基于明确版本的 A 编写九份规格 Markdown，沿用现有九份文件名及写作参照。王磊八份原设计作为写作参照，独立数据结构为第 3 份。案例中的业务、登录、技术栈与接口须按本项目和 Octopus / Arcubase 边界重新设计。

  • 填写通用调研输入的已知事实、客户意向、约束及来源。未知项写“未确认＋向谁或取什么材料确认”；没有该场景时写“不适用＋理由”。已有原件能够回答的内容直接附材料位置。
  • 业务流程和规格设计中的关键问题分别集中澄清。Meta Spec 发现业务目标、规则、职责或流程仍有缺口时，返回业务流程环节补齐；九份规格引用明确的业务流程版本。能力未实测和上线前验证要求写为限制，保留负责人和下一步。
  • 需求、流程、用例、数据、角色、页面、调用和测试使用稳定编号；业务流程、九份 spec 和开发计划中的同一对象保持一致。
  • 设计、实际实现、测试结果与审核决定分别记录。总架构师审核由夏洛克进行，工具检查通过只说明其覆盖的检查项。

来源快照、草稿和澄清过程在 working/ 中保留；收束后的业务流程、整体架构图和 graph 进入 workflow/，构成 A；design/ 下九份 spec 构成 B。A+B 作为开发架构一起送审。开发计划按统一模板填写，独立保存在 plan/开发计划.md。实施后的 Schema、typed SDK、员工配置、Skill 包、代码及部署回执按相应工具原生格式保存；在项目内登记版本、实际 ID、证据位置与限制。

上述 workflow/、design/、plan/ 均放入 §0 建立的对应场景文件夹。确需跨场景复用的开发模块可放在仓库根目录的 shared/，并列明使用它的场景；各场景仍保留自己的开发入口。Arcubase 保存原始业务资料、关键澄清、决定与解释，GitHub 只引用这些记录。input/、working/ 中的调研原件、运行草稿和取源快照保留于获授权的本地工作区或 Arcubase，不提交到 GitHub。

第一部分 先登记建库，再形成 A、B 与开发计划并送审

0 先在 Arcubase 登记，再建立母项目仓库与场景文件夹

一、登记母项目及其场景。 项目经理在 Arcubase 确认母项目编码、客户名称、期号及所属场景。每个场景关联对应母项目，并有自己的场景编号。客户背景、业务内容、职责、阶段、调研、沟通和决定等完整项目资料在 Arcubase 维护。后续建库和建目录直接读取已确认的标识。

二、为该母项目新建内部开发仓库。 在 quekou-fde-development 组织建立一个 private 仓库，命名规则为：

<母项目编码>-<客户名称>-<期号>

母项目编码采用 Arcubase 的真实编码。客户名称和期号采用事先确认、已登记的仓库写法。例如，QK-2026-001-Aokai-P01 表示母项目编码 QK-2026-001、客户名称仓库写法 Aokai、期号 P01；此例仅说明格式，实际值须从对应记录取得。

GitHub 仓库名仅支持 ASCII 字母、数字和 . - _，长度不超过 100 个字符。中文客户名称使用项目经理确认的英文名或拼音写法，并在 Arcubase 记录与原客户名称的对应；期号同样登记固定写法。不要交给开发 AI 临时取简称或自行截断。字符要求见 GitHub 建库文档。

项目经理将完整仓库名与 URL 回填到 Arcubase 现有项目资料索引。仓库名经登记后固定使用。 客户显示名称、人员、阶段或开发版本变化沿用原仓库。已有仓库先核对登记映射；编号或命名异常由项目经理单独处理，禁止自行改名或删除重建。缺少建库权限时由组织管理员协助。

三、在母项目仓库下建立场景文件夹。 仓库根目录对应母项目，其下按 Arcubase 场景编号分别建文件夹。送审阶段，每个场景只准备 workflow/、design/ 和 plan/ 三类材料；README 作为关联和阅读导航。送审时的目录如下：

<母项目编码>-<客户名称>-<期号>/       # 仓库根目录＝该母项目
├── README.md                     # 标识、Arcubase 链接和场景目录索引
├── <场景编号一>/
│   ├── README.md                 # 场景关联和开发文件入口
│   ├── workflow/                # A：业务流程、整体架构图、graph
│   ├── design/                  # B：九份 spec
│   └── plan/开发计划.md           # 独立开发计划
└── <场景编号二>/
    ├── README.md                 # 场景关联和开发文件入口
    ├── workflow/
    ├── design/
    └── plan/开发计划.md

母项目 README 只写母项目编码、仓库名、Arcubase 记录链接，以及“场景编号 → Arcubase 场景链接 → 场景文件夹”的索引。场景 README 在送审时只写关联标识及 A、B、计划的阅读入口；开发后再补已有的实现、测试和发布入口。具体项目内容、客户业务解释与管理记录回到 Arcubase 查看。

审核通过后先进入开发，在场景下建立 releases/，保存开发版本及产物；形成可测试版本后再进入测试，建立 tests/，保存对应版本的测试、缺陷和复测记录。后续发布与技术交接资料继续归入相应开发版本。开发实现按所选工具和框架组织，不统一要求建立 src/；跨场景共用模块在开发中有实际需要时再组织。

完成登记、建库、场景目录和关联链接后，再进入 §1—5 形成开发架构与计划。提交审核和后续开发持续使用该仓库及对应场景目录。

1 整理检索与调研输入，启动业务流程设计

架构负责人先收集并核对前置检索结果、调研原件和已经确认的需求，建立同一项目的材料入口。填写现有通用调研输入文档的项目副本；资源总包的 inputs/ 中也提供同一空表。至少能找到：业务目标与交付范围、参与角色、关键场景、真实样本、当前规则与异常、既有系统和可用接口、验收范围与验收标准，以及客户必要的授权和配合事项。

把事实、已确认规则、待核实假设分开标注，并为每条重要结论附原件位置。遇到缺样本、规则冲突、关键接口未知，登记具体缺件与负责人；由 PM 协调补齐。影响范围或技术路线的缺件在架构送审时明示，不交给开发 AI 自行补成事实。

材料索引分别记录两种状态：原件是否取得并实际读取；相关能力处于文档说明、源码核对、样例验证还是目标环境实测。来源未取得正文、现场尚未验证等情况随送审包保留。

工具路线： Meta Workflow 负责文件组 A，采用 Meta Skill 与 Meta Orchestrator 的理论结构；Meta Spec 以 A 为设计输入，编写文件组 B 的九份 spec。工具拆分与现有源码入口见文末资源索引。

怎样启动： 把填过的输入副本、原件位置和本次工作目录交给业务流程设计环节。输入允许部分填写；先取源、梳理流程与业务架构，再集中澄清。将业务流程、整体架构图和 graph 作为文件组 A 保存到 workflow/，核对 §3 的交付清单并标明版本和来源，随后把整组 A 交给 Meta Spec。九份规格中的设计选择应能回到业务流程或有权人的明确决定。

填写重点： 调研范围和角色、真实作业路径、异常与决定权、单据和样本、现有系统、目标与交付范围、验收依据、Octopus / Arcubase / Workbench 已知环境及授权。既有 App 记录真实 ID 与 Schema；拟新建 App 写计划与依据。

产出： 通用输入项目副本、来源快照与缺件记录，进入本次运行的 input/、working/；正式业务流程材料进入 workflow/。沿用已有调研成果，只针对业务流程与架构缺口补证。

2 使用 Meta Workflow 拆解业务流，形成 A 的流程部分

Meta Workflow 以 Meta Orchestrator 的目标分解、流程结构与依赖分析，以及 Meta Skill 的目标、执行段、判断段和判据分析为理论基础。本节与 §3 共同形成文件组 A，包含业务流程、整体架构图及 graph；正式的员工、Skill 包编译在第二部分执行。

完成时序流程后，再按 Orchestrator 判断工作形态：单条线性的工作，直接展开其执行与判断段；涉及多个主体、时间跨度、独立触发或独立完成核验的工作，再建立跨段网络。每次拆分要写出理由，避免仅按职能名称或页面数量增加节点。

2.1 从结果倒推完整任务

为选定业务写清最终结果、成功与失败条件、谁使用结果、谁有权作决定。再用一条真实案例，从触发开始顺着信息与动作走到结果：谁发起，拿到什么，做了什么，交给谁，如何知道已完成。

把规则表和职责表还原为“何时、满足什么条件、做什么”的时序事实。流程图标出持续等待或中断、需要裁决的分叉、同时开展的分叉；由材料推断出的关系单独标注。保留事实清单，检查每项必要事实和动作在流程中的归宿。

保留人工环节、系统外环节和异常分支。例如，业务员确认异常原因、负责人批准处理、客户补充资料，都应有输入和输出。自动化范围由任务需要和实际能力决定。

2.2 逐段区分执行与判断

执行段是按明确规则完成操作、留下可观察成果的部分；判断段根据证据作出选择，并改变后续走向。为段落编号，写明正常顺序、分支、汇合、等待、失败返回和结束条件。并行段需要说明启动前提、共同依赖、合流条件和失败接手人。

为执行段填清下面内容。此时描述业务与系统所需能力；进入 Skill 蒸馏时，再按现役 Meta Skill 补齐其机器契约和验证要求。

执行段字段 必须回答
动作与对象 谁对哪个对象做什么
输入与依据 读取什么材料或数据，遵循哪条规则
可达入口 经哪个系统、工具、接口或人工交接完成；可用性是否已确认
产出与位置 形成什么记录或状态，保存在哪里，交给哪一段
合法结果与核对 哪些值或状态才成立，怎样核对操作产生的结果
影响与失败 是否改业务数据、发消息或触发后续动作；失败、重复、状态未知时怎样处理

2.3 展开判断过程

每个判断段按四个相位追问：检索需要什么证据；整合时如何处理来源冲突；形成哪些候选解释或方案；审核时依据什么标准选定，并转向哪一段。

最终留下三件事：判断标准、触发条件、逐分支去向。标准已有权威来源时直接引用；需要从案例提炼时同时看成功、失败和边界案例。证据不足的判断标明假设、适用条件和待补项，保留有权人员的判断位置。不得用模型生成的数字补业务阈值。

每个判断段都应覆盖信息不足的情况：需要补什么、交给谁、何时重新判断。禁止把“视情况处理”作为流程终点。

多段协作时，逐条检查交接：下游启动所需数据和授权是否齐备，交接者是否有权作该决定，等待是否有负责人、期限与兜底。需要独立确认完成的段，定义完成凭据；需要跨时段存活的工作，定义中断后的接手或重启条件。关键事实与必要动作都应有明确归宿。

2.4 用样本推演并收束

至少推演一条主流程和项目最重要的异常路径。逐段检查上游产物能否作为下游输入、对象与状态是否一致、每个分支有没有接手者和终点。发现缺口回到对应段修订；推演只说明设计的连贯性，实际运行效果在开发后验证。

产出： workflow/ 中可审阅的业务流程图、段落说明、规则来源、正常及异常案例、未决事项。读者应能沿着编号复述一件业务如何完成。

3 补齐整体架构图和 graph，交付完整文件组 A

沿业务流逐段决定由人、既有系统、新建应用、数字员工或 Skill 承担。先确认每一段需要的能力、身份、数据和动作，再划分模块与角色。一个员工可以调用多个 Skill，一个 Skill 可以服务多个用例；是否拆分依据职责、复用、权限和运行依赖。

系统架构至少说明下列关系：

设计面 应表达的内容
系统边界 项目交付到哪里；客户既有系统、平台能力和人工工作各承担什么
模块职责 每个模块负责哪些流程段、产出什么、由谁维护与接手失败
数据流 数据从哪来、以哪份记录为准、如何流转与更新、哪些只是展示或缓存
控制流 谁触发员工或任务，谁批准有影响的动作，谁可以中止，结果返回哪里
能力与入口 数据表、Workbench 页面、员工、Skill、API 或其他工具如何连接；哪些能力已经核实
关键约束 身份与权限、业务时效、数据量、运行成本、重复执行与恢复等会改变方案的条件

统一画出整体系统图，并附“业务段 → 承担方 → 数据 → 工具入口 → 结果接收方”对应表。系统图中的每条调用和数据连接，都要在表中找到依据。

出现技术缺口时，先区分参数、版本、身份、权限、环境与能力缺失。记录需要支持的用例、预期能力、已核查证据和替代方案，交架构负责人判断；涉及对外承诺或客户投入变化时，由 PM 接回上层决策。

A 组交付清单： 下列三个文件提供默认落点。已有项目可以沿用原文件名，在场景开发目录的 README 中逐项登记实际路径；三个内容项必须齐备。

A 组文件 必须写清楚什么
workflow/business-workflow.md 开发范围、角色、业务流程图及逐段说明；业务目标与背景附 Arcubase 链接；每段的触发、输入、执行或判断、规则依据、输出、交接和异常处理；至少推演主流程与关键异常
workflow/architecture.md 整体业务与系统架构图；人、既有系统、Workbench、Arcubase、数字员工、Skill 和外部工具的职责与边界，以及数据流、控制流和权限关系
workflow/graph.md 业务协作关系的 graph 及节点、边说明：稳定编号、节点对应的业务段与承担方、边的类型与触发条件、前后依赖、并行与汇合、等待、回退及失败接手关系

流程图、整体架构图和 graph 均保留可编辑源（例如 Markdown 中的 Mermaid），并提供可直接阅读的图。graph 允许表达实际业务中的回路；连线区分数据传递、控制触发和同步调用，节点与边必须能对应到流程说明和架构职责。采用 Meta Orchestrator 的 topology.json 时，从该拓扑源生成对应的人读图，保持同一套节点与边定义。

A 的阅读入口写明母项目编码、场景编号、版本和上述开发文件链接，来源与已确认决定引用 Arcubase 对应记录；影响开发的未决项保留摘要与链接。完整文件组 A 随后作为 Meta Spec 的输入，并保留为开发架构的正式组成部分。 B 编写过程中发现需要改变业务规则或职责时，先回到 A 确认并同步，再修订对应 spec。

对照 Orchestrator 原规格，审核前使用其 Step 0—3 的事实清单、流程判别、切段和边约束方法。此时的系统图属于架构设计；依赖实际 Skill 包的最终网络声明、版本核对和运行测试，留在审核通过后的编译与联调中完成。

4 使用 Meta Spec，以 A 为输入编写文件组 B（九份 spec）

以下九步说明 Meta Spec 每份文档应怎样形成、填写什么及怎样核对。起草前完整读取明确版本的 A（业务流程、整体架构图和 graph）、相关来源、技术约束与同编号写作参照，将业务流程和业务架构落实为开发所需的具体规格。按下列顺序起草，发现冲突时返回关联项修订；需要改变业务范围、规则或职责的事项，回到业务流程环节澄清并同步两个部分。安全约束贯穿各项，数据模型与权限、页面与接口需要往返核对。

第 1 步 概念梳理

从流程和真实样本提取业务对象、角色、术语与关系。对容易混淆的词写清含义、范围、唯一标识和边界；区分业务名称、系统内部名称及外部系统名称。把业务规则挂在对应概念上。

交出 01-concept.md： 术语表、角色与对象关系、关键约束、原始样本指针。后续用例、表格、页面和接口沿用同一含义。

完成检查： 同一对象跨文件可识别，关键名词有定义；未知关系明示，未被 AI 补造。

第 2 步 用例

按真实角色和目标写编号用例。每条用例包括发起者、触发条件、前提、输入、主流程、成功结果、失败及异常、权限要求和对应验收项。把前段业务流程编号关联进来。

交出 02-use-cases.md： 用例及验收对应表、主流程和异常样本。页面点击、员工触发和定时任务都应追到用例。

完成检查： 已确认的验收范围有覆盖；每条用例能说明业务完成后会留下什么可检查结果。

第 3 步 数据建模

架构负责人结合用例与样本，与 AI 逐项讨论表格结构。先确定一行代表什么，再确定唯一键、字段、关系、状态及转换、约束、来源、写入者和读取者。记录计算值的规则，区分主数据、业务事件、当前状态和派生展示。

将设计落实到 Arcubase 的计划结构：App 采用既有还是新建、表与字段的稳定 key、类型、必填及合法值、关联、业务编号、访问范围和可调用入口。复用已有 App 时先回读其真实 Schema，列明保留、扩展和迁移内容。尚未创建的资源只写计划名称与 key，实际 ID 留待获批实施后回填。

交出 03-data-model.md： 表与字段字典、关系及状态图、数据来源与权威位置、样例映射、拟采用的 Arcubase 结构和待核实能力。

完成检查： 用例需要保存和读取的事实都有位置；重复、历史、状态变化和授权关系能表达。第三步完成后，后续建表以该版结构为依据。

第 4 步 权限与安全

按“角色 × 对象 × 动作 × 数据范围”定义授权。区分可信登录身份、应用业务角色、对象归属与项目成员关系，明确它们的映射和唯一维护入口。敏感动作标明批准者、批准记录和审计要求。

交出 04-security-privacy.md： 权限矩阵、身份映射、授权维护方式、后端执行位置、敏感数据规则、重复操作和失败处理要求。

完成检查： 允许与拒绝路径都能说明；页面隐藏按钮以外，后端或数据层有对应约束；没有需要人工长期维护的多套角色名单。

第 5 步 站点架构

沿整体系统架构，为不同角色安排工作台入口、菜单、路由和任务之间的转场。列清哪些任务由页面完成，哪些进入员工会话、人工审批或外部系统。各页面注明对应的用例、对象与权限。

交出 05-site-architecture.md： 站点结构图、路由与页面清单、角色入口和跨系统交接。整体模块职责和数据流引用前面的系统架构总结。

完成检查： 核心用例有可达入口和返回位置；没有脱离业务与后端能力的孤立页面。

第 6 步 页面布局与视觉交互

逐页确定主任务、信息层级、主要操作、字段与数据来源。把加载、空、错误、成功、无权限和等待人工处理等状态画出来。按项目选定的视觉参考包，明确布局、组件、颜色、字体、密度与适配要求，并标注引用了哪个参考页面。

本手册的前端基线为 quekou-工作台前端共享包-1.0.0.zip。按包内 START_HERE.md、design/style-spec.md、design/page-recipes.md 和组件说明读取。第 6 步写清所选风格：6 号 Bento、7 号 Glass 或 10 号 Ambient，以及 accentHue / density / radiusScale / surfaceMode 四项参数；未另行选择时沿包的 6 号与缺口品牌色起草，随架构送审。

页面采用包内 Overview、List、Detail、Settings 配方与标准区块；每个页面选择适合其用例的配方。正式配方顺序以 design/page-recipes.md 为准，样品页仅作相应视觉参考。超出现有配方或参数范围的需要，先说明业务理由和视觉扩展方案，随设计审阅。

交出 06-page-layout.md 及必要原型： 关键页面布局、状态与动作说明、视觉参考、组件约定。演示数据应明确标识，不进入正式业务运行逻辑。

完成检查： 使用者能找到任务和操作；按钮对应真实动作；真实长文本、空数据、错误和权限状态有表达。视觉参考的业务结构须经本项目用例筛选。

第 7 步 API 与调用契约

按用例列出页面、员工、Skill 和既有系统实际使用的调用入口。每项写清提供方与调用方、输入输出、身份权限、错误语义、分页或批量、幂等与重复处理、超时和结果回读方式。

交出 07-api.md： 调用契约及能力映射。采用 Arcubase 时包括 typed ingress 的计划；采用平台现成客户端时引用其真实契约；需要自建接口时说明理由、责任模块与生成方式。

完成检查： 页面动作和技能执行都有可达入口，调用双方理解一致。接口变更需要同时追踪数据模型、调用代码及测试。

第 8 步 技术选型与目录

为已确认架构选择实施工具，写明采用、复用与新增的依据。数字员工使用 Meta Agent，技能使用 Meta Skill，Workbench 工作台使用 workbench-app-development。结构化业务数据按第 3 步落到选定 Arcubase App；其他系统接入沿第 7 步契约实施。

交出 08-tech-stack-and-directory.md： 工具与 Skill 的精确入口、实读版本或提交、项目代码与文档目录、认证方式、环境、依赖及锁文件、生成代码位置、部署目标和运行责任。

5.2 在既定场景目录 push，由项目经理邮件异步送审

一、核对既定开发入口并 push。 使用 §0 已登记的母项目仓库及本次场景文件夹。核对仓库名、Arcubase 母项目与场景映射，确保 workflow/ 中的 A、design/ 中的 B 和 plan/ 中的独立计划属于对应场景。Arcubase 项目资料索引登记仓库 URL、各场景开发目录及送审版本链接；GitHub 中只保留开发文件、关联链接和技术记录。

首次送审前，将对应场景的 workflow/、design/ 和 plan/开发计划.md push 到该仓库，检查审核人能够访问，并记录本次 commit。实现代码、技术变更与测试记录随获批开发持续 push。项目背景、调研原件、沟通解释和实际推进记录继续在 Arcubase 维护。

主题：【项目编号】【架构送审】【版本】项目简称

GitHub 仓库：母项目编码-客户名称-期号，仓库链接
场景开发目录：对应场景文件夹链接
送审版本：commit
第一部分｜开发架构（A+B）：该 commit 下的统一阅读入口
  A：业务流程、整体架构图及 graph
  B：九份 spec Markdown

  计划摘要：开发时间、开发方式、预计 token 与费用范围

送审采用异步方式，不要求总架构师即时响应。 项目经理发出邮件后等待异步审核意见，并安排团队继续推进不依赖该审核决定的准备工作。IM 发包、聊天中询问“是否可以开发”或临时要求同步审阅，均不作为正式送审方式。材料需让审核人按自己的时间独立读取、判断和回复；技术答疑及修订由项目经理统一组织。

三、在 Arcubase 留存审核与推进结果。 项目经理将夏洛克本人对明确开发版本的审核结论及意见来源关联到对应母项目和场景，记录审核人、时间、送审 commit、各场景获批范围、决定和条件。GitHub 保留被审核的开发版本及对应 Arcubase 记录链接。实施人员依据各场景的通过记录领取批准文件和条件；退回时由项目经理在 Arcubase 组织补料与问题处理，架构师修订开发架构，push 新 commit 后由项目经理重新发邮件送审。

邮件已发送只表示完成送审。尚未取得通过记录的场景范围继续保持待审；按审核结论和实际推进情况更新 Arcubase 场景阶段，阶段流转记录写明变更原因和影响，“新版本／依据链接”关联相应审核依据与开发版本。母项目的“项目交付流程”维护整体交付环节，场景进展按所属关系汇总。AI 可整理材料与检查引用，审核决定由夏洛克作出。

第二部分 审核通过后开发

6 领取批准文件，在原项目仓库开发

FDE 核对审核通过版本、本次实施范围、条件与实际环境。PM 按 §5.1 已提交的开发计划统筹资源、客户配合和交付安排，并落实审核附带的条件。

获批后按以下顺序执行，沿用同一母项目仓库和场景目录：

  1. 领取批准版本，落实开工条件。 项目经理在 Arcubase 留存审核来源、获批 commit、场景范围及附带条件，落实人员、权限和资源；FDE 读取获批的 workflow/、design/ 和 plan/。
  2. 先建立 releases/，开展开发。 按 A+B 和开发计划选择工具并实施，按版本保存开发产物。实现代码、Skill、工具配置及可复现的产物入口按实际工具和框架组织；每个开发版本记录产物位置、对应 commit、运行方式、采用工具版本和已知问题。形成可测试版本后，标记为“待测试”并交给测试环节。
  3. 再建立 tests/，执行测试。 针对明确的开发版本，按 §13 执行用例，记录被测版本及 commit、环境、预期、实际、证据、缺陷和结论。测试记录与 releases/ 中的对应版本相互关联。
  4. 修复后重新形成版本并复测。 发现实现缺陷时返回开发，更新 releases/ 中的开发版本，保留变更说明，再在 tests/ 中补充复测记录。涉及已批准架构或范围的变更，按 §15 返回相应审核环节。
  5. 测试通过后复核、发布和交接。 按 §13 完成技术复核，取得发布批准后按 §14 上线并进行正式环境验证。部署回执、运行入口和技术交接资料归入 releases/ 对应版本，上线测试与复测证据保存在 tests/。项目经理在 Arcubase 更新实际阶段、审核验收依据及这些开发文件的链接。

releases/ 从开发阶段开始保存版本，版本状态随实际结果标注为开发中、待测试、测试通过或已上线；进入该目录本身不表示已完成测试或上线。正式测试开始前无需预建 tests/。两目录各自索引已有产物与记录，避免重复维护同一份源码。

开发继续使用 §0 建立并登记的母项目仓库及对应场景文件夹，固定仓库名、母项目编码与场景编号保持一致。对应场景的 workflow/、design/、plan/、实现代码、资源映射、技术变更及测试发布版本持续维护在 GitHub，并引用 Arcubase 中相应的批准依据。项目核心内容、日常推进、审核与验收结论由 Arcubase 维护；仓库记录采用的通用手册与工具版本。项目材料按对应访问权限保存，凭据按环境配置管理。公共规范仓库集中承载共用手册、工具与可公开的反馈。

把批准的开发架构 A+B 与独立开发计划交给开发 AI，要求实际读取本任务指定的 Toolkit、Skill 和 references，回报已读文件、采用版本、输入和输出。开发任务写清：批准版本、用例、允许修改的目录和资源、指定工具、真实样本或授权测试记录、预期结果、完成条件和阻塞接手人。实现、实际测试和未验证项分别报告。

9 用 Meta Agent 制作数字员工

把获批的业务目标、职责、用例、协作关系、知识来源、权限、工具入口、人工决定点和失败接手要求交给 Meta Agent。按实际安装版本的入口读取和执行，输出位置保存在所属项目。

使用前取得项目指定的 Meta Agent 包，核对入口、目标宿主、依赖和验证状态。包尚未接入时，先完成工具准备；员工制作继续遵循 Meta Agent 路线。

组织内数字员工按 FDE Meta Agent 路径准备五块规格：身份、职能、权限、面孔、环境。环境中列出实际团队、员工目录、模型与技能目录、知识库路径、工作区和所需表格。所需工作区、知识库、Arcubase 和触发任务按各自工具预先落实或另行安排；Meta Agent 负责员工构造及配置。

依据指定包完成环境连通、规格校验、身份与目录解析、提示词与简介编译、形象生成与核对、员工创建或更新、配置逐项写入与回读、最终完整回读。原规格列出的九类配置和十六项回读按包内清单逐项完成，保存期望配置、实际配置、证据和交付清单。需要对外发布市场产品时，另按 Meta Agent 的 Builder 路径及其发布授权处理。

员工设计要能说明：接什么任务、负责什么结果、何时调用哪个 Skill、怎样获取授权数据、哪些动作要等待人工决定、怎样报告完成或失败。选择已有员工复用或新建员工时，依据批准的系统架构，避免出现重叠职责和多套规则来源。

员工产物生成后，完成工具与 Skill 的实际绑定，并在目标宿主验证。至少覆盖正常任务、材料不足、无权访问、执行失败、需要人工决定及越出职责的输入。报告所用身份、实际触发、工具动作、保存结果、接手人和未覆盖项。

工具必须安装或接入到员工实际可访问的设备或云端环境。记录宿主、执行身份和真实工具路径，Skill 使用该路径，测试从员工侧触发并回读结果。开发者自己能调用工具，不构成员工可调用的证据。

需要人工决定的动作，只读取相应对象、版本和有权人员的真实决定。未回复时等待或按已定规则升级，拒绝时进入拒绝分支；员工和 Skill 不得代替人作批准，也不得继续执行依赖该批准的动作。

交出： Meta Agent 生成的员工文件与配置、实际绑定、测试记录及运行边界。员工岗位正文或头像已存在，只能说明相应配置已经形成；可交付状态以实际任务结果为依据。

10 用 Meta Skill 蒸馏技能

按批准的技能划分，把业务流中的执行段、判断段、权威规则、正反样本、接口契约、输出位置和权限交给 Meta Skill。所有本项目技能蒸馏统一经 Meta Skill 入口处理。

蒸馏依次完成目标与边界、段落切分、判断与执行展开、判据来源和缺料处理，再编码并检验 Skill 包。现役 Meta Skill 的机器契约、触发检验、独立检验和回流要求随包执行；手册只规定业务输入和交付要求。

审核前形成的分析材料作为正式蒸馏的输入。正式制作仍走 Meta Skill 完整流程，核对输入与批准版本，并保留该次编译的实际产物与检验记录。

涉及写业务数据、发消息、启动任务等副作用时，按 Meta Skill 的 stateful 工作流要求，明确重复执行、未知状态、失败恢复和人工接手。没有核清外部结果前，不直接重试同一写入。

把检验通过的包部署或绑定到目标员工后，再在该宿主运行授权用例：确认 Skill 被实际触发，读取了指定规则与真实数据，执行了获准动作，结果可回读，人工决定有真实记录。定时或事件业务先明确执行员工、目标与范围、时区和业务日历、触发方式及重复执行规则，再验证真实触发、执行和结果保存的整条路径。

交出： Skill 包、版本、评测与运行记录、宿主绑定、未验证范围和失败回流位置。技能问题回到对应步骤或判据修订；涉及业务规则、权限或架构的改变，先进入项目变更路径。

按获批需求选择能力：仅认证页面无需额外业务客户端；使用 Host 资源选 octopus；任务与项目选 taskboard；共享持久业务数据选 arcubase。按 Skill 的选择规则安装与使用官方客户端，记录实际依赖和锁文件。

逐条用例实现页面与动作：从目标 App 或平台获取真实数据，按第 6 步落页面，按第 7 步接生成接口。每个主要按钮必须执行它所声称的动作，展示处理中与错误，成功后回读并刷新结果。真实空数据展示空状态。

视觉复核： 对照第 6 步批准的参考与布局，在真实数据下检查信息层级、内容密度、主操作、长文本、空错状态、权限状态以及约定屏宽。遵循包内正文及辅助文字至少 4.5:1 的对比度要求，核对键盘与焦点、明暗和密度、弹窗取消与失败、手机页面无整体横向溢出。表格在自己的容器内滚动。原型图和实际页面并排检查，并保留关键页面截图。

按包内 docs/上线验收.md 补验真实对象和指标口径，未知值不显示为零；保存后刷新并按权限换会话核对结果。危险操作等待真实异步结果，失败保留错误和可恢复状态。包的既有前端测试只覆盖其声明范围，目标客户浏览器、真实权限和业务运行按本项目继续验证。

交出： 可操作的本地应用、代码与依赖版本、真实用例证据、视觉复核结果和未完成项。

14 发布与上线测试

Workbench 发布按现役 Skill 执行：先完成本地实际验证，提供本地 URL 和证据，取得发布批准；开发者明确免除交互式本地验收时，保留该授权，并完成代理侧验证。架构审核通过与上线发布批准分别记录。

发布前固定代码、依赖、Schema 和 Skill 版本，核对部署目标，准备需要的数据迁移、上一可用版本和实际可执行的恢复方式。新建远程项目之前先按现役 CLI 的 list/show 合同排查已有项目，确认目标与复用范围。恢复方案同时核对旧页面、代码与当前数据 Schema 是否兼容。只运行项目声明的相关检查与生产构建，检查 dist/index.html。

按官方 coding projects list/show/create/publish/watch 路径发布。首次创建远程项目的结果不明时，先查询已有项目。发布返回中的 deployment.taskId 用于跟踪任务，deployment.id 不作替代。queued / processing 时继续查询同一任务，默认每 5 秒一次、最多 10 分钟；执行时以指定 Skill 的有界跟踪合同为准。failed 时记录错误并停止本次发布推进；结果未知或超时时先核查实际状态。active 和可用 workbenchUrl 确认部署完成，业务完成还需下一步正式入口测试。

打开正式入口，用目标身份和约定测试数据重新走核心用例，核对团队、真实读取、获准写入、写后回读、权限拒绝及视觉。员工或定时任务还需在目标宿主验证触发、执行和结果位置。发现线上错误数据时先停住受影响动作，核清范围后修复并复测；需要恢复时按已核实的恢复路径执行。

最终交出： 正式入口、代码/依赖/Schema/员工/Skill 版本，部署 projectId / taskId / status / workbenchUrl，已核验环境，上线测试与缺陷复测结果，限制、接手人及恢复资料。技术交付随后接入上层 FDE 的真实业务试运行、培训和客户验收安排；重合的试运行测试共用证据。

将实际部署回执、运行入口、恢复资料与技术交接入口补入 releases/ 对应开发版本；将正式环境的测试与复测结果补入 tests/，回链具体部署版本。客户验收原文及项目推进结论由项目经理保存在 Arcubase，GitHub 保留对应开发文件与关联链接。

排产：OctoPlanner

OctoPlanner 是 Bun-first TypeScript 命令行工具。先读取官方 README、package.json 与命令帮助，记录采用的提交或版本。仓库给出的准备入口为 npm install，工作区初始化为 npm run octoplanner -- workspace init；按所选版本核对 Bun、Node 和依赖要求。

通过适配层把 ERP、MES 或 Excel 数据转换为 requirements、items、routings、resources JSON，检查稳定 ID 与引用关系，再加载规则并创建计划。情景调整沿 plan load → plan revise --from-plan → plan diff 的真实命令合同实施；Excel 回写用 externalRef 对齐原始行和基线，核对 diff 后按授权写入。

业务建模先确定变量、硬约束、优化目标和可行性判据。用人工可核对的小样本，再用真实样本检查资源冲突、工序顺序、停机、断料和不可行情形。每次读取命令返回的 ok / data / warnings / notModeled，解释未排程原因与未建模范围，并保存计划、差异和异常报告。排程结果经业务人员审核后，按批准规则写回系统或触发后续任务。
