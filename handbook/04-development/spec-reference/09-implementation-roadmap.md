# 08 - 宏观实现路线(Implementation Roadmap)

## 0. 总原则(强制)

1. 先后端, 再前端  
2. 先生成 TS 类库, 再构建前端  
3. 最终必须建立并通过全链路类型验证  

---

## 1. 阶段A: 后端优先落地

目标:
- 完成领域模型、用例编排、API 路由与权限边界
- 所有请求/响应模型强类型化(VO/struct), 禁止动态结构漂移

输出物:
- `host` 后端可运行
- `06-api.md` 对齐的接口实现
- OpenAPI 原始契约可生成

完成门槛:
- 后端单测/集成测试通过
- 核心 API 行为稳定(成功与错误语义固定)

---

## 2. 阶段B: TS 类库生成先行

目标:
- 把后端契约转为前端唯一数据源

执行:
1. 从 OpenAPI 生成 TS SDK/Types
2. 生成物提交入库(只读管理, 禁止手改)
3. 建立漂移检查(重新生成后必须无 diff)

输出物:
- `types/ts/*/api.ts`
- `api-wrapper.ts`
- 生成脚本与 CI 漂移门禁

完成门槛:
- 任何接口变更都会先体现在 TS 类库
- 漂移检查失败即阻断合并

---

## 3. 阶段C: 前端构建与业务实现

前置条件:
- 阶段A、B完成并稳定

目标:
- 前端仅依赖 TS 类库进行开发
- 页面/服务层不允许手写 `fetch` 绕过 SDK

执行顺序(建议):
1. `portal`(高频业务路径)
2. `tenant`(租户管理能力)
3. `admin`(平台运营能力)
4. `pay`(购买链路收口)

完成门槛:
- 前端类型检查通过
- 前端构建通过
- 核心交互链路可用

---

## 4. 阶段D: 全链路类型验证(最终门禁)

验证链路(必须全通过):
1. 后端类型与质量: `go test` / `go vet` / `golangci-lint`
2. 契约一致性: OpenAPI 生成 + TS 类库生成 + 漂移检查
3. 前端类型与构建: `lint` / `type-check` / `test` / `build`
4. 关键链路联调: 核心业务 e2e/集成验证

阻断规则:
- 任一环节失败, 禁止合并
- 禁止“先合并后补验证”

---

## 5. 里程碑定义

- M1(后端可用): 后端核心 API 可用且测试通过
- M2(契约稳定): TS 类库稳定生成并纳入漂移门禁
- M3(前端可用): 前端主路径可运行且构建通过
- M4(可发布): 全链路类型验证与关键链路验证全通过

---

## 6. 变更控制要求

- 接口变更必须先改后端契约, 再更新 TS 类库, 最后改前端
- 禁止前端先行定义临时字段“反推后端”
- 禁止绕过类型系统做临时兼容
