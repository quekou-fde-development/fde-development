# 澄清与决定循环

## 加载链（上下游）

**上游**：`../SKILL.md §澄清循环` — 分析发现设计关键缺口、冲突或可选方案时读取本文件。

**管辖文件（下游）：**
- `pre-review-analysis.md` — 获得回答后重新计算业务流、判断和系统边界。
- `nine-document-authoring.md` — 已确认内容需映射进九份文档时继续读取。

**同级联动：**
- `input-and-evidence.md` — 每项问题回到原始材料、来源状态和决定权。

## 何为必须澄清

下列事项缺失、含糊、互相冲突或存在多种会改变设计结果的解释时，必须向人确认：业务范围和成功条件、角色与批准权、流程和异常终点、实体及权威记录、状态变化、权限、现有系统或接口能力、Arcubase App 的既有/新建选择、业务角色和对象授权、外部动作与失败接手、验收、技术与部署约束。

可以保留尚未实测的平台能力、上线前联调和总架构师审核条件为限制；它们与“现在无法确定该怎么设计”的问题不同。后者必须先澄清。

已确认约束下有多种等价表达时，Skill 自行选用清楚、一致的术语、字段名、接口名、章节或呈现方式。不要把每个 API、字段或页面措辞拆成人类问题。候选设计在范围、权力、数据、动作、合规、成本、周期、验收或运行责任上产生实质差异时，才集中呈现选项和影响。

## 平台选择与核验的分界

对 Arcubase，先判断既有 App 与新 App 哪一种符合项目边界。存在多个候选既有 App 而材料无法判定时，问题簇要求有权人选择精确目标；选择新 App 时，问题簇确认业务所需的表、字段、Link、角色和访问边界。候选设计可以提出这些结构，平台写入留在审核通过后的实施阶段。

业务问题应聚焦角色能做什么、谁维护角色关系、对象归属如何影响操作资格、哪些操作需要批准，以及撤权的预期时效。Arcubase organization actor 的精确数值 ID、表 ID、field ID、SDK 方法与 `linkto` JSON 形状由官方类型、CLI `--help`、schema 读回或最小验证确定；它们不是让业务方逐项拍板的材料。当前项目里出现过的 WorkOS 三个角色、人员 ID 或任何固定角色集只属于该项目上下文，不能写入通用候选架构。

若设计依赖 Host 能力、人类与数据入口的身份映射，问题簇要说明需取得何种允许/拒绝验证。项目涉及数字员工代办或 `conversation_member` 时，再加入发起与执行身份的验证条件。未取得证据时，将该能力写为实施前核验条件；不要把管理 CLI 成功或管理员读取成功当作普通成员隔离、撤权或代办身份的完成证明。

## 问题簇格式

按同一决定主题合并问题，避免把同一件事拆成散问。每簇使用以下结构：

```text
问题编号：D-xx
决定主题：
已知事实与来源：
需要确认的内容：
可选项或需要补的材料：
会影响的流程段 / 九份文件：
建议由谁回答：
最短可回答方式：
```

问句要说明证据与影响，让回答者能作出业务决定；不得要求回答者理解内部实现术语。没有材料支持时，写“需要补什么”，不要把模型建议包装成唯一选项。

## 吸收回答

对每个回答记录：问题编号、回答原文或决定位置、回答人及其权限依据、回答时间或版本、涉及的流程段、对象、用例和文件。随后：

1. 将已确认回答写回事实或决定；
2. 更新受影响的流程分析、数据、权限、接口、页面、技术路线和实施依赖；
3. 对仍开放部分拆出新的具体问题，或保留其为实施前验证限制；
4. 检查是否引入与既有回答或来源相冲突的新结论。

一项回答改变对象、状态、权限、接口或路由时，不能只修订一个文档。必须更新它所影响的所有候选内容。

## 停止条件

可生成最终九文档候选的条件是：影响设计的问题已回答或被有权人明确裁为范围外，且 `unresolved_questions` 为空。总架构师对可行性、商务匹配、周期、风险和条件的审核在此之后进行；不能用“后续审核会看”跳过当前设计所需的澄清。
