# 架构 · Meta Agent（09.20）

本件是 `spec-09-meta-agent.md` 的架构面：组件、边界、数据流、与既有两代编译器的关系、与平台的关系。

## 一 · 在系统中的位置

```
席位意图（认知位 / 职能）
      │
      ▼
┌─────────────────────┐        出图请求单        ┌──────────┐
│  meta agent skill    │ ───────────────────────▶ │  Codex   │
│  （一席 → 一体）      │ ◀─────────────────────── │ image_gen│
└─────────────────────┘        PNG 成对            └──────────┘
      │
      ├── FDE 面：团队管理 API  → 团队私有数字员工
      └── Builder 面：builder CLI → 市场上架产品
      │
      ▼
  回读证据（十六项 / 七项）
```

meta agent 的上游是席位规格（谁需要存在、干什么），下游是平台实体。它自己不是运行期组件，是**编制期的编译器**：一次运行产出一批静态配置，运行期不再介入。

## 二 · 组件

| 组件 | 形态 | 职责 | 不做什么 |
|---|---|---|---|
| `fde-meta-agent` | Claude skill | 席位规格 → 团队私有数字员工 + 回读证据 | 不建工作区 / KB / ArcuBase 应用 / 本体；不改系统设置；不管批量循环 |
| `builder-agent` | Claude skill | 产品定义 → Builder worker + 已发布版本 + 回读证据 | 不编译技能包（meta-skill 的活）；不做租户侧部署与升级 |
| 出图执行体 | Codex 内置 image_gen | 按请求单产出成对图像 | 不做风格判定（QA 闸的事） |
| 批量驱动 | Codex / Claude Code | 遍历席位清单，串行调 skill | 不内联编制逻辑 |
| meta-skill | Claude skill | 把上面两个 skill 蒸馏成持久包 | 不产出员工配置（提示词是一次性产物） |

## 三 · 数据流

### 3.1 输入侧

```
图谱节点 graph-09.16.json ─┐
域参数包 params.json ──────┤
默认表（工具键 / 模型 / 技能）├─▶ seat-spec.json ──▶ skill
现役目录（运行时读）────────┤
09.14 面孔清单 ───────────┘
```

`seat-spec.json` 是冻结快照，落 `seats/<logical_id>.json`。编制过程中不回读图谱，只读快照，保证同一份输入产生同一份输出。

### 3.2 输出侧

```
skill → identities/<id>.json      （平台 id 对账表，供后续席位解析回报目标）
      → desired/<id>-profile.json （意图态九键）
      → desired/<id>-effective-prompt.json（终版提示词逐字节）
      → evidence/<id>-*.json      （每步 intent 与 response）
      → images/<id>-*.png + qa.json
      → after/<id>-images.json
      → readback.json             （十六项结果表）
      → manifest.json             （整批汇总）
```

`identities/` 是批内唯一的跨席依赖：后编制的席位要用前面席位的 `employee_id` 填回报目标。因此**批内必须先建体、后配边**，或者对未解析的目标登记 `UNRESOLVED` 并在该目标建体后补 PATCH。

## 四 · 架构决策

### D1 · 为什么是一席一体，不是一批一体

批量的两个诉求（吞吐、一致性）由外层驱动与共享权威源满足。skill 内部一旦引入批，就必然要处理部分失败、回滚与跨席依赖顺序，而那三件事的正确性取决于席位清单，不取决于编制器。一席一体的失败域是本席：已通过的席位不因后续席位失败而回滚，失败席位单独重跑。

### D2 · 为什么提示词是主产物，而不是配置的附属

平台的提示词字段是运行期唯一的**行为载体**：身份、职责、域边界、权限约束、思考骨架都在里面。九键配置决定「能碰什么」，提示词决定「会怎么做」。因此编制器的核心是**六段编译器**，其余是 IO。这条决定了 skill 的成败判据是提示词逐字节相等，而不是配置写成功。

对照两代的演进，这条是逐渐显出来的：09.07 的提示词是模板加条件尾巴（浅）；09.13 全参数化，1466 字，无目录（深）；09.16 提示词变薄而尾部挂 5 KB 目录 JSON（广度换深度）。09.20 取 09.13 的深度，目录移出。

### D3 · 为什么出图交 Codex

Claude Code 无原生出图。09.14 的二十二张图是 Codex 内置 `image_gen.imagegen` 出的，链路已验（三参考图 + 系列风格块 + 视觉 QA + 哈希回读）。把出图留在 skill 内会引入一个 skill 无法自证的能力声明；改成请求单 + 独立 QA 闸，skill 的每条断言都可由自己的工具链验证。

### D4 · 为什么 Builder 侧必须做租户无关性 lint

Builder 产品的可移植性要求它的定义里不含任何租户实体。团队私有员工与市场产品写的是同一个 `promptSpec` 字段，一个经验不足的编制者会把 FDE 侧的提示词直接搬过去，于是产品里带上 `de_*`、`workspace_*`、`/kb/人力/`，上架后对其他租户无效。lint 是机器可判的拒绝条件，成本一行正则，收益是发布前的硬门。

两个已核事实说明产品面与实例面是两套：08-17 的草稿 worker `{{BUILDER_DRAFT_WORKER_ID_1}}` 把提示词与八个运行文件直接写入 Builder（scan 为 draft，`file_count=8`）；08-25 v3 上架后，08-19 入职的租户实例 `{{FDE_EMPLOYEE_INSTANCE_ID_1}}` 仍持旧版快捷入口。写进一个面的内容不会自动到达另一个面。

### D5 · 为什么版本与升级分属两侧

Builder 发布产生新版本，已雇实例不自动替换（08-25 上架的 v3 对 08-19 入职的实例无影响）。skill 因此把发布与升级拆成两段：发布在上架前完成并有硬断言；升级产出计划表，动作归租户侧。把升级写进 skill 会让「上架成功」的判据混入外部系统状态。

## 五 · 与平台的关系

| 平台事实 | 对架构的约束 |
|---|---|
| 提示词字段只在管理面可写（会话面三十条非 GET 路由无此入口） | 编制器必须持管理面凭据；运行期席位无法自我改写身份 |
| `accessPolicy.mode` 只有 `all_team_members` 与 `restricted` 两档 | 「全员可见且域内隔离」表达不了；受限域取隔离优先 |
| `restricted` 恒含该队全部管理员 | 「仅某人可见」在平台上不存在；设计接受为「仅管理员可见」 |
| 回报目标无员工级载体 | 落为提示词约束，机制标 `prompt_constraint`，不声称硬 ACL |
| 记忆配置无载体 | 从产品定义中删除，不编造字段 |
| 图像上传走 `:upload-url` 预签 + PUT + PATCH token | 出图与上传必须分两段，中间那次 PATCH 是幂等键的锚点 |
| 工具键目录 29 项，团队 catalog 24 项 | 判据是 PATCH 加回读，不是 catalog 命中 |

## 六 · 风险与反例

| 风险 | 反例（会推翻什么设计） | 处置 |
|---|---|---|
| 挂载技能在运行期读不到 | 若探针失败，「目录移出提示词」的收益为零且新增一个不可用依赖 | P0 探针 + 回退 `prompt_embedded`；回退路径保留在契约里 |
| 六段模板在 Builder 侧语义不符 | Builder 产品无域、无 ArcuBase 授权，③⑤ 段为空壳 | Builder 侧只取 ①②④⑥ 四段，空段不写 |
| 四位骨架对职能席过肥 | 现役职能席提示词约 1.4 KB 正文，骨架四段占近半，可能挤压域参数 | 骨架写成短标签段，逐条一句话；不展开成教学段 |
| 影子编制与 09.16 差异过大 | 若差异集中在权限键而非提示词，说明真正的不确定性在写面而非编译器 | 差异逐条判定为「设计变更」或「缺陷」，缺陷先修 skill 再全量 |
| 幂等键跨批冲突 | 同一逻辑键在两批里各建一个身体，目录出现两条 | 幂等键含发布号；P2 先解析既有身份，命中即走 PATCH |
