# Meta Spec

读取明确版本的客户分析A、解决方案、来源与技术约束，使用内置的需求登记、流程拆解、概念、用例与数据推导方法，形成B组九份候选技术设计。项目架构师提出技术可行性，FDE编制独立开发计划，PM将解决方案与技术材料作为一套方案一次送审。

[阅读 Skill](source/SKILL.md) · [下载 ZIP](meta-spec-10.19.1.zip) · [查看验证说明](source/verification.json)

各类客户统一先形成解决方案，再生成技术架构，最后由总架构师一次审核商业可行性、技术可行性及整体一致性。产品决定明确后可生成B；缺少业务规则、权限、信息去向或关键交互时先澄清。尚缺独立计划与技术可行性判断时可先形成B，正式整套送审前须补齐。计划沿[现有模板](../../handbook/02-project-management/templates/04-development/开发计划模板_10.08.md)填写。

客户分析A记录现状及来源，产品方案说明拟实现的改善与工作方式，B将其落实到技术设计；三者按明确版本关联。产品或技术变化需同步受影响材料，核对整套一致性后重提。整体审核通过并落实启动与开工条件后实施，已签验收文件保持固定。

10.19.1在预览、最终渲染和独立审计中加入业务决定来源检查。取源前在运行输入区登记App选择、角色对业务对象的操作权限及系统读写边界；每项当前决定须唯一，并逐行引用对应的项目方案或有权人答复。开放或缺失的决定会阻断生成；模拟、参考材料和失真的引文不能关闭这些决定。新答复进入新的候选运行目录，重新取源。

方案作者已经明确的候选决定可继续形成待审B；表、字段和Link仍由Meta Spec推导。来源身份、引文是否支持决定及实际决定权由内容复核与整体审核判断。该检查不增加预先审批或第十份项目交付文档。

九份写作参照和内置推导方法保持。安装以ZIP为准，解压后的`meta-spec/`为安装根；仓库`source/`与安装包逐项一致。本次仓库发布不安装到运行宿主。

本轮验证范围与结果记录在`verification.json`的`clarification_guard_checks`：19项决定守卫回归、16条机械断言及各自反例、原有三组工程回归，以及独立前向运行的实际终态。此前10.19方法与接口审核保留在`single_review_checks`。机械检查覆盖来源绑定和状态约束；完整内容质量、平台行为及跨项目重复生成按各自实测结果判断。

历史四案例属于frozen-v14／10.09.1：借用11/11、客户12/12、巡检9/13、培训报名16/17。后两者的权限、输入约束或汇报缺陷仍保留，不能由本轮流程调整推定已修复。10.15.1、10.16及10.17的历史接口验证见同一验证文件。本轮结果不证明跨项目重复生成、真实客户或目标宿主运行通过。
