# Meta Spec

## 目标与边界

以明确版本的客户分析A（业务流、整体架构图及graph）、方案文档、调研证据、实际审核状态和技术约束，形成以下九份B组候选设计文件：

```text
design/
├── 01-concept.md
├── 02-use-cases.md
├── 03-data-model.md
├── 04-security-privacy.md
├── 05-site-architecture.md
├── 06-page-layout.md
├── 07-api.md
├── 08-tech-stack-and-directory.md
└── 09-implementation-roadmap.md
```

业务流、系统边界、判断点和方案分歧先在本次运行的 `working/` 中分析，再被映射进九份文件。不要新建第十份架构治理文件、巨大统一表头或与项目无关的模板。九份文件的机械回执保持“待总架构师审核”。面向人的交接说明整套材料的实际审核状态及缺件，按下文“整套方案一次送审接口”执行。

本 Skill 不替代现场调研，不自行确认业务规则、阈值、权限或客户承诺，不创建 Arcubase 资源、数字员工、Skill、Workbench 应用或外部系统写入，不安装或发布任何包。获批后的实施由指定的 Meta Agent、Meta Skill、`workbench-app-development` 和其他现役工具负责。

既有九份设计可以作为输入资料，用于发现已定内容、矛盾和需要修订的范围；它们不自动高于原始业务证据和有权人决定。修订仍输出到新的候选 `run-dir`，不覆盖既有项目文件。

## 整套方案一次送审接口

1. 先沿现有流程工具与方法取得客户分析A：业务流、整体架构图及graph，附baseline、来源与版本；再形成解决方案，包含问题及意义、目标与baseline、价值、产品设计、AI采用依据、信息流和客户体验流，关联范围报价。A记录客户现状，方案明确本期拟改变的工作方式。
2. 解决方案中的产品决定明确后，即以同版A、方案、来源和技术约束生成技术架构B。所有客户类别采用同一顺序；整套方案的总架构师审核位于B、独立开发计划和技术可行性评估形成之后。客户类别仍供投入与安排参考，不作为B生成的批准前提。
3. 运行下文内置推导方法：在已有working分析中登记产品要求与来源，沿产品的信息流和体验任务识别对象、角色、状态与决定权，形成BF→UC对应；01统一概念，02写用例和分支，03从这些用例的读写推导实体、字段、Link与状态，再展开04—09。A中的客户事实与方案中的拟议变化分别保留身份和来源，不把拟议产品写成既有现状。这些对应保存在已有working与九份正文中。
4. A或方案尚缺、产品含义互相冲突、存在会改变业务结果或权力边界的未定选择时，先集中澄清。已明确产品决定下的字段、API、页面和技术表达由本Skill推导为候选；未实测平台能力与AI贡献如实列为验证条件。不得凭空补造产品规则或平台事实。
5. 项目架构师提出技术可行性判断，FDE协作验证及编制独立计划，PM核对范围报价、版本和材料齐备性，将A、解决方案、范围报价、B、独立计划与技术可行性判断作为一套方案一次提交总架构师。计划与可行性判断可据B完善；缺少它们时可先生成B，但正式整套送审须补齐。
6. 审核同时覆盖商业可行性、技术可行性与整体一致性，对整套明确版本给出通过、退回或暂缓结论及范围、条件。Skill候选与机械回执保持待总架构师审核，不能替代本人批准。技术设计改变产品目标、业务规则、权限、范围或报价时，交项目架构师补齐或修订方案，再同步受影响的B与计划后整体重提。
7. 整体审核通过并落实启动与开工条件后才能实施。项目启动签字后的验收标准及清单版本固定；技术缺口或新增诉求按既有异常流程处理，不能靠重写签字范围、目标或标准取得一致。

AI环节沿方案中的具体采用判断展开。缺少工程方案对照、采用依据或贡献证据时，列为待澄清或待验证，交项目架构师处理；不得为填满模板而补造AI需求、验证结果或价值数字。

信息流沿业务节点提供最初输入、信息拆解、逐步处理、中间产出、传递条件及最终反馈。技术规格逐项承接到数据、逻辑与接口；输入来历、处理依据或输出去向尚未明确时，列出缺口并交项目架构师补齐，保留待确认状态。

体验流提供具体使用情境、产品入口、首屏信息、逐步操作与反馈、信息下沉及完成结果，作为页面、交互、数据与接口设计的依据。仅有功能名称或概括性流程时，列明缺失的产品判断并交项目架构师补齐。技术规格沿明确体验展开，不自行决定尚缺的产品交互。

整套方案版本与审核状态、客户分析A版本、差异和未验证条件写入已有working/分析及最终交接报告；B仍为现有九份spec，独立开发计划按项目现行模板编制。本Skill不新建第十份架构交付文件。机械渲染通过、问题数组清空或回执“待总架构师审核”均不能充当整体审核通过的证据。

## 固定平台边界

本包覆盖的全部候选架构以 Syngy Workbench React、Octopus 与 Arcubase 为固定平台边界；这一边界是本项目的已确认决定，应写进九份设计的相应位置。

调研转写中出现的 “Occupace” 或 “AQBase” 在本包内统一规范为 Arcubase；引用原始口述时可保留原词并在首次出现处标明该规范化。

1. Workbench 应用保留官方 React 脚手架和 `@syngy/workbench-auth`，由受信任的 Workbench 会话提供人类身份。候选架构不设计独立登录页、令牌仓或第二套认证链。
2. Octopus 承担 Host 能力及组织管理入口。项目需要用户、团队、组织目录、数字员工、会话、文件、Skill 或其他 Host 能力时，实施选择 `octopus` feature 与 `@syngy/octopus-client`；只读取已认证查看者的页面无需虚构额外 Host API。
3. 所有共享、持久、可查询的业务事实落在 Arcubase App 的原生表、字段和 Link 中。实施使用 `arcubase` feature 与生成的 typed ingress client；本地对象、静态样例及 `octopus.api` 的通用 Arcubase 代理不构成业务数据层。Taskboard 只在项目确有任务或项目工作流时选择。
4. 架构必须明确 Arcubase App 采用既有 App 还是新 App。既有 App 需要以实读的精确 App ID、schema 和稳定键为依据；新 App 先在九份设计中给出表、字段、Link 与访问模型，再在批准后的实施阶段创建。名称匹配、推测 ID 或静默创建都不能充当选择依据。
5. Octopus 提供 Arcubase 原生组织角色及成员关系的统一管理入口，Arcubase 原生角色和表规则承载有效业务授权。所有业务表引用同一组已核验角色；Host 管理员或团队成员资格、对象归属、负责人和审批人分别保留各自语义，不能直接互相替代。前端消费当前有效授权，数据入口也必须执行授权。涉及代理、后台代办或 `conversation_member` 的项目，还需在实施中取得真实调用者、执行身份和撤权的允许/拒绝证据后才能称为可用。

## 运行前提

1. 调用者提供显式 `run-dir`，并指定本次项目的方案文档与实际审核状态、客户分析A版本、调研输入、技术约束、相关材料或需要修订的既有设计。输入可完整、部分填写或尚为空白，按下条识别缺口。
2. 随包 `assets/通用调研输入文档.md` 是可携带的空白输入结构。项目运行时指定它的项目副本；副本中已有的材料与来源构成本项目输入权威。空白项、空白单元标记、不适用项和部分填写都可进入取源、分析与澄清；它们分别按未知、不适用或需要补充处理。设计关键问题未清零时阻断九份文件渲染；方案定义尚缺时交项目架构师补齐，客户分析A缺失时补前置客户业务流与整体架构graph，产品决定及设计输入按“整套方案一次送审接口”判定是否满足B生成条件。
3. 输入文档列出可访问的访谈转写、观察记录、真实样本、规则原件、现有系统或接口证据，以及每项的权威性和取得状态；并列出 Arcubase App 选择、既有 schema、组织角色/成员关系、现有 Workbench 应用及目标环境的已知证据。
4. 先按 [输入与证据](references/input-and-evidence.md) 获取并实际阅读必要来源。随包机械合同可用时，使用其 `acquire_sources` 形成运行快照；快照证明取源完成，不替代语义判断。
   在取源前把本次业务决定及其来源整理为 `input/decision-register.json`，作为 `kind: decision-register` 加入同一来源清单；格式与证据类型见[业务决定来源守卫](references/mechanical-contract.md#业务决定来源守卫)。至少逐项核对 App 既有／新建选择、角色对业务对象的操作权限、系统读写边界。把原件尚未回答的项记为 open；方案作者已明确的候选决定可记为 proposed，不要求总架构师预先批准。来源中的未知项不能由本次技术推导关闭。该记录只在运行输入区使用，不增加项目交付文档。
5. 当前候选只在显式 `run-dir` 内写入。因此属于 `artifact`。若有人要求直接改共享项目目录、调用平台写操作、排程或改变其他共享状态，停止并重新按 stateful 工作流设计恢复与授权边界。

输入或原件缺失时，说明缺少的具体文件、字段、样本或接口证据。可以保留 `working/` 候选分析，不能用模型常识补成项目事实。

## 确定性辅助段

执行段：acquire_sources  
动作：读取 `input/source_manifest.json` 中声明的只读资料，逐项落盘原始字节快照、来源快照和取源回执。  
副作用：run_dir_only  
可达接口：`python3 scripts/run_meta_stages.py --stage acquire_sources --run-dir "$RUN_DIR"`  
依据：`references/mechanical-contract.md §input/source_manifest.json` 与 `§acquire_sources receipt`。  
产出：`working/sources/`、`working/source_snapshot.json`、`acquire_sources_receipt.json`。  
值域：来源清单符合 1.0 结构且每项资料可读时，回执逐项记录来源标识、取数时刻、路径与内容哈希、字节数和快照位置；清单或资料不合格时停止本段。  
断言：source receipt（T1）+ schema conformance（T1）+ count/hash 与实际文件重读（T1）。

执行段：render_documents  
动作：读取 `working/render_request.json` 的业务内容槽位，在设计关键问题清零且本版预览内容复核记录齐备后，从原参照生成固定标题、表头、分隔行、列表编号及标签，核对结构后写出精确九份候选 Markdown 和回执。  
副作用：run_dir_only  
可达接口：`python3 scripts/run_meta_stages.py --stage render_documents --run-dir "$RUN_DIR"`  
依据：`references/mechanical-contract.md §working/render_request.json` 与 `§render_documents receipt`。  
产出：`design/` 下九份指定文件、`render_input_receipt.json`、`render_documents_receipt.json`；问题未清零时只产出 `working/render_blocked.json`。  
值域：`unresolved_questions` 为空、冻结业务决定无 open 且来源有效、内容槽位符合 2.0 契约、结构检查通过且内容复核声明与当前请求、来源和预览字节匹配时，脚本固定排版并保留填写内容，回执固定为待总架构师审核；数组非空或业务决定缺失／开放时不创建或改写 `design/`，复核缺失或失效时停止写出。  
断言：source receipt（T1）+ schema conformance（T1）+ count/hash（T1）+ artifact hash（T1）+ row/column/sheet reconciliation（T1）+ summary reconciliation（T1）+ output field coverage（T1）。

## 先理解业务，再形成设计

按 [审核前业务流与系统架构分析](references/pre-review-analysis.md) 处理材料：

先按该文件第 1 节，在已有 `working/` 分析中逐条保留来源的明确要求及限定条件，指定各条在九份文件中的承载位置。每项独立的允许、禁止、例外、数量、时限和关系分别登记；出现“各、所有、分别、每次、同时”等词时，按实际适用的对象、事件和所需事实展开，不能压缩为一条概括要求。带着这份要求登记执行下面的分析与写作。

1. 锁定交付对象、业务目标、成功/失败条件、使用者和决定权；每项都带来源锚点。
2. 还原从触发到结果的时间顺序，分开事实、推断、异常、等待、人工裁决与并行。
3. 区分执行段与判断段。执行段写动作、依据、入口、产出和失败处置；判断段写证据、整合、候选、标准、分支去向。
4. 沿流程划出人、既有系统、新建 Workbench 应用、潜在数字员工、潜在 Skill 与数据权威位置的职责边界；分别说明数据怎样产生、传递与保存，以及业务信息怎样汇总支持决策、决策怎样到达执行者。记录调用、数据流、信息流、身份与恢复约束。
5. 为每个 `BF-xx` 标出 Workbench 入口、所需的 Octopus 能力、Arcubase 表/字段/Link 和角色规则、是否确有 Taskboard 需求，以及外部交接。没有实读证据的 App ID、字段类型、Link payload、调用者映射或平台能力保留为核验项。
6. 使用 Meta Orchestrator Step 0—3 的画时序、判别、切段和交接分析方法，使用 Meta Skill 的目标、段落、判据与补料方法。此处不生成 `topology.json`、网络 ABI、最终 Skill 包或运行测试声明。

分析产物只服务于本次候选设计。持续维护来源编号、流程段编号、对象和用例编号，使九份文件可以互相引用。

## 澄清循环

发现下列任一情况时，立刻读取 [澄清与决定循环](references/clarification-and-decision-loop.md) 并向人集中提问：范围或成功条件、角色或决定权、流程及异常终点、数据权威和状态变化、权限、既有能力或接口、Arcubase App 的既有/新建选择、业务角色和对象授权、对外动作与失败接手、验收、技术或部署约束。

一次只合并同一决定主题的问题。每个问题簇说明已知证据、需要作出的决定、可选项或需补材料、影响的流程段与九份文件，以及最短可回答方式。收到回答后记录决定来源和决定人，更新所有受影响的分析与候选正文；回答没有解决的部分继续保留为问题。

`working/render_request.json` 中存在任何设计关键 `unresolved_questions` 时，不得请求渲染最终九份文件。外部能力尚未实测、上线前验证或总架构师审核条件可作为限制写入相关文档；它们不能掩盖尚未回答的设计问题。

问题清单须覆盖冻结决定记录中所有 open 项，保留相同编号。清空请求数组不会解除来源守卫。获得回答时保留回答原文、作出决定者及其依据，在新候选运行目录重取来源与决定记录；不得改旧快照、把模拟资料改标为项目事实，或只重签哈希。方案明确新 App 后，表、字段与 Link 由技术设计推导；无需逐字段请人确认。

## 方案推导与提问边界

基于已确认的业务目标、流程、对象、权限和约束，主动提出可审阅的 Arcubase 表/字段/Link、API 形状、Workbench 页面结构、Octopus/Arcubase 系统分工、技术路线和实施顺序，并说明它们如何满足已知依据。这样的内容是待总架构师审核的设计推导，不能伪装为客户既有事实。

同一业务含义下的命名、字段内容、页面呈现和 API 表达可由 Skill 在固定文档结构内写清，不要求人逐个决定。章节层级、顺序、固定标题、表头和表达形式按九份原参照及写作规则执行；只展开有项目依据的角色、端、表、场景和能力分组。只有选择会改变业务范围或结果、决定权、数据权威或状态、权限、对外副作用、既有系统接入、合规、验收、成本/周期承诺或运行责任时，才把备选方案和影响集中交人确认。技术能力未知时先确认约束或实际能力，不能把一个未核实的候选当作既成事实。

## 起草九份文件

读取 [九份文件写作](references/nine-document-authoring.md)，并在每份正文起草前完整读取 `references/design/` 中同编号的原参照。保留原参照文件，生成件采用其标题层级、章节顺序、固定表头、关系/路由/目录树、用例表及阶段标签。仅按写作规则替换项目名词、展开重复单元并适配平台内容；不合并章节、不把逐表小节提升为总章节、不增删或合并字段列。生成件的编号和交叉引用采用当前九件文件名。案例中的 Ticket、特定语言、缓存、部署、路由、身份系统和业务规则不能复制到新项目。

逐份读取参照；读取结果截断时，分段补读到文件末尾再起草，在已有 `working/` 分析中记录读取范围。只得到标题、摘要或被截断的合并输出时，先补读对应原文。

填写每份内容前，先取出要求登记中由本文件承载的条目；把每项已确认要求写进原参照的现有槽位，再展开实现该要求的设计。完成后在登记中回填实际章节和正文短句。任何已确认条目没有正文落点、只有概括来源引用，或被无依据地收紧/放宽时，先修订对应内容；未知的设计关键条目进入澄清。

渲染前逐项对照参照检查正文。`03-data-model.md` 保留“表、每表字段、Link、业务流”四项；字段分别写展示 `label`、稳定 `key`、原生类型代码、必填、唯一、默认值模式/值及按需 options。已知类型的 options 列按 [九份文件写作](references/nine-document-authoring.md) 填可解析 JSON；新建 `select` 的稳定整数 item key 由设计规划，与平台生成 field ID 分别处理。用 `text`、`textarea`、`datetime` 等已知代码表达类型；表名或应用内模块名不能冒充平台自带的表级 stable key。Link 写清源字段、目标表及 ID 取得方式、单选/多选和关系所支持的流程；业务时间按已知契约写 epoch seconds 与首次回读要求。实际资源 ID 和目标环境行为可留待实施核验，随包已知的 schema 结构必须写进设计。遗漏这些内容时补齐正文后再渲染。

先检查九份内容的对象、角色、状态、权限、入口、契约和依赖是否一致，并按最终用例编号同步 `working/` 分析中的交叉映射。按写作规则的参数来源检查逐项区分受信身份、授权业务输入、人工判断和系统结果；04/06/07 的每一条禁止项都须与实际允许输入对照。03 每个字段的可读/可写列须从原始权限事实逐行核对，不能用表级或页面级总述覆盖相反的字段权限。对每个写入操作，逐项给出未知结果的定位依据、成功/未执行/仍未知的证据和重试条件；创建尚未取得记录 ID 且只能查到非唯一业务字段时，查到相似记录不能证明本次创建成功，零匹配、多匹配或无法归因均保持未知，停止重试并交人工核对。不得为此偷偷改变已确认的业务唯一性、增加必填业务编号或假定平台幂等能力。设计关键问题清零后，按随包机械合同准备 2.0 版 `working/render_request.json`，先完成下面的预览与内容复核，再调用最终 `render_documents`。

用 JSON 序列化工具填写内容请求。表格只填按原表头顺序排列的单元格数组；单元格保留原始字符，脚本处理管道符、换行及 HTML 字符的转义。数据列数不符时按错误给出的文件、章节、表号、行号核对输入内容，不能自动补删。不要手写或修补最终 Markdown 的固定结构。已有渲染回执时使用新的候选运行目录，保留原稿和原检查记录。

每个写入用例还要正向走通全部实际写入字段，包括入口派生的身份、时间、状态、关联和跨表结果。分别明确人能提交什么、哪个受信入口派生什么、以哪个获权主体写入哪些字段；派生写入同样需要与 03/04 的授权相容。不能把“人不能自由编辑”写成“合法流程也无法写入”，或用泛称“服务端写入”填补未声明的权限。逐条核对原始材料的其余已确认约束在九份正文中的落点，尤其保留期限、到期处理、自动化边界和禁止动作；只在 working 中记下或引用整段来源，不能代替写进相应正文。

来源要求每次写入具有稳定操作标识时，核查、补偿和恢复等独立提交也须遵循该要求。分别表达本次请求的标识和所操作的既有对象或原操作标识，并在03/04/07写清持久关联、允许输入及重复提交行为；同一次逻辑请求的内部派生写入共用该请求关联，避免把每次内部落盘递归扩成新业务操作。

## 先预览和复核，再生成最终候选

**动作：** 设计关键问题清零后，执行 `python3 scripts/run_meta_stages.py --stage render_documents --preview --run-dir "$RUN_DIR"`。**副作用：** run_dir_only。**依据：** `references/mechanical-contract.md §工作区预览`。**产出：** `working/previews/` 本版请求哈希目录中的九份预览和预览回执。**值域：** 使用最终编排器检查通过时返回 rc0，标记为内容尚未复核；问题未清零返回 rc3，输入或路径不合格返回 rc2。同版重试保留原字节，修改内容请求后生成新目录。

完整读取九份预览，同时逐段回到原始来源快照复核要求登记，不能仅从自己写出的设计反推“已覆盖”。对量词展开后的每个适用对象和事件，分别核对所需事实是否落在 03 的具体表与 field key、04 的写入授权、07 的写入与回读、09 的验证位置。逐项记录原文位置、实际预览文件行号或短句和结论，保存到已有 `working/` 分析。使用已确认的平台原生元数据时写出其名称、保留语义和证据；“创建审计字段”“平台会记录”等泛称不足以承载明确的持久事实。

复核时先从原件独立判断每个业务决定的实际状态，再与冻结记录和正文比较：摘录是否支持该 statement，记录的 owner 是否有相应决定依据，原件仍待定的内容是否被写成 defined/proposed，模拟规则是否越过适用范围，候选是否被写成既成平台事实。发现任一项即退回来源／澄清，不填完成声明。机械守卫只核对登记覆盖、显式状态、来源类型与字节，无法判定自然语言蕴含或实际决定权。

检查出遗漏、矛盾或无依据的限制时，修正 `working/render_request.json` 的对应内容槽，重新预览并复核。已确认语义可以推导的字段由本 Skill 补齐；需要有权人决定的业务问题返回澄清。所有已确认要求有正文落点且跨文件一致后，按 [机械合同的内容复核声明](references/mechanical-contract.md#workingcontent_review_proofjson) 填写 `working/content_review_proof.json`：绑定实际请求、预览、来源快照和本次复核记录的哈希，并把来源要求持久保存且采用业务字段承载的每个事实列入 `field_checks`。此文件由实际复核者填写，随包工程夹具的声明不能用于项目内容复核。

完成本版内容复核后调用前述 `render_documents` 执行段。脚本重编译并核对复核声明的新鲜性、预览全部字节和已声明字段的存在，符合后才写九份最终文件及回执。脚本无法证明要求登记完整或业务语义正确；复核者仍对上述逐项检查负责，候选状态保持待总架构师审核。

内容检查失败时按定位修正对应槽位；项目绑定中的编号错误按 02 实际用例清单纠正并同步分析。原参照指纹变化、编排后结构错误或独立回读不一致时停止并保留证据，不修改参照、校验器或最终 Markdown 来绕过。同一确定性错误连续两次失败时报告断点。输出后运行全量审核：`render.structure` 独立核对原参照结构，`render.content` 独立核对填写内容与落盘正文，`render.native_fields` 从实际 03 文件检查已知类型选项。再把预览复核的落点与实际最终正文对应核对。发现新遗漏或矛盾时保留当前候选，使用新候选目录修订并重验；已知内容缺陷尚未解决时，报告缺项及修订或暂缓入口，不能提交成功候选或请求批准进入开发。

## 结束与报告

先说明实际完成范围、方案版本及审核状态、客户分析A版本、当前应处理的审核或缺口、建议下一步及可直接回复的选项。技术证据放在末尾，不能只给路径或回执。根据本轮实际状态选择下列分支。

### 输入或设计关键问题需澄清

说明九份最终候选尚未生成、已读材料和停在哪个缺口；在报告正文集中列出需要有权人回答的问题、已知依据、影响和最短回复。方案或A尚缺时，分别列明缺少的产品定义或前置客户分析，请项目架构师补齐对应内容及状态。答复齐备后更新分析，纠正来源后重查受影响部分；回复“暂缓”则保留材料与问题并停止推进。证据不足以推荐业务选择时明确交有权人决定。

### 整套方案候选与送审接续

说明A、解决方案的明确版本，B九份文件的实际生成位置及来源到概念、用例、数据和后续规格的对应；说明独立开发计划与项目架构师技术可行性判断的取得状态。缺少计划或判断时列明补件，B生成成功仅表示技术候选形成。

材料齐备时建议PM把A、解决方案、范围报价、B、独立计划与技术可行性判断在一封邮件一次送审，请总架构师同时判断商业可行性、技术可行性及整体一致性。列出未确认、待验证和附带条件，以及其对范围和实施的影响。

可回复“整套方案审核通过，按此版本与条件执行：……”后核对本人批准、具体版本、范围、条件及开工安排；回复“退回，修改：……”则修订受影响材料并核对整套一致性后重新提交；回复“暂缓”则保留候选并停止。商业或技术部分尚未通过时，保持待审或退回状态。没有实际批准记录时，不把候选标为获批。

### 方案差异或启动签字后问题

说明差异及其来源、影响的方案和技术文件。涉及问题、产品、目标、规则、权限、范围或报价时，交项目架构师处理，同步受影响技术文件及计划，由PM重新提交整套明确版本。启动签字后保持已签版本，转项目既有异常处理；不把模型建议当成客户同意或批准。可回复“补充依据：……”或“暂缓”。

所有分支说明本次未执行开发、平台资源创建或安装发布。若候选存在未解决内容缺陷，不请求批准进入开发。机械检查、内容复核、项目架构师的判断和总架构师批准分别说明，不相互代替。

整套方案审核通过后，实施人员按批准版本、审核条件及项目开工条件进入既有流程。退回或实施发现设计问题时，按上列分支回到受影响的来源、澄清或候选九份文件，保留原版并使用新的运行目录。
