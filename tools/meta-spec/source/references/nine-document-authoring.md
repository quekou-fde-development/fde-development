# 九份开发设计文件写作

## 使用原则

`design/` 下九份原参照提供固定文档结构。保留原文件字节，生成件只替换本项目事实、明确的项目名称槽和重复单元；生成件的编号与引用采用当前九件文件名。保留原表头、标题层级和顺序、列表、场景步骤、树形代码块及阶段内标签。平台和业务内容以本项目依据填写，不继承 Ticket、Go、Redis、Kubernetes、认证、路由、API 或部署答案。

只写这九份设计文件；业务流和系统架构分析在运行材料中完成，再由各文件引用相关 `BF-xx`、对象、用例和决定编号。

## 固定结构与项目变量

先在已有 `working/` 分析中确定 02 的完整用例清单（角色、唯一 UC 编号、正式用例名）及 BF→UC 对应关系，再在 `working/structure-bindings.json` 中记录以下对象。它属于本次运行分析，不增加第十份交付物。名称与排序先取已确认输入中的首次出现顺序；需要设计推导时引用已有 BF/UC 分析，定稿后在九份中统一复用。同一项目修订沿用既定绑定；发现编号记录错误时按实际用例表纠正绑定、正文及分析，并保留纠正记录，不能通过改变固定结构绕过检查。

- `project`：本项目名称。
- `special_topic`：01 的业务专项规则名称，替换原例“券码 Meta 与标签”的位置，例如本项目的状态及不可变规则；始终保留该位置。没有额外专项时填写“业务专项约束”，正文说明不适用及依据。
- `roles`：实际具有业务用例的角色名称数组；平台运维身份只有承担项目业务用例才列入。
- `surfaces`：实际应用入口/工作台名称数组。同一 Workbench 中按权限显示不同页面时只记一个端，不拆出多套门户；名称在 01、05、06 中统一。
- `api_groups`：实际调用契约的能力/消费者分组名称数组。保持输入或分析中的顺序；只列有依据的分组。
- `tables`：实际业务表名称数组。
- `scenarios`：用例关键场景名称数组。
- `flows`：业务流小节完整名称数组，每项写成 `BF-编号 / UC-编号 正式用例名`；编号与完整用例名必须成对复用 02 用例表。一个业务流涉及多个用例时，逐一列出其 UC 编号和完整用例名；不得按 BF 的顺序臆配 UC 编号。
- `sources`：以上八个键各自对应一个非空来源/设计推导锚点字符串。

执行 `python3 scripts/document_structure.py --bindings "$RUN_DIR/working/structure-bindings.json" --document 03-data-model.md` 可查看指定文件的预期标题、表头、必要表达形式和原参照行号；省略 `--document` 查看全部。脚本从原参照取结构，不提供项目正文。将此 JSON 对象原样放入 `working/render_request.json` 的 `structure_bindings`。

首次准备内容请求时执行 `python3 scripts/document_content.py --bindings "$RUN_DIR/working/structure-bindings.json" > "$RUN_DIR/working/render_request.json"`，副作用仅为本次运行的草稿文件。已填写的请求保留，勿重新生成覆盖。生成的每个章节对象只填写 `text` 及该节已有的 `tables`、`items`、`tree`、`steps` 或 `labels`；槽位详见 [机械输入与落盘契约](mechanical-contract.md)。程序按原参照决定顺序和固定格式，AI 填写业务含义与数据行。不要把完整 Markdown 字符串作为渲染输入。

逐份按下列边界写作：

1. 01 保留五个二级位置：概念、角色边界、业务专项规则、结构关系树、单一路径约束。角色表固定三列；业务专项只替换标题名；关系树用 `text` 代码块。
2. 02 保留“范围与假设 → 按 roles 顺序重复的角色用例段 → 关键场景”。每个角色用例段固定 `编号 / 用例 / 主流程 / 验收` 四列；场景为三级标题及编号步骤。角色和场景数量由项目绑定确定。
3. 03 保留原参照四个编号二级章节。每张表放在第二章的三级标题中，固定八列表清单、十一列字段表、九列 Link 表；不得合并或省略列。每条业务流放在第四章的三级标题中，按原参照四个编号步骤和粗体标签写。本版统一省略原参照标为“必要时”的补充六列表，把相同信息写在四步流程内。
4. 04 保留原参照九个二级章节及原三级章节，最后的引用范围更新为 01~09。技术机制按 Workbench/Octopus/Arcubase 填写；不适用的固定节保留并写明原因和依据。
5. 05 保留“角色边界表 → 通用路由约束 → 按 surfaces 顺序重复的端 → 禁止项”。每个实际端沿用原租户管理端的“text 路由树 + 菜单/页面/路由/说明四列表”单元；表头“域名”可填写宿主入口及实施取证条件，不能编造新域名。
6. 06 保留“通用交互规范 → 同一 surfaces 顺序的逐端页面项目符号列表 → 禁止项”。逐页用列表写，不额外升格为章节。
7. 07 保留“API 分组四列表 → 通用响应 → 按 api_groups 顺序重复的能力/API 三列表 → 禁止项”，章节编号连续。表头仍用 `Method / Path / 说明`；原生 SDK 场景在单元格写调用操作、typed client/ingress 入口及取证条件，不能由列名推断自建 HTTP API。输入、输出、授权、错误、回读等细节写在说明及同节正文中。
8. 08 保留五个二级位置及 1.1/1.2/1.3 技术分层，目录为 `text` 树。固定标题去掉原例的 Monorepo 与 16xxx 建议；内容按官方 Workbench 和平台约束填写。
9. 09 保留总原则、A/B/C/D 四阶段、里程碑和变更控制的顺序，以及原阶段内“目标、执行、输出物、完成门槛”等标签。阶段 A 的后端内容写 Arcubase 数据与权限，B 写 typed client，C 写 Workbench，D 写平台和业务验收。

段内固定标签仅限 09 明列的阶段标签，以及 03 的四个业务流步骤标签。原参照中的案例域名、租户名、权限断言和“必要时补充”等写作提示都按项目含义处理，不作为必须复制的正文标签。

只填项目内容、行数和明确绑定的重复单元。不得增加任意 H2/H3、改写固定标题、改动表头或新增替代性表格。信息应放入已有的合适章节、说明单元格或正文。结构检查不代替项目事实、平台语义和跨文档一致性审核。

## 固定平台落点

九份文件共同采用 Workbench、Octopus 与 Arcubase。将该已确认平台边界写成项目设计，不将它混同为调研得出的业务事实：

- Workbench React 与 `@syngy/workbench-auth` 提供应用壳、会话和页面入口；项目没有独立登录、令牌存储或替代认证链。
- Host 用户、团队、组织目录、数字员工、会话、文件或 Skill 等能力按用例选择 `octopus` feature 和 `@syngy/octopus-client`。Taskboard 只在用例含任务或项目工作流时采用。
- 所有共享、持久、可查询的业务记录使用 Arcubase App 的原生表、字段和 `linkto` 关系，通过 `arcubase` feature 与生成的 typed ingress client 读写。页面样例、静态对象及 `octopus.api` 的通用 Arcubase 代理没有业务数据权威。
- 每份涉及存储的文档都说明 Arcubase App 采用既有还是新建：既有 App 写实读 App ID、schema 与稳定 key 的来源；新 App 写待批准的 schema 和访问模型。未实读的 ID 留空并列为实施前取证，不能由名称推断。
- 角色成员关系由 Octopus 的官方 Arcubase organization role 管理入口维护，Arcubase 原生 actor 和表 access rule 形成有效授权。业务对象的归属、负责人和审批人留在业务表；Host 团队资格不自动授予业务权限。

## 各文件的最低内容

### 01 概念

让同一对象在其他八份文件中有同一含义。必要时给短术语表、角色边界、关系树或约束清单。每个名词说明范围、唯一标识或权威位置；可自行统一同义命名，概念范围或权威位置尚不明确时回到澄清。

### 02 用例

按用户、系统或人工角色列出真实目标。每个用例关联 `UC-xx` 和 `BF-xx`，写触发、前提、输入、主流程、成功可检查结果、异常或拒绝、权限与验收。选择少量真实关键场景串联，不以页面清单代替业务用例。

### 03 数据建模

从用例和真实记录出发，先明确一行代表什么。共享持久事实写为 Arcubase 原生表和字段，关联写为 `linkto`；用简洁的实体说明和关系/状态图或表表达稳定 key、必要字段、值域或计算规则、关系基数、历史/重复、状态转换、来源、权威位置、写入者和读取者。字段名和内部结构可由已确认的业务语义推导；会改变业务含义、数据权威或权限的字段与状态先澄清。App、表 ID、field ID 和具体 schema payload 只取自目标环境读回、当前 CLI 帮助或批准后的建表回读，不能伪造。

`text`、`textarea`、`datetime`、`select` 的字段表“类型专属 options 与证据”单元格填写 **FieldVO.options 本身的 JSON 对象**；来源说明放在同一行“已确认约束”单元格。示例仅表示已有原生形状：text 用 `{"type":"text"}`；普通 textarea 用 `{"html":false,"size":6}`；需要时刻的 datetime 用 `{"type":"datetime"}`。select 用 `{"options":{"mode":"custom","items":[{"key":1,"value":"已确认选项一"},{"key":2,"value":"已确认选项二"}]}}`，将其中选项替换为项目已经确认的实际值。按原参照要求，旧字段保留实读 item key，新字段按选项顺序规划唯一整数 item key；真正的平台 App / entity / field / actor ID 才保留到实读或建表回读。程序拒绝缺项、字符串 key、重复 item key 和把已知 options 延后处理的内容。

### 04 安全与隐私

从角色、对象、动作和数据范围展开权限。Octopus 的官方接口维护 Arcubase organization actor 成员关系；Arcubase 表规则引用这些 actor，实施时以当前真实 role/actor 映射为准。写清哪些业务角色可 `view`、`add`、`edit`、`delete`，哪些字段需受限，谁能维护角色以及对象归属如何参与后端判定。Arcubase 字段规则实施时以 `:<field_id>` 为键，不能以展示 key 代替；同一 rule 的多项 scope 是 OR，多个 ingress 的合并语义仍需实测。前端只消费当前有效授权，数据入口执行同样的限制。涉及外部调用时写身份、最小暴露、幂等、重复/未知结果、拒权和失败处置。人类调用者映射与撤权列出允许/拒绝验收条件；项目涉及数字员工代办或 `conversation_member` 时，再列出发起和执行身份的验收条件。

### 05 站点架构

沿用例安排 Workbench 入口、菜单、路由、工作台、员工会话、审批或外部系统交接。每个页面或入口关联角色、用例、Arcubase 对象和权限；需要 Octopus client 的 Host 能力明确列出，只有认证查看者的页面不虚构调用。页面清单之外的能力不得被描述为可达；整体模块职责、数据流引用分析所得结论。Host 管理屏与业务数据屏分别标明其角色管理或 Arcubase 数据职责。

### 06 页面布局

逐页写主任务、信息层级、字段及其数据来源、主要操作、状态与权限。可按已确认任务推导清晰的页面和交互结构；品牌、无障碍、设备或视觉参考已有约束时遵从，缺失时把不影响业务结果的呈现作为设计选择。原型和演示数据不能充当真实后端或验收依据。

### 07 API

只为已经确认的页面、员工、Skill、既有系统或人工交接定义调用入口。每项明确提供方和调用方、输入输出、授权、错误语义、分页/批量、幂等、超时、结果回读和版本或迁移影响。Arcubase 业务读写走生成的 typed ingress client；Octopus Host 调用从当前 `@syngy/octopus-client` 类型确定。既有接口引用实际契约；新接口可从确认的用例、数据和权限推导责任模块与契约形状。接口名称和字段表达由 Skill 统一；接入方式、外部能力、权限或副作用未确认时进入澄清。

### 08 技术栈与目录

技术选择服从用例、数据、安全、接口和部署约束。使用官方 Workbench React 脚手架，保留 `@syngy/workbench-auth`；按已确认用例选择 `octopus`、`arcubase` 和按需 `taskboard` feature。既有应用先写明实读的 `package.json`、锁文件、`src/lib/syngy.ts` 与保留范围；新应用再写明所需 feature、Arcubase App 选择、schema、访问模型及生成 typed client 的位置。可基于这些约束提出目录和工具分工，并说明理由；会改变成本、周期、合规、外部接入、运行责任或客户承诺的选择集中提问。列出采用、复用和新增的理由，以及实读版本、代码和文档目录、环境、依赖/锁文件、生成物、部署目标和运行责任。没有项目依据时保留候选方案及待确认点，不沿用案例技术栈。

### 09 实施与验证路线

以用例为主线拆任务，说明输入、产物、前置依赖、负责人、完成条件、风险与验证。先安排既有/新 Arcubase App 的明确选择，再安排 schema 与 access rule、typed client、Workbench 页面和必要的 Octopus 能力；应用权限变更时先读取完整角色成员关系，保留无关角色，再以单 App `bulk-apply` 的 `dry_run` 和实际回读验证表规则。优先安排一条含真实人类会话、Arcubase 数据、业务动作、保存和回读的完整链路；共享数据、权限和契约明确后再安排并行。联调包含已知允许与拒绝主体、角色调整、撤权和直接数据入口；项目涉及数字员工代办或 `conversation_member` 时，再验证代办的发起/执行身份。写上线条件和恢复准备，但不声称这些测试已经完成。

## 交叉检查

提交渲染前检查：术语和对象在九份中一致；每项用例有数据、权限、入口、契约和验收去向；状态转换不冲突；技术选择支持而不覆盖业务边界；路线图未绕过依赖；所有设计关键问题已经清零。检查失败时回到材料、分析或澄清，不用额外模板掩盖缺口。

在已有 `working/` 分析中按每个写入用例列出参数名、来源、谁可提交、服务端验证和落盘字段，并据此逐句核对 04/06/07 的允许项与禁止项：

- **受信身份与授权**：当前调用者、实际执行者、核查人和有效角色由受信会话或平台取得；客户端不能通过请求字段覆盖它们。
- **可选择的业务对象**：用例允许操作者选择的成员、负责人、样品或其他目标对象属于业务参数。前端可提交选择值，数据入口验证该对象真实存在、处于允许范围及操作者有相应权限；不要把被选对象误写成调用者身份并禁止传入。创建时可选择的负责人/归属字段与“该用户有权访问这个对象”的鉴权结果分别表达：前者按用例接收，后者由数据入口判定。禁止项不得笼统禁止“对象归属”或“任务归属”而同时要求人选定负责人。
- **人工证据与判断**：输入授权人提交的核查证据、意见或结论，应保留其角色、值域和对应持久字段。当前会话派生提交人，数据入口验证权限与状态，再按已确认规则接受；不要用“禁止客户端传入结果”覆盖这个人工判断入口。
- **系统权威结果**：自动执行是否成功、实际落盘状态、占用或授权结果由受信执行与回读得出。人工核查结论需要影响结果摘要时，明确触发者、证据、校验与更新规则，保留两者的字段和责任。

对每个禁止句做反例检查：把该句逐一应用到 02 中已允许的真实输入，若会拒绝合法用例，则收窄禁止项到具体的受信字段或伪造行为。检查记录引用 03 的字段及 04/07 的对应段；没有冲突的依据写在已有分析中，不能仅记“已检查”。

逐句检查须覆盖 **04 全文、06 的通用规范与禁止项、07 全文**。身份保护明确写“由受信会话取得的当前调用者/实际执行者身份”，或列出具体受信字段；用例中可选择的业务成员、负责人和对象分别列为授权输入。不要写笼统的“客户端不得填写某业务角色身份”，再依赖另一章的允许句解释例外。对每个禁止句，在已有分析中记录原句位置、一个已允许用例的实际输入、该输入为何仍可提交。单纯检索出两个相同词不算完成语义核对。

写 03 的“可读 / 可写角色”列前，先在已有分析中按来源逐项列出角色、表、记录范围、允许读取的字段集合、允许动作与可写字段。若来源限定某个关联对象只能暴露少数字段，使用这些字段的**明确白名单**：逐项确认需要显示的字段含该角色，并逐项确认其余字段不含该角色。再逐行核对 03 的实际权限单元格，检查 04、06、07 的读取范围是否一致。已有角色总述正确不代表字段单元格正确；字段名字相邻也不能复制同一权限。记录实际字段 key 和通过/需修订依据，不新增第十份设计文件。

对每个写入用例，从允许的触发角色出发，列出该次操作涉及的全部表字段及其创建、更新或状态转换条件，再逐项验证写入授权：

- 将页面可编辑输入、受信入口派生字段、实际执行主体分开。一次合法提交派生的关联、初始状态或另一张表记录同样必须有获权写入路径，不能只核对表单输入字段。
- 在 03 的相应字段行说明哪些角色可读、谁在何种动作/状态下可写。创建后不可变的标识和 Link、受限状态转换、核查后才可更新的结果都写明相应条件；可在同一行的“已确认约束”列表达或精确引用已有流程条件，避免把“可写”留成可任意编辑的歧义。
- 人不能直接填写某派生字段时，写明该字段由哪个受信入口、基于哪个合法触发动作和已核验对象派生写入，以及输入越权或状态不合时如何拒绝。若沿用调用者身份，03/04 须容许这次受限写入；若确需不同执行身份，须有来源或明确设计依据，并列出授权与平台能力的实施验证，不能静默借用管理员权限、新增后台服务或默认提权。
- 读取权限与写入权限分别完整表达。为人标注“只读”时，仍要明确合法业务流程中的派生写入边界；该写入不授予随意创建、改关联、改状态或关闭记录的能力。字段行、04 授权、07 调用契约和09允许/拒绝验收必须指向同一套条件。
- “仅创建时可写”“创建后不可变”等条件必须有本项目来源依据。来源允许编辑纠正时，逐字段核对业务输入和 Link 的编辑范围；不能从参照案例或关联字段类型推导不可修改。已明确允许的字段须同时进入03字段权限和关系变更、06编辑表单、07更新输入。真正未定且影响业务的选择交人决定。

逐条使用 [审核前分析第 1 节](pre-review-analysis.md#1-锁定结果与边界) 已建立的原始要求登记核对正文，不在末尾重新凭记忆概括来源。按原文短句、负责章节、实际正文逐项比较；角色可兼任或互斥关系、多重授权及撤权规则、保留期限、到期处理、规模和运行责任同样需要落点。分别列出两种角色权限不足以表达来源给定的兼任规则；保留期限也不能替代到期处理决定。未覆盖条目先补对应槽位，再渲染；渲染后以实际文件行号回查。来源没有提出的限制不补写，九份原参照的章节与表头保持不变。

在已有 working 分析中逐项核对 02 的写入动作及输入要求留存的记录：03 必须给出相应持久字段或已确认的平台原生记录能力，包含来源要求的执行人、发生时间、状态变化以及结果未知时所用的持久定位信息。按来源覆盖的每个对象和适用事件分别核对；创建、提交、关闭和作废的事实不能互相代替，也不能用“审计字段”等泛称代替 field key。04/07 承诺留存、审计或恢复的信息均回指 03 的具体表字段；缺口由已确认业务语义补齐，不能只写“实施时验证”后略去设计。实际平台是否支持所设计的唯一性、条件写入或恢复原语仍列实施验证，未验证时保留阻断条件。

对每个创建、更新和跨表写入用例，在已有分析中分别核对结果未知时的记录定位和归因证据，并把可执行分支写入 03/04/07，页面状态和验收同步写入 06/09：

- 已取得记录 ID 时按该 ID 回读；判定该次操作是否生效还需核对操作相关事实。已有来源要求稳定操作标识时，设计保留其持久字段和回读关系。
- 创建超时且尚未取得记录 ID 时，只能采用已经核验的请求关联/平台回执，或已确认唯一且能归属于本次写入的证据。项目允许重复的姓名、时间、内容等字段仅作查找线索；即使只有一个匹配，也不能仅据相同内容认定属于本次请求。
- 零匹配、多匹配、可见性不足、回读超时或无法归因时，保持“结果未知”，停止自动及盲目人工重试、停止依赖本次成功的后续写入，由授权人核对。只有证据明确成功或明确未执行时才进入相应分支；“暂时查不到”不等于“未执行”。若证据仍不足，保留未知，不通过再次提交求证。
- 未知结果的核对沿已有权限和来源要求处理，不擅自引入业务唯一编号、额外必填字段、额外业务表或未确认的平台幂等/事务承诺。平台能力待验证时列上线阻断项，同时给出上述安全停止路径。

分析记录写明每个实际写入用例采用的定位依据、三种结果的判据、重试门槛及对应正文位置，不能只写“超时后查询”。

来源若要求每次写入有稳定操作标识，逐一覆盖独立的人类或系统提交，包括核查、补偿、恢复和更正。本次请求的标识与其目标记录、被核查原操作的标识分别命名并持久关联；重复提交本次请求时复用本次标识，不能把原操作标识同时当作另一种操作意图的唯一请求标识。03给出两者的字段或已确认平台凭据，04允许必要参数并保护受信身份，07写清两者如何传入或可靠派生、留存和回读。每次独立提交保留来源要求的发起人、时间、对象和结果；同一次提交内部的派生写入与审计更新沿用该请求关联，不递归制造独立请求。只在来源要求的范围内落实这些约束，不据此增加业务表、业务编号或假定平台幂等能力。

07 中自行命名的复合业务动作明确标作“应用层候选语义操作”；分别写其待绑定的真实 generated client/ingress 方法。未经实读的业务动作名称不得标成已存在的 SDK 方法。

检查清单和验收条目统一写明它们是待实施验证的条件。未实际执行的资源创建、权限测试、撤权、并发或回读不得写成“已完成”“已经验证”等事实；原参照中的完成态示例须转换为本项目当前状态。候选正文、检查清单、路线图和面向人的报告保持同一状态。

逐份对照已经完整读取的同编号参照。03 必须能直接找到四项：表清单、每表原生字段、Link、业务流；字段至少明确 label、key、原生类型代码、required、unique、default_value_mode/value 和类型所需 options。只有真实 ID、当前 SDK 方法或目标环境行为需要实施取证；已经由随包契约明确的原生类型、字段语义、Link 结构和 epoch-seconds 写入要求应在本次设计写清。机械审核同时检查原参照结构与落盘一致性；业务与平台内容仍逐项核对。
