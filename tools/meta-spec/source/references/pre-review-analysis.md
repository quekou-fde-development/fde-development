# 审核前业务流与系统架构分析

## 目的

本方法把调研材料变成可审阅的业务与系统理解，采用 Meta Orchestrator 的 Step 0—3 和 Meta Skill 的前置分析思想。它只服务于架构设计，停止在总架构师审核之前。

## 1. 锁定结果与边界

先写清交付对象、使用者、业务目标、成功和失败的可观察条件、范围外事项及有权决定者。每一项附证据或决定编号。若目标只有抽象口号、验收对象不明或决定权不清，先提问。

在还原时序前，逐段读原始材料，把每项明确要求登记到本次已有的 `working/` 分析中。每条至少留下原文短句与来源位置、完整要求、已确认或待澄清状态、负责承载它的九件文件及现有章节。一个句子包含多个独立条件时分开登记，保留“可同时、仅、每次、不得、除非、到期后”等影响规则的限定词。背景描述可记为背景；不能把不容易转成用例的明确要求归为背景。

依次核对材料中的目标与范围、角色关系与授权、数据与关联、动作与状态、异常与恢复、时限与保留、规模与环境、验收与批准。该顺序用于检查读源遗漏；来源没有的类别记为未给出或不适用，不补造业务规则。角色能否由同一人兼任、多重授权与撤销其中一组的结果分别登记，不能只记录每种角色各自可做什么。

遇到“各条、所有、每次、分别、同时”等覆盖多个对象或动作的要求，先列出实际适用对象，再按该对象具有的事件展开所需事实。例如来源要求各类记录留存相应业务责任人与时间，就逐对象检查其实际存在的创建、提交、关闭、作废等事件；一个对象的提交人不能代替另一个事件的创建人。来源未要求或对象不存在的事件不补造。每项需持久保存的事实随后对应 03 的具体字段或有证据的平台原生元数据，并接到该事件的写入、授权、回读和验证位置。不能用一行“统一审计”或全局能力总述覆盖这些对象差异。

用这份登记驱动后续写作：先把来源已经作出的决定写入对应原参照槽位，再推导字段、页面和调用。跨文件约束只定义一次，其他文件采用一致描述或明确引用。每条要求在起草后补实际正文短句，在最终回查后补文件行号；暂不属于本期、发生冲突或需人决定的条目写清来源和去向。来源要求不能默默消失，也不能仅靠“参见来源某节”代替正文。该登记留在运行工作区，不增加交付文件或固定表头。

## 2. 还原完整时序

从一次真实触发开始，按“谁收到什么、做了什么、留下什么、交给谁、如何知道完成”铺开。标出：

- 正常顺序、等待、持续断点、判断分叉和并行；
- 人工步骤、系统外步骤、异常、失败返回和中止；
- 输入、产出、记录位置、来源事实和推断；
- 真实案例覆盖的部分与尚未见到的部分。

原始材料按岗位、表单或规则组织而没有时间顺序时，先将“何时、满足何条件、做什么”还原为时序骨架，并把这一步标为推断。不要根据页面数量、组织名称或预设技术拆流程。

## 3. 分析执行与判断

对每个稳定流程段分配 `BF-xx` 编号。

执行段至少表达动作与对象、输入与依据、可达入口、产出与位置、合法结果、影响和失败处置。判断段按检索、整合、候选、审核四相位表达证据、标准、触发条件和逐分支去向。对任何判断先检查反例、边界和信息不足情形；无法追溯的阈值与规则不予补造。

分段的目的在于让人能看清独立完成、等待、交接或裁决，不能把它当成未来 Skill、数字员工或页面数量的预分配。连续单线流程可以保持一个段；跨时间、独立触发或独立核验的工作才需要更细的交接说明。

## 4. 形成系统架构理解

沿每个 `BF-xx` 写出当前或候选承担方：人、既有系统、新建工作台、潜在数字员工、潜在 Skill 或外部服务。说明：

- 职责、触发者、结果接收者和失败接手者；
- 权威数据从哪里来，谁能读写，哪些只是展示或缓存；
- 入口、接口或人工交接，及其已核实状态；
- 需要人工批准的动作、重复执行和未知结果的处置；
- 身份、权限、时效、数据量、成本和环境约束。

画出的系统图和对应表只是项目设计分析。不要输出 Orchestrator 的 `topology.json`、edge contract、stamp、最终网络声明或运行期调度；这些属于完整 Skill 网络编译及后续实施验证。

## 5. 按 Octopus 与 Arcubase 定位承载

所有候选系统按以下边界拆解，并为每个 `BF-xx` 留下可追溯的承载说明：

- Workbench React 承担页面、路由和经 `@syngy/workbench-auth` 取得的会话入口；不增设项目自有登录或令牌存储。
- Octopus 承担项目实际需要的 Host 能力和组织管理入口。只有用例需要 Host 用户、团队、目录、数字员工、会话、文件、Skill 或相近能力时，才安排 `octopus` client；具体方法以后续安装类型或官方契约为准。
- Arcubase 承担每个共享、持久、可查询的业务对象。沿业务流写出 Arcubase 原生表、稳定 field key、`linkto` 关系、状态、读写入口和权威来源；本地缓存或页面计算不能替代该记录。
- 业务授权由 Arcubase 原生 organization actor 和各表 access rule 落地，Octopus 的官方组织角色/成员关系接口作为统一管理入口。Host 团队资格、业务角色、对象归属、负责人和审批人分别建模；每个关系说明在何处维护、由何处执行授权和如何验证。
- Taskboard 仅承接已确认的任务或项目工作流。用例没有该需求时不在图中增加该服务。

把既有 App 或新 App 的选择也列入架构边界：既有 App 以实读的精确 ID、现有 schema 和稳定键为依据；新 App 以待批准的 Arcubase 表、字段、Link 和角色规则为依据。不能用名称推断现有 App，也不能预填未取得的 ID。

实际人类调用者到 Arcubase 用户/actor 的映射、允许/拒绝路径和撤权传播都标为需验证的交接。项目涉及数字员工代办或 `conversation_member` 时，再标出发起与执行身份；当前 `conversation_member` 身份模式没有完成证据，不能作为已可运行的架构连接。

## 6. 收束检查

先从原始材料反查第 1 节的登记，确认每个明确条件均被独立保留，再用至少一条主流程和最重要的一条异常路径推演。检查每个上游输出能否成为下游输入，对象与状态是否一致，是否存在无接手的异常或无来源的数据。把事实没有归宿、外部能力未核实、方案有多种合理选择的地方汇入问题簇，再进入人工澄清。
