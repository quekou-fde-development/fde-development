# FDE 架构方法论

阅读入口见[架构设计手册](README.md) · [架构底层理论](架构理论.md) · [可填架构手册](架构手册.md)

## 1 链条总览

```
力 → 问题定义 → 应然 → 解法 → 手段化 → 产品 → 报价
                          ↑                │
                          └──── 验收闭环 ───┘
```

六个动作加一条闭环。顺序由依赖决定，不由习惯决定。

| 步 | 一句话 | 出口 |
|---|---|---|
| 一 实然 | 这家企业实际怎么运转，每处靠什么撑住 | 力清单、δ 清单、环格编号 |
| 二 应然 | 要送出这个功能、在这些破坏下，必须存在什么 | 必需清单、关键业务、设防表 |
| 三 解法 | 应然与实然之差在哪里 | 须增／须改／须删三列 |
| 四 手段化 | 这些差集里，软件与 AI 能承担哪几项 | 可行改动集、做不了清单 |
| 五 产品 | 我们承诺什么、验收什么 | F 声明、E 声明、验收项 |
| 六 报价 | 多少钱、分几期 | 报价、分期表 |

**三步之间的顺序不可换。** 没有实然，应然无处对照；没有应然，解法没有目标；没有解法，手段化无从判断；没有手段化，产品的承诺无边；没有产品，报价没有对象。

### 现状有效性前提

公司一定在运转。结构断裂、功能送不出去的企业不会留在市场上，也不会成为我们的客户。这条前提推出一项判定：**FDE 的项目不存在重建情形，只有优化情形。**

它的执行含义有三条：

一，每一条力现在都有人在对抗它。对抗方式可能是制度、可能是某个岗位的经验、可能是私下表格与加班。第一步的动作是找出这些既有对抗方式，判断它够不够、贵不贵。

二，应然与实然必然大面积重合。差集小是正常的；差集巨大说明应然判错了（把偏好当必需），或实然没看懂（漏掉了现有的对抗方式）。

三，把客户现状诊断为残缺，是方法论错误，会直接导致方案越做越大、验收无处落脚。

## 2 第一步 · 实然

实然的事实来自调研。现场调研按[调研方法论](../2-项目经理/④调研/调研方法论.md)执行，出口为问题六样齐与五张表；客户分析 A 按开发手册 §2—§3 形成。本节只写调研之后必须完成的判断，不重复调研动作。

### 2.1 三项产物

**一、环格编号。** 从客户经营目标向下梳理到部门、岗位、动作、系统与表单，每一段能说明输入、判断、输出、交接的业务闭环编为一个环（环-01、环-02……），环内可单独观察和改善的量编为一格（环-01a、环-01b……）。编号全链复用：力清单、关键业务、验收项都挂这个号。

**二、力清单。** 每条力记六项：

| 项 | 内容 | 判据 |
|---|---|---|
| 编号 | 挂环格号 | 可追溯 |
| 内容 | 使哪条功能的送出条件恶化 | 指向具体功能，不写「管理混乱」 |
| 来源 | 物质条件、有权的主体、制度规则、时间窗口、历史沉积 | 能归入其一；归不进即新增一类 |
| 维持者 | 谁受益、谁能改、谁担代价、移除后谁付 | 四项核对俱全才算一条力 |
| 现有对抗方式 | 现在靠什么撑住 | 必须指认得出来 |
| 痕迹证据 | 断裂／绕行／阻力／缺失四类之一 | 无痕迹者标「取证不足」，不作结论 |

**三、δ 清单（真实系统与应然的差）。** 第一步只能给出 δ 的四类候选，不能定稿——应然尚未产出，差集无从计算。此处的动作是分类：哪些是冗余（同一必需有多个可选载体）、哪些是沉积（力已解而结构仍被日常维持）、哪些是失序残留（无人维护中漂移出的不一致）、哪些是未承重空壳。

### 2.2 三项判据

一，**每条力都有痕迹。** 无痕迹而只有自述的，进待核清单，不进力清单——「没找到痕迹」与「没有这条力」是两件事，前者是取证不足。

二，**每条力都指认得出现有对抗方式。** 指认不出来的，说明还没看懂这家公司在怎么运转，回调研。

三，**没有「应该是」这类措辞。** 数据清单、流程记录、权限登记一律只写查到的，未知项保留待取数，写清所缺样本、取数路径与接续人。

### 2.3 情境策略

- 客户讲不清流程 → 跟一件真实业务从触发走到终态，不听讲述
- 组织图不可信 → 用交接次数、单据流向反推实际协作
- 数据在纸上或在人脑子里 → 先测能不能形式化，不问有没有系统
- 部门口径不一致 → 同一个词三处各问一遍，差异本身即发现
- 客户说「我们一直这么干」→ 问维持者四项核对，判断真力还是沉积
- 看到私下表格、双录、微信群对账 → 判为代偿，记下它绕开的是什么，不作不规范处理

## 3 第二步 · 应然

### 3.1 应然是什么

**应然不是客户的期望，是我们设计出来的架构(F, E)。**

F 由客户指派——指派方是承担该功能不成立之后果的一方。E 由我们与客户共同划定，划定的依据是基线、成本与承诺意愿。两者定了之后，**「要送出这个功能、在这些破坏下，必须存在什么」由我们回答**。这个回答就是应然。

应然是单一对象，不作投影。它只回答一件事：必须存在什么。客户看不看、开发怎么写，是后面的事。

**两重投影发生在产品定义处**（§6）：产品是本轮唯一对外成立的交付物，它向客户投影为解决方案，向我方投影为技术架构（所需 spec 的写作对象）。两次投影的源是同一个产品，不是同一份应然——应然包含本轮不承诺的部分，直接投影会把承诺范围外的内容一并说出去。

### 3.2 三路输入与设计

应然由三路输入加一次设计合成。三路的局限各不相同，缺一路就有一类错误无法发现。

| 输入 | 提供什么 | 看不见什么 |
|---|---|---|
| **访谈** | 客户对功能的表述、对破坏的感知、对承诺的期待、部门之间的权责说法 | 客户已经习以为常的对抗方式；说了但没在做的事；说不出口的政治性力 |
| **走访观察** | 现场痕迹：绕行、加班、双录、纸质单据、岗位上的临时办法；实际动作与图纸的差 | 动作的意图与因果；为什么这么做；这么做的代价落在谁身上 |
| **设计** | 必需集、关键业务、设防取舍；应然的完整形态 | 无输入则无法设计；设计不产生事实 |

合成的次序：

```
访谈 + 观察 → 功能与力的判定 → 消去推演 → 必需集 → 无冗余剔除 → 关键业务 → 设防表
```

前两步属判断，中间三步属设计，最后一步属取舍。

**三路都必须留下记录**，且同一项在访谈与观察中结论不一致时，以观察为准，分歧进待核清单——这类分歧常是力的最强证据：客户说自己不看这张表，现场发现所有决策都从这张表出发。

### 3.3 三项产物

**一、必需清单**

对每一项功能，逐条列出「必须存在什么」。判定只有两步：先假设某组件不存在，看功能还成不成立；再从成立的那些里剔除可以被替代的。

对每一项功能，逐条列出必须存在的组件。

| 项 | 内容 | 判据 |
|---|---|---|
| 编号 | 挂环格号 | 可追溯 |
| 必需内容 | 哪一项功能所必需 | 指明功能，不写「需要一套系统」 |
| 移除推演 | 设其不存在，功能是否仍能送出 | 结论与推演过程都写 |
| 对抗的力 | 它对抗哪一条力 | 回指力清单编号 |
| 替代可能 | 有无其他项可承担同一必需 | 有则本项不入架构，改记替代方案 |

判定按最小组合做，不按单件做：先找出「功能会断掉」的最小组合，再看哪些组件出现在所有这样的组合里。按单件逐个删会出错——两条互为备份的路径，各删一条功能都还在，于是两条同时被判为非必需。

判定要在失效场景下跑：异常路径、追溯、责任归属这类组件，平时不用，正常运行时删掉也看不出差别，只有在出事的时候才显效。

**二、关键业务**

只列少了就断的那几条，不追求完整覆盖。按走的是什么分：权责、钱和物、风控追溯、信息、业务工单。每条登记五项——从哪产生、经过谁、在哪留痕、到谁、有没有专人推。

其中「有无专门机构推动」一项单列：风控、审计、追溯一类业务在组织里天然没动力源，若不专门设一个推动者，它永远滞后。

每一条都收对功能承重的部分。判据同上：少了它功能就断。

**三、设防表**

对每一种被承诺覆盖的异常破坏，给出设到什么程度、付多少代价。

E 逐项列出，每条给四项：破坏事件、程度分级、频率计数（相对承诺期）、设防决定与成本。

| 项 | 内容 |
|---|---|
| 破坏事件 | 具体事件，不写「各类风险」 |
| 程度分级 | 按后果切档，档数由本行业惯例定 |
| 频率计数 | 单位时间或单位业务量内的发生次数，窗口＝承诺期 |
| 设防决定 | 全设防／部分设防／不设防但隔离／不设防 |
| 成本 | 静态代价、设防代价、降低常态效率的代价，三项分列 |

条目可少，不得空白。承诺期之外的事件不进表——它们在承诺有效期内发生的概率趋近于零，不构成这份承诺的代价；在表外单列一句，说明这类事件的后果由客户自留，或由保险、法规、上级单位等机制承接。

设防表进架构手册，对客户可见。理由：承诺须可检验；藏成本的后果是客户在验收时把「你没做到」和「你没承诺」混为一谈。

### 3.4 判据

- 每一项必需都能回指一条力；回指不到的是偏好，删
- 每一项必需的移除推演都写了过程，不只写结论
- 关键业务的每个环节有承接者，没有断头
- 设防表无空白行
- 应然里没有「先不管，做的时候再说」的项
- 应然与实然的差集规模能解释：差集大时，须能说明是应然判紧了还是实然看漏了

## 4 第三步 · 解法

### 4.1 解法是差集

**解法 ＝ 应然 − 实然。**

这一步的全部工作是逐项对照，产出三列：

| 列 | 定义 | 典型内容 |
|---|---|---|
| **须增** | 应然有、实然无 | 缺的必需、缺的关键业务、缺的检查环节 |
| **须改** | 实然有、形态不对 | 同一必需做坏了；靠临时办法硬撑；关键业务接错了人 |
| **须删** | δ 中阻碍功能送出的部分 | 沉积、未承重空壳、失序残留 |

三列的判据各不相同：须增看移除推演，须改看现有对抗方式能不能撑住，须删看维持者四项核对的第四项——移除后谁付。

### 4.2 为什么解法是差集而不是重新设计

差集有界，重新设计无界。

差集的上界由应然给（必需集就那么大），下界由实然给（已经运转的东西不动）。方案越做越大时，一定是有某一项越出了这两个界：要么应然里混进了偏好，要么实然里漏了现有的对抗方式。

这一步同时给出「为什么一定是优化、不是重建」的机制解释：现有对抗方式能撑住的部分，不在差集里。

### 4.3 价值三元分解

差集中每一列的改善，拆成三个来源，分别说明各贡献多少：

| 来源 | 说明什么 |
|---|---|
| 流程调整 | 取消、合并、前移带来的改善。不需要软件也能拿到的那部分 |
| 普通工程 | 固定规则、既有系统改造能实现的改善 |
| AI | 前两者做不到、须靠模型判断的那部分 |

不分这三者，AI 会吃掉流程调整的红利——把「流程本可省掉」算成「AI 带来的」。这一项直接影响报价的可信度，也是客户后期质疑价值时的第一处攻击面。

### 4.4 不动清单

必须产出。明确写出哪些部分我们不改，以及理由（承重、刚改造完、在等客户内部决定、风险高于收益）。

这份清单是后面全部分歧的防火墙：客户后期加的每一条要求，先对照它。没有这份清单，项目的范围会在交付中持续扩张。

### 4.5 判据

- 三列的每一项都有编号，能挂回环格
- 须删列中的每一项，都有第四项的记录（移除后谁付）
- 价值三元已分开，AI 部分的贡献有反事实检验支撑（见 §5.4）
- 不动清单已写，且每一项有理由
- 差集规模可解释

## 5 第四步 · 手段化

结构判断到此为止。手段化开始问：这些改动里，软件与 AI 能承担哪几项，承担到什么程度。

### 5.1 三个检查项

**检查项一 · AI 能力边界**

逐项回答：这项改动要求的判断与动作，模型做不做得了。

判据：信息表征的变换（改变记录形态、持有者、时间位置、处理方式）可以承担；直接改变物理过程、直接改变人的信念、直接改变法律归属的，须补出经信息层的传导链，补不出则不做（回 §4 重判该项是须改还是不做）。

另有一条：模型能给候选、能给判断，不能替代组织判断的采纳环节。凡须由人授权的节点，无论模型能力多强，该节点留人。

**检查项二 · 数据环境**（§8.1 七层）

逐项回答：做这一项需要的信息，存不存在、形态对不对、取不取得到。

七层是递减的门，卡在哪一层是确定的。这一项与上一项不同：上一项判「想不想得明白」，这一项判「拿不拿得到料」。

**检查项三 · 成本**

逐项回答：做到什么程度、付多少。成本三项分列：静态（运行与维护）、设防（异常对抗的专门构造）、降低常态效率（冗余与监控带来的时延、人力、操作步骤）。

成本须能与第二步的损失并排放。对不上的，回 §4 重判。

### 5.2 两项产物

**一、可行改动集。** 三个检查项全过的项，逐项标出：由什么承担（AI／确定性工程／流程调整／人）、做到什么程度、依赖什么前提。

**二、做不了清单。** 结构上合理而手段做不到的项。这份清单有两个去处：交回客户（由他自己组织人做），或列为二期（等条件成熟）。含糊处理会变成项目末期的主要纠纷源。

### 5.3 蒸馏项单列

若某处须把人的隐性判断转为可执行的规则集，该处单列，逐项验三条前置：输入数据是否可得、判断能否被采纳、对象能否被处置。三条缺一，该处定位为辅助而非替代，并写进承诺边界。

### 5.4 反事实检验

对可行改动集中每一项拟由 AI 承担的能力，逐条回答：**去掉 AI，这一项的改善受什么影响？**

- 无影响 → 这一处不需要 AI，改由确定性工程或流程调整承担
- 有影响但可替代 → 写替代方案，比较代价
- 不可替代 → 写依据，以及支撑这个依据的样本与验证条件

### 5.5 判据

- 每一项可行改动都过了三个检查项，且每项的结论都写下来
- 做不了清单存在，且每一项有去处
- 每个 AI 节点有判据与待验证条件
- 蒸馏项的三条前置各有明确结论，不写「效果待评估」
- 反事实检验对每一项 AI 能力有结论

## 6 第五步 · 产品

### 6.1 产品是交集

**产品 ＝ 可行改动集 ∩ 承诺范围。**

两个方向都可能不等：能做到但不承诺的，出承诺边界外，明写；承诺了但实现路径由我方决定的，客户不管怎么实现，只看 F 与 E。

产品不由「我们做了什么」定义，由「我们承诺送出什么、在什么破坏下兑现」定义。

### 6.2 三件产物

**一、F 声明——承担什么功能**

我们承担哪些功能，对谁负责。写成客户能核验的句子：谁在什么场景下，能拿到什么结果。

**二、E 声明——在什么破坏面前兑现**

在哪些破坏面前兑现，每条设到什么程度。直接引用设防表，不复述。

两轴同时写明，缺一承诺不可检验：只写功能范围，客户不知道出了事你保不保；只写设防范围，不知道你在保什么。架构文件须附一句：本架构在功能范围与设防范围不变的前提下成立；两者任一变更，须重新判定。

**三、验收项**（闭环）

逐条对应第一步的损失。每一条验收项写：客户语言的现象、可测的量、现状值、目标值、测法与样本范围。

### 6.3 场景量与业务结果

| 类 | 例子 | 能否进验收 |
|---|---|---|
| 场景量 | 处理耗时、一次通过率、偏离度、人工复核比例 | 能。可判、可控 |
| 业务结果 | 每单赚多少、成不成交、营收、利润 | 不能。只进观察 |

场景量的改善支撑价值判断，不直接替代客户经营结果。写成「降本 X 万」时，X 须由场景量乘真实业务量推出，且标明推导链。

### 6.4 验收闭环

**每一条验收项须回指第一步问题定义中的某一条损失。**

回指不上的验收项删；第一步有损失而产品无对应验收项的，补上或在 E 里明写不承诺。

这条规则同时给出三项保护：方案不越做越大（每加一项就要回指一条损失）；验收不扯皮（验收项自第一天以客户的损失表述固定）；报价说得清（成本挂改动、改动挂损失）。

### 6.5 体验流

写明使用者一天多干几步、少干几步。这一步不是文档装饰，是 §6.7 业务成立的证据基础。

### 6.6 判据

- F 与 E 都写成客户能核验的句子
- 每条验收项有可测的量、现状值、目标值与测法
- 验收项能逐条回指损失；回指表附在验收文件内
- 业务结果没有被写成承诺
- 体验流中有操作量增减的算术
- 承诺边界外的事项有明确归属

### 6.7 技术可实现性

逐项检查完（§5），把产品当一个整体再问一遍。这一项与 §5 的检查项一不是一回事：那一项逐项问「模型做不做得了」，这一项问整个产品装起来、在客户那儿真跑起来站不站得住。

| 问什么 | 说明 |
|---|---|
| 接不接得上客户现有系统 | 接口、数据格式、谁配合 |
| 扛不扛得住客户的量 | 单量、并发、历史数据规模 |
| 跑一次要多久 | 客户等不等得及，慢在哪一步 |
| 客户那边没人懂技术，出了问题谁处理 | 客户自己、我方、还是第三方 |
| 上线以后谁来维护、多久动一次 | 维护责任与频率 |

答不上来的写进假设清单，并写明不成立时怎么退。

### 6.8 业务成立

业务成立问三句：

| 问什么 | 判据 |
|---|---|
| 用的人一天多干几步、少干几步 | 体验流里有算术，不是定性描述 |
| 出了错，用的人能不能看出来 | 有异常的发现方式，不是等下游出事 |
| 用的人如果不照着办，会怎样 | 有不靠自觉的约束；只靠自觉的不算成立 |

第三句是这一节的重心。系统做得再对，人不用就是不成立。它的证据不在客户老板嘴上，在具体岗位上的人手上——所以只有现场看得到，坐在办公室想不出来。

业务成立不过时的去向见 §10 回边：回 §4 改人机分工，或回 §3 重判必需集。

### 6.9 判据汇总

| 项 | 判据 |
|---|---|
| 技术可实现 | 五个问题各有结论，答不上的进了假设清单 |
| 业务成立 | 三句各能答，操作量有算术 |
| F 与 E | 两轴都写了，客户能核验 |

## 7 第六步 · 报价与范围

由产品推出，不由成本反推。

报价结构三项：开发成本（按 §5 可行改动集分模块拆分）、运行投入（复核、返工、模型调用、人工兜底）、设防成本（按设防表逐项）。三项分列，不给总数——按「不做会怎样」分层报价，客户可以选择不做哪一部分。

分期依据：数据依赖在前，判断能力在后；每期至少有一个可测的场景量验收点；没有可测验收点的一期不立项。

现行流程（开发计划、架构设计〔含架构图〕、解决方案一次送审，范围报价作附件）不变，本节只补三项成本的来源。

## 8 两根贯穿轴

数据环境与权限结构不做专章，在六个动作里各设切口。切口位置如下。

### 8.1 数据环境七层

| 层 | 问什么 | 卡在这里意味着 |
|---|---|---|
| 1 软件 | 用的什么系统、什么厂商、哪些模块、什么版本 | 系统存在不等于数据可用 |
| 2 部署形态 | 本地／SaaS／混合 | 决定 3—7 层的可行性 |
| 3 存储 | 什么数据库；是否自建；有无中间库 | 决定能不能直取 |
| 4 存储结构 | 表结构、主数据在哪、单据与主数据如何关联、定制字段多少 | 决定取出来能不能用 |
| 5 权限 | 系统内角色；谁能读、谁能写、谁只能看报表 | 决定取不取得到 |
| 6 安全要求 | 数据分级、出域限制、等保、审计要求 | 决定数据能不能离开原地 |
| 7 接口 | 有无 API、有无文档、能否开放、谁批、推还是拉、有无中间件 | 决定取数方式与工作量 |

部署形态的决定作用单记：SaaS 通常有接口与文档，不能自建中间层、不能直连库，取数受供应商版本与配额限制，数据出域往往最硬；本地自建可直连库，但结构常被定制改乱，接口常无文档；混合最易出问题，同一业务对象两处各一份，权威源说不清。

六步中的位置：第一步清点、第二步定应然的可行性前提、第四步关二判能否承担、第五步写进承诺边界、第六步计入成本。

### 8.2 权限结构

权限是两个来源的交集：组织架构给出谁有权批、谁能否决、谁负最终责任；业务流给出这个节点必须谁参与、信息经过谁的手、异常由谁兜底。单看组织图会漏掉实际发生的授权（代批、越级、惯例），单看业务流会漏掉制度上谁担责。

三态并列登记：制度权限（组织图）／实际权限（业务流观察）／系统权限（系统配置），标出差异。差异处即风险点。

两轴的处置差别：数据不可用可以花钱清洗，权限不可用只能靠人给。同一个「做不到」，在数据上是成本问题，在权限上是关系问题。

## 9 依据指针与剩余物

### 9.1 依据指针

链上每个判断后挂一个依据指针，并标确认状态。

| 段 | 挂什么 | 确认状态 |
|---|---|---|
| 实然 | 事实来源：客户原话、单据、系统导出、观察记录 | 已确认／待确认 |
| 力 | 痕迹类型与证据位置 | 已取证／取证不足 |
| 应然 | 移除推演、回指的力编号 | 已判／待判 |
| 解法 | 差集三列的编号与对应实然项 | 已对照／待对照 |
| 手段化 | 三个检查项的结论、假设与测法 | 已验证／待验证 |
| 产品 | 损失回指关系、验收项编号 | 已闭合／待闭合 |

确认状态是独立字段，不写进正文。审阅时先看状态列：全「已确认」而依据栏空，说明虚报；大量「待确认」而手段化已通过，说明检查不实。

指针断处即未想清处。可 grep。

### 9.2 五份剩余物

六步之间不是等价变换，每一步都筛掉东西。筛掉的部分必须显式写在文档里，否则边界会在交付中自行扩张。

| 步间 | 筛掉什么 | 写到哪 |
|---|---|---|
| 实然 → 应然 | 有痕迹但客户不认的力 | 待核清单，下次调研再问 |
| 应然 → 解法 | 原因不在结构上的问题（人、流程、市场） | 非本项目范围，明写 |
| 解法 → 手段化 | 结构合理而手段做不到的改动 | 做不了清单，交客户或二期 |
| 手段化 → 产品 | 能做到但不承诺的 | 承诺边界外，明写 |
| 产品 → 报价 | 承诺了但本期不做的 | 分期表 |

五份合起来是一份「我们不管什么」的清单。FDE 项目最常见的失败不是做不出来，是边界从不写下来，最后每一项都算我方的责任。

## 10 回边与升级

| 情况 | 去向 |
|---|---|
| 手段化关一不过（能力做不到） | 回解法重判该项：改承担方式，或改判为不做 |
| 手段化关三不过（成本对不上） | 回解法缩范围，或回应然改设防档位 |
| 产品门不过（人不这么用／安静失败不可接受） | 回解法改人机分工，或回应然重判必需集 |
| 应然发现某项必需补不出传导链 | 回实然重判该项是不是力 |
| 实然发现硬力过多、无一条可动 | 交 PM 按商务问题处理 |
| 验收项回指不到损失 | 回产品补验收项，或回应然改 E |
| 审核通过后写 spec 发现应然没有的结构 | 回补应然并升版；涉及已审核的不可逆判断送审复核 |
| 开发中信息不足（二次调研） | 补证回写应然并升版；影响范围或验收的同时交商务决策 |
| 启动会签字后 | 已签验收版本固定；技术调整服务于原签字范围与标准；新增诉求按商务流程处理 |

**两轮升级规则**：同一动作连续两轮未通过，不在原地继续改，交 PM 组织商务处理——调整范围、改报价、或建议客户暂缓。防的是无限打磨：第三轮产出通常不如第一轮，耗掉的是交付窗口。

## 11 推导：这套方法从哪来

本文不对读者的前置阅读作任何假设。本节先把三组前提各自讲清楚——它们说什么、为什么成立、在方法里起什么作用——然后说明六步怎样由这些前提推出。

前提分三层。分层的意义在于证据身份不同：第一层是我们可以独立辩护的命题；第二层是把组织当作认识对象时必然遇到的限制；第三层只说明「用软件和 AI 来做」这件事带来的具体约束。混在一起，方法论会说不清哪一条是架构的必然、哪一条只是因为我们恰好用软件。

### 11.1 第一层：架构是什么

**命题**：架构是系统为使某一功能在给定破坏面前持续成立而必须存在的、不可替代的那部分结构。

这句话里每个词都有具体所指。

**功能**，指这个组织对某个外部对象的义务——比如「按合同把货在约定日期发出去」。功能由外部指派，不由我们观察得出；指派方是承担功能不成立之后果的那一方。同一套组织，对不同对象承担不同功能，所以架构总是相对于某一功能而言的。

**破坏**，指使功能成立条件恶化的作用。判断破坏不看是否已经出事，看条件是否在恶化。台风季来了而大楼没倒，破坏仍然成立，只是被结构挡住了。

**必须存在**，用消去法判定：假设某个组件不存在，推演功能还成不成立；不成立，这个组件就在该功能上承重。

**不可替代**，指这个承重组件不能由别的组件顶替。两个组件共同满足同一项需要时，进入架构的是「这项需要」，两个组件属于实现方式。

由这一定义派生出四条对本方法直接起约束作用的结论：

| 结论 | 通俗表述 | 在本方法中的落点 |
|---|---|---|
| 架构必然存在 | 只要系统在承担功能，就必须有一组结构撑着它 | 不存在「没有架构」的项目，只有「架构有效但可优化」 |
| 架构小于实际系统 | 撑住功能的结构，总比系统里所有东西少得多 | 应然的规模必然小于实然，差集小是正常状态 |
| 架构是判定出来的 | 它不能直接看见，只能通过推演确认 | 架构须留判定依据，不能只留结论 |
| 真实系统里有实际无用部分 | 冗设、已失效的旧规矩、无人维护的残留 | 这些是改造可动的空间，也是改造风险的来源 |

### 11.2 第二层：认识一个组织时的三条限制

组织是复杂系统。我们对它做的调研是认识活动，不是数据采集。三条限制直接决定了方法的第一、二、三步怎么做。

**第一条：先看这个组织在更大的系统里干什么，再拆它的内部。**

任何一个单元——公司、部门、岗位——都在更大的体系中承担某项功能，并与上下游交换东西。判断它内部哪些结构是必需的，前提是先知道它对外承担什么。先拆内部再定外部，会得到一个边界画错的系统：把不属于它的职责算进来，或把它真正的职责漏在外面。

这条限制的实操含义是：调研的第一组问题不是「你们内部怎么分工」，而是「你们向谁交付什么、他们拿不到会怎样、上游给你们什么」。功能边界确定了，内部拆解才有参照。

**第二条：任何描述都会丢东西，所以必须记下丢了什么。**

把一家公司的运作写成文档，无论如何都会压缩：口头约定被省略、人员的临时办法被省略、没人说但大家都遵守的默契被省略。这不是写作不认真，是描述的固有性质。

由此产生一条硬要求：**产物必须标出被压缩掉了什么**。本文 §9.2 的五份剩余物就是这一条的落点——每两步之间筛掉的东西，都要写下来，而不是默默丢弃。

**第三条：人和 AI 在认识活动中的分工是固定的。**

给候选、做结构化整理、把散落信息按格式归拢，这些可以由 AI 承担。判断一个结构是否成立、一个组织整体是不是这样运转的，只能由人做——因为这类判断要承担后果，而承担后果不是一个可以委派给工具的动作。

这条限制决定了本文 §3.2 的三路输入：访谈与现场观察负责取事实，设计由人做，AI 在两侧做整理与比对。

### 11.3 第三层：软件与 AI 能做什么

这一层只回答一个问题：我们手里这个手段，因果上能做到什么程度。

**命题一：软件改变的是信息的表征。**

所谓表征，指同一条信息以什么形态存在、由谁持有、在什么时点出现、经过什么处理。软件能做的四件事都在这一层：把纸面记录变成数据记录；把信息从一个人手里转到另一个人手里；把信息从「事后才知道」变成「发生时就知道」；把需要人工计算的处理变成自动计算。

软件不能直接改变物理过程，不能直接改变法律归属，不能直接改变人的信念。任何声称软件能直接做到这三件事的方案，其中必有一段传导链没写出来——须补出它，补不出则该项不做。

**命题二：AI 的能力边界在语言层。**

模型能读能写能推演，能在给定判据下批量执行，能给出候选与解释。它不能替代组织判断的采纳环节——一个判断算对了但没人据此行动，问题不在能力，在采纳。它也不能替代须由人承担责任的授权动作。

这条边界与模型强弱无关，是结构性的。本文 §5.1 的第一关和 §5.3 的蒸馏三条件都建立在这一条上。

### 11.4 六步怎样由前提推出

| 步 | 推出过程 |
|---|---|
| **一 实然** | 组织随时间自发失序，功能成立条件持续恶化，故必有正在起作用的破坏（第一层＋第三层前提一）。破坏不可直接看见，只在系统上留痕，故必须现场取证而不能只做访谈（第一层结论：架构是判定出来的）。先看对外功能再拆内部（第二层第一条）。公司一定在运转，故这些破坏现在都已有对抗方式，须找出它们（§1 现状有效性前提） |
| **二 应然** | 要回答「必须存在什么」，只能用消去法，且须按最小组合判定，否则会把互为备份的两项同时误剪（第一层定义与不可替代条件）。结果是判定产物，不是观察产物，故须留推演过程（第一层结论）。设计过程会丢信息，故须标出丢了什么（第二层第二条） |
| **三 解法** | 应然与实然是两个可对照的对象，故解是二者的差，而不是重新设计（第一层定义）。差必然小，因为实际系统里撑住功能的部分本就少于全部（第一层结论：架构小于实际系统）。差中的「须删」来自实际无用部分（第一层结论：真实系统有实际无用部分）。回指不到破坏的项出局（剃刀，见 §11.5） |
| **四 手段化** | 结构与手段是两个判断，不能混谈，故单列一步（第三层）。能力边界关来自第三层两条命题。数据环境关来自：软件只能处理已被表征的信息，而表征是否存在、形态是否可用、能否被取到，须逐层清点。成本关来自：每一步改动都要付静态、设防、效率三项代价 |
| **五 产品** | 承诺须两条轴同时成立——向谁兑现什么（功能范围），在哪些破坏面前兑现（设防范围）。缺一条，承诺不可核验（第一层定义中的 F 与 E）。承诺期外的事件不构成这份承诺的代价，逐项排除 |
| **六 报价** | 成本本来就分三项，故报价分三项列，不给总数。按「不做会怎样」分层，使客户可以选择不做哪一部分 |

### 11.5 剃刀在方法中的三处用法

奥卡姆剃刀在这里不是一句格言，而是一条可执行的删除规则：**指不出它在对抗什么的，删。**

它在方法中有三处形态，删的对象不同。

| 形态 | 删什么 | 位置 |
|---|---|---|
| 删组件 | 指不出对抗哪条破坏的承重项 | §3.3 必需清单、§4.1 须删列 |
| 删耦合 | 指不出对应破坏的、过度集中的连接 | §4.1 须改列（拉平） |
| 删描述 | 超出功能所需范围的材料与字段 | §2.2 判据、§9.2 剩余物 |

第三处需要一个限定，否则会被误用：不是查到什么就写什么，但删掉的东西要记在剩余物里。剃刀让产物变小，不让事实变少。

### 11.6 一条被刻意排除的起点

**不以客户诉求为起点。**

客户的诉求多数是手段诉求：「上一个 AI」「做个看板」「把流程搬进系统」。以它为起点，方法论会退化成手段选型——先定工具，再找理由。

本文的起点是功能与破坏：诉求进 §2 作为线索，进 §3 作为功能指派的输入，不直接作为目标。

这条排除有代价：客户会觉得我们没在听他说。故 §3.2 要求访谈原话完整保留，§6 要求产品用客户的语言表述——**方向由我们定，语言由客户认**。

## 12 与旧版的差异

旧版（11.05，归档于 `_archive/方法论_10.24版_2026-11-07/`）为四项核对加 Q5 排序。本版的改动：

1. **Q2 应然的内容重写。** 旧版 Q2 是「选一条约束松动」，即从客户诉求中挑目标；本版 Q2 是设计架构(F, E)——由访谈、观察、设计三路输入合成，产出必需清单、关键业务、设防表。这一改动的原因是理论把架构定义为抽象、应然的判定产物，目标不由客户给，由我们设计。
2. **解法改为差集。** 旧版 Q3 是「松动之后的解长什么样」，独立设计；本版解法是应然减实然的三列对照（须增／须改／须删），方案有界。
3. **新增手段化一步。** 旧版把技术判断混在 Q3 与门一里；本版单列，三个检查项（AI 能力边界、数据环境、成本）明确分开结构与手段。
4. **新增现状有效性前提。** 明确项目不存在重建情形，只存在优化情形。
5. **新增剩余物清单。** 五份筛掉物的去处。
6. **新增验收闭环。** 验收项须回指第一步的损失。
7. **设防表进入手册**，对客户可见。
8. **四维定位保留但移位。** 旧版在 Q2 用于定位改善落在哪一格；本版移到 §6.3 与验收项，用于取数。
9. **价值三元、反事实检验保留**，分别移到 §4.3 与 §5.4。
10. **旧版约束记录改为力清单。** 理论删除了「约束」这一空转概念，台账改用力的六项记录：编号、内容、来源、维持者、现有对抗方式、痕迹证据。
11. **数据环境七层、权限三态保留**，改为六步中的切口（§8）。

## 附：适用范围

本方法论承接咨询与现场调研，先形成客户业务流、整体架构 graph 与 ER 图，再判应然、出解法、做手段化、定产品，最后展开为开发方案。咨询提供事实与基线；客户分析 A 梳理客户当前的业务与整体结构；应然给出架构(F, E)，回答必须存在什么；解法给出差集；手段化给出可行改动与做不了清单；产品给出承诺与验收，并在产品定义处做两重投影——向客户为解决方案，向我方为技术架构。

送审对象为开发计划、填好的架构手册（架构设计，含架构图）、解决方案，同版一次提交总架构师审核；范围报价作附件。客户分析 A 是架构设计的依据，不单列为送审件。所需 spec 审核通过后由 FDE 按项目需要自行撰写，不送审。

客户分析 A、方案文档与范围报价保存在知识库「FDE 全链」对应项目；开发仓库保留 A 的同版引用与知识库来源链接、开发方案 B 及独立计划，项目记录关联明确版本和审核原文。填写格式从[项目管理模板目录](../2-项目经理/README.md)进入。

## 附：合同验收与结果核对

场景基线与改善效果采用同类样本和可比条件，记录实际结果、差异及限制。场景量可以承载可判、可控的功能验收；客户营收、利润等经营结果用于观察和价值讨论。
