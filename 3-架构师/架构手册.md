# FDE 架构手册

[返回项目管理手册](../2-项目经理/项目管理工作手册.md#stage-45) · [全部模板与参考](../README.md) · [架构方法论](架构方法论.md)

## 使用说明

**谁填**：项目架构师一个人填。填好即架构设计；对外架构图与解决方案从同一份手册摘出，不分开另判。

**什么时候算填完**：每一段末尾有一张「这段算填完的标准」，逐条打勾才算。打不了勾的，写清缺什么、谁补、哪天补。

**填的时候守三条**：
1. 每一格都要能指回一个出处——谁说的、哪份文件、哪次看到的。指不回去的写「待核实」。
2. 不写「应该是」「一般来说」「建议」。只写查到的、算出来的、跟客户谈定的。
3. 客户原话单独存一份，不改写成我们的说法。

**六段的顺序不能换**：现状 → 必须有什么 → 差在哪 → 能不能做 → 承诺什么 → 多少钱。前一段没填完不要往后填，后面每一段都吃前一段的结论。

## 角色与存放

| 角色 | 干什么 |
|---|---|
| 项目架构师 | 填这本手册；对每一条判断负责 |

# 第一部分 · 架构本体

## 第一段 · 这家企业现在怎么运转

这一段全部是查来的，不含任何我们的想法。写不出来的地方标「待核实」，不许用推测填。

### 1.1 业务是怎么走的

事实来源是《调研报告》一、二、三、四节（业务流、资金流、生产流、数据流）。这一段只做一件事：把报告里的东西搬到架构的位置上，标出分叉、回退、并行。

**报告里没写到的**，标「待补」并写明请谁补，不在架构里自己编。

| 步 | 这一步干什么 | 谁做 | 交给谁 | 用什么记 | 会卡在哪 |
|---|---|---|---|---|---|
| | | | | | |

### 1.2 环和格的编号

一个能说清输入、判断、输出、交接的业务闭环绕一圈，编一个号：环-01、环-02……环里面可以单独观察和改的一个量，编成一格：环-01a、环-01b。

**编号全篇通用**：后面的问题、要防的事、要验收的东西，都挂这个号。

| 编号 | 名称 | 起于 | 止于 | 谁负责 | 现在的量 |
|---|---|---|---|---|---|
| 环-01 | | | | | |
| 环-01a | | | | | |

### 1.3 现在在对抗哪些事

方法论里把这种东西叫「力」——一直在给功能添麻烦、不会自己消失的事。写的时候写具体：写「客户改图纸后车间不知道，还按老图做」，不写「沟通不畅」。

每条记六项，缺一项不算一条：

| 编号 | 什么事（让哪一环的什么做不成了） | 来源 | 谁在维持它 | 现在靠什么撑住 | 痕迹证据 | 挂哪个环 |
|---|---|---|---|---|---|---|
| 力-01 | | | | | | |

**来源**五选一：物质条件／有权的人／制度规矩／时间窗口／历史遗留。五类都归不进的，写「新增一类：＿＿」。

**谁在维持它**必须答全四项核对：谁受益、谁能改、谁在承担代价、真拿掉以后谁付账。四项核对答不全的，先别当一条力。

**痕迹证据**四选一，没有不算数：
- 断裂痕：故障记录、返工单、投诉、审计发现
- 绕行痕：私下表格、两套账、口头确认、加班、群里对数
- 阻力痕：提案被否、推不动、没人接
- 缺失痕：该有的记录和岗位没有

**找不到痕迹的**，写进「待核清单」，不进这张表。找不到痕迹和不存在是两件事。

### 1.4 现状里哪些是多余的

这一段先只能给候选，等第二段写出「必须有什么」以后才能定稿。这里只做分类：

| 类别 | 意思 | 本项目看到的 |
|---|---|---|
| 重复 | 同一件事有好几套做法在顶 | |
| 过时残留 | 当初的事已经不用管了，规矩还每天在做 | |
| 走样 | 没人维护，越走越不一致 | |
| 空转 | 既不顶事，也没人天天在维持 | |

### 1.5 数据环境（七层）

一层一层往下问，卡在哪一层写清楚。

| 层 | 问什么 | 现状 | 判定 |
|---|---|---|---|
| 1 软件 | 用的什么系统、哪家做的、哪些模块、什么版本 | | |
| 2 部署 | 装在本地、用云上的，还是混着 | | |
| 3 存储 | 什么数据库；是不是自己搭的；有没有中间库 | | |
| 4 存储结构 | 表结构长什么样；主数据在哪；单据怎么跟主数据连；改过多少 | | |
| 5 权限 | 系统里谁能读、谁能写、谁只能看报表 | | |
| 6 安全 | 数据分几级；能不能出公司；有没有等保、审计要求 | | |
| 7 接口 | 有没有接口、有文档没有、能不能开、谁批、怎么取、有没有中间件 | | |

**判定五选一**：不用动／凑合着用／要改／另起一套并行／换掉或新建。

部署方式单记一句：云上的系统一般有接口和文档，但取数受对方版本和额度限制，数据出公司最难；本地自己装的能直接连库，但结构常被改乱、没文档；混着的最麻烦，同一份数据两处各有一份，说不清哪个为准。

### 1.6 权限（三态）

| 事项 | 制度上谁说了算 | 实际是谁在定 | 系统里设的是谁 | 差在哪 |
|---|---|---|---|---|
| | | | | |

三种说法对不上的地方，就是风险点。

### 1.7 这段算填完的标准

| # | 标准 | ☐ |
|---|---|---|
| 1 | 业务流能向客户复述一遍，客户认 | ☐ |
| 2 | 每个环和格有编号、有负责人 | ☐ |
| 3 | 每条力有四项核对、有痕迹、挂了环 | ☐ |
| 4 | 每条力都能指出「现在靠什么撑住」 | ☐ |
| 5 | 文档里没有「应该是」这类话 | ☐ |
| 6 | 数据七层逐层判过，未知项写了谁补、哪天补 | ☐ |
| 7 | 权限三态差异已标 | ☐ |

## 第二段 · 必须存在什么

这一段是设计，不是观察。出来的是我们应该给出的答案，不是客户的期望。

### 2.1 我们向谁承诺什么（功能）

| 项 | 内容 |
|---|---|
| 功能是什么 | 一句话，客户能听懂：谁在什么情况下，能得到什么结果 |
| 谁指派 | 谁承担这件事办不成之后的后果 |
| 主要功能 | |
| 附带功能 | |

一个单元可以承担好几个功能。主要功能只有一个，其余写附带。

**有好几条互不相干的生意时**：按主要功能分开写，一条生意一段。组织结构只拆一次，不重复拆。

### 2.2 哪些事会破坏它（基线）

| 项 | 内容 |
|---|---|
| 承诺期 | 从哪天到哪天（一般按合同期） |
| 会破坏它的事 | 分常态和异常两类写 |

**常态**：经常发生、程度有限的事，比如旺季单量翻倍、人员流动、系统每月例行维护。

**异常**：不常发生、一旦发生后果严重的事，比如断电、断网、大批退货、监管抽查、关键人离职。

写基线的时候，用客户行业里的普遍情况打底，客户自己出过几次事只作参考——一个一直没出事的公司，往往是因为它已经在防了，光看它的事故记录会把风险估低。

| 会出什么事 | 程度 | 多久一次 | 属于哪类 | 出处 |
|---|---|---|---|---|
| | | | 常态／异常 | |

### 2.3 必须有的东西

两项两步判：先假设它不存在，看功能还成不成；再从「不存在就不成」的那些里，剔掉可以被别的东西顶替的。

**要按组合判，不能一件一件删。** 两条互为备份的路，各删一条都不影响，一件一件删会把两条同时判成不必要。做法是：先找出「少一样就断」的最小组合，再看哪些东西出现在所有这些组合里。

**要在出事的时候判。** 异常处理、追溯、责任归属这类东西，平时不用，正常运行删掉也看不出差别。

| 编号 | 必须有什么 | 哪一项功能少了它就不成 | 去掉会怎样（写推演过程） | 它对抗哪条力 | 有没有别的东西能顶 |
|---|---|---|---|---|---|
| | | | | | |

「有没有别的东西能顶」填「有」的，本项不进架构，另记替代办法。

### 2.4 关键业务怎么走

不是所有流程都要画，只画少了就断的那几条。每条登记五项。

| 编号 | 走什么（权责／钱和物／风控追溯／信息／工单） | 从哪产生 | 经过谁 | 在哪留痕 | 到谁 | 有没有专人推 |
|---|---|---|---|---|---|---|
| | | | | | | |

**「有没有专人推」单列**：风控、审计、追溯这类事，组织里天然没人愿意推，不专门设一个人，它永远慢半拍。

### 2.5 防哪些事、防到什么程度

前三段定的是「要做成什么样」。这一段回答另一个问题：出了事我们保不保，保到什么程度。**这一段要给客户看，写客户能看懂的话。**

先列事，再定档。写具体的事——写「车间断网两小时，当天的工单导不出来」，不写「各类系统风险」。

| 序号 | 会出什么事 | 出了有多严重 | 多久出一次 | 防不防 | 防了要多付什么 |
|---|---|---|---|---|---|
| 4-1 | | 三档：只耽误事／要赔钱／要停机 | 按最忙的时候算，一年几次 | 全防／防一部分／不防但隔开／不防 | 平时多花几个人、系统慢几秒、多几道手续 |

四条规矩：
1. 四档里选一个，空着不行。选了「不防」也要写，写明这事出了客户自己扛，还是找保险、找上级单位。
2. 条目可以少，不能空。
3. 承诺期之外的事不进这张表，在表下面单列一句：这类事出了由客户自己承担，或者由保险、法规、上级单位接着。
4. 三条成本分开写：结构本身的重量和日常维护、专门为防这件事加的东西、为了防它牺牲掉的日常效率。

### 2.6 这段算填完的标准

| # | 标准 | ☐ |
|---|---|---|
| 1 | 功能写成客户能核验的一句话 | ☐ |
| 2 | 每项必须有的东西都回指一条力，回指不到的是偏好，删掉 | ☐ |
| 3 | 每项的「去掉会怎样」写了过程，不只写结论 | ☐ |
| 4 | 关键业务每条都有承接人，没有断头 | ☐ |
| 5 | 防的表里没有空行 | ☐ |
| 6 | 这一段里没有「先不管，做的时候再说」 | ☐ |
| 7 | 与现状的差有多大能解释：差得多，要能说清是这一段判紧了还是第一段看漏了 | ☐ |

## 第三段 · 差在哪

### 3.1 解法就是两段的差

**要做的改动 ＝ 第二段（必须有什么）减第一段（现在有什么）。**

不是重新设计一遍。差是有边界的：上界是第二段，下界是第一段已经跑得通的部分。方案越做越大时，一定是某一头破了界——要么第二段里混进了偏好，要么第一段漏了客户现有的办法。

逐项对照，出三列：

| 列 | 什么意思 | 典型的东西 |
|---|---|---|
| 要加 | 第二段有、第一段没有 | 缺的关键环节、缺的检查、缺的记录 |
| 要改 | 第一段有、做法不对 | 同一件事做坏了；靠临时办法硬撑；该交给谁的交错了 |
| 要删 | 第一段里挡路的那些 | 过时残留、空转、走样 |

三列的判法不一样：要加看「去掉就不成」，要改看「现有的临时办法还能不能撑」，要删看「拿掉以后谁付账」。

| 编号 | 列（加／改／删） | 内容 | 挂哪个环 | 依据 | 谁受影响 |
|---|---|---|---|---|---|
| | | | | | |

### 3.2 三笔价值分开算

每一列带来的改善，分成三个来源，各占多少写清楚：

| 来源 | 说明 |
|---|---|
| 流程调整 | 取消、合并、往前挪就能拿到的改善。不用软件也能拿到的那部分 |
| 普通工程 | 靠固定规则、改现有系统能实现的 |
| AI | 前两样做不到、非要模型做判断的那部分 |

**不分这三笔，AI 会把流程调整的好处算到自己头上。** 这直接关系到报价站不站得住，也是客户后期回过头质疑价值时第一个盯的地方。

| 改动编号 | 流程调整 | 普通工程 | AI | 合计 |
|---|---|---|---|---|
| | | | | |

### 3.3 不动的清单

必须写。明确写出哪些地方我们不动，以及为什么。

| 不动的部分 | 为什么不动 |
|---|---|
| | 少了就断／刚改完／在等客户内部定／动了不划算 |

这份清单是后面所有分歧的挡板。客户后期每加一条要求，先对照它。没有这份清单，项目范围会在交付过程中一路变大。

### 3.4 这段算填完的标准

| # | 标准 | ☐ |
|---|---|---|
| 1 | 三列每一项都有编号、挂了环 | ☐ |
| 2 | 「要删」的每一项都写了「谁付账」 | ☐ |
| 3 | 三笔价值分开了，AI 那笔有依据 | ☐ |
| 4 | 不动的清单写了，每项有理由 | ☐ |
| 5 | 差有多大能解释 | ☐ |

## 第四段 · 能不能做

前三段只讲结构上该不该做。这一段开始问手段：这些改动里，软件和 AI 能接哪几项，接到什么程度。

### 4.1 AI 能力边界（逐项）

一项一项过。每一项问一句：**这件事要不要模型做判断？模型做不做得了？**

| 改动编号 | 这件事要模型干什么 | 做得了／做不了 | 卡在哪 |
|---|---|---|---|
| | | | |

**判据**：信息形态上的事可以做——把纸记的变成数据、把一个人在手上的东西转到另一个人手上、把事后才知道的变成当时就知道、把人工算的变成自动算。要直接改变物理过程、直接改变人的想法、直接改变法律责任归属的，做不到；这类要补出「通过信息绕一道」的完整链条，补不出来就不做，退回第三段重判。

**AI 另有一条**：模型能给候选、能给判断，不能代替组织里「采纳」这个动作。凡是要人签字、担责的节点，不管模型多强，这个节点上留人。

### 4.2 数据环境（逐项）

| 改动编号 | 要什么信息 | 存在吗 | 形态对不对 | 取不取得到 | 卡在第几层 |
|---|---|---|---|---|---|
| | | | | | |

这一项跟 4.1 不是一回事：4.1 判「想不想得明白」，这一项判「料拿不拿得到」。

### 4.3 成本（逐项）

| 改动编号 | 平时维护要多少 | 专门防出事要加多少 | 会让日常效率慢多少 |
|---|---|---|---|
| | | | |

这三项要能跟第二段里估的损失并排放。放不下的，回第三段重判。

### 4.4 能做的清单

三项都过的，逐项写清：谁来承担（AI／固定程序／流程调整／人）、做到什么程度、依赖什么前提。

| 编号 | 哪项改动 | 谁来承担 | 做到什么程度 | 依赖什么 |
|---|---|---|---|---|
| | | | | |

### 4.5 做不了的清单

结构上合理、手段做不到的。每一项写去处：交回客户自己组织人做，或者排到第二期。

| 编号 | 哪项改动 | 为什么做不了 | 去处 |
|---|---|---|---|
| | | | |

含糊处理会变成项目后期最主要的一处纠纷。

### 4.6 要不要靠模型做判断

如果某处要把老师傅脑子里的判断变成一套能执行的规则，这一处单列，逐项验三件事：

| 验什么 | 结论 |
|---|---|
| 要的数据拿得到吗 | |
| 判断出来了，有人按它办吗 | |
| 判断出来之后，能对那个对象真做点什么吗 | |

三件缺一件，这一处就只能定位成「帮人参考」，不能定位成「替代人」，并写进承诺范围。

### 4.7 去掉 AI 会怎样

对每一项打算交给 AI 的事，问一句：**把 AI 拿掉，这一项的改善会受多大影响？**

| 编号 | 去掉 AI 之后 | 结论 |
|---|---|---|
| | 没影响／有影响但能换别的办法／没法替代 | 改别的承担方式／写替代方案和代价／写依据 |

写「没法替代」的，要写清依据，以及这个依据靠什么样本、什么条件验证。

### 4.8 这段算填完的标准

| # | 标准 | ☐ |
|---|---|---|
| 1 | 每一项都过了三个检查项，三个结论都写下来了 | ☐ |
| 2 | 做不了的清单有，每一项有去处 | ☐ |
| 3 | 每个交给 AI 的节点，有判据、有还没验证的条件 | ☐ |
| 4 | 要变成规则的那几处，三件事各有明确结论，不写「效果待评估」 | ☐ |
| 5 | 去掉 AI 会怎样，每项都有结论 | ☐ |

---

<a id="product-definition"></a>

## 第五段 · 承诺什么

### 5.1 承诺什么

**承诺 ＝ 能做的那些 ∩ 愿意承诺的那些。**

两个方向都可能不重合：做得到但不承诺的，写明在承诺范围之外；承诺了但怎么实现由我们定的，客户不管实现，只看两件事——保什么功能、防哪些事。

承诺不由「我们做了什么」来定义，由「我们保什么、在哪些事面前兑现」来定义。

### 5.2 技术可实现性（整件过一遍）

逐项过完以后，把产品当一个整体再问一遍：

| 问什么 | 结论 |
|---|---|
| 接不接得上客户现有的系统 | |
| 客户那个数据量扛不扛得住 | |
| 跑一次要多久，客户等不等得及 | |
| 客户那边没人懂技术，出了问题谁来处理 | |
| 上线以后谁来维护、多久动一次 | |

这一项跟第四段 4.1 不是一回事：4.1 是一项一项问「模型做不做得了」，这一项是整个产品装起来、真跑起来站不站得住。

### 5.3 业务成立

问三句：

| 问什么 | 结论 |
|---|---|
| 用的人一天多干几步、少干几步 | |
| 出了错，用的人能不能看出来 | |
| 用的人如果不照着办，会怎样 | |

第三句最关键。一个系统做得再对，人不用，就是不成立。这一条的证据不在客户老板的嘴上，在具体岗位上的人手上——这一点在第六段体验流里落。

### 5.4 功能声明

写成客户能核对的一句话：谁，在什么情况下，能拿到什么结果。

| 项 | 内容 |
|---|---|
| 保什么 | |
| 对谁保 | |
| 什么情况下算兑现 | |

### 5.5 设防声明

直接引第二段 2.5 的表，不在这里重抄。表下面加一句：本架构在功能范围和要防的范围都不变的前提下成立，任何一个变了要重判。

### 5.6 验收项

验收项逐条回指第一段记下的损失或问题。回指不上的验收项删掉；第一段有问题而没有对应验收项的，补上，或者在设防声明里写明不保。

| 编号 | 客户那边看到的现象 | 测什么 | 现在是多少 | 要做到多少 | 怎么测 | 测多少样本 |
|---|---|---|---|---|---|---|
| | | | | | | |

**哪些能进验收、哪些不能**：

| 类型 | 例子 | 能不能进验收 |
|---|---|---|
| 过程量 | 处理要多久、一次做对的比例、要人复核多少、偏差多大 | 能。可判、可控 |
| 经营结果 | 每单赚多少、成不成交、营收、利润 | 不能。只能作为观察 |

写「省了多少钱」的时候，这个数要由过程量乘真实业务量推出来，并且把推导过程写出来。

<a id="customer-experience"></a>

### 5.7 客户体验流

写清楚用的人一天多干几步、少干几步，怎么找到入口，第一次用需要知道什么。

| 场景 | 现在怎么做（几步、多久） | 以后怎么做（几步、多久） | 净变化 |
|---|---|---|---|
| | | | |

这一节不是文档装饰，是 5.3 业务成立的证据。

### 5.8 这段算填完的标准

| # | 标准 | ☐ |
|---|---|---|
| 1 | 功能声明和设防声明都写成客户能核对的句子 | ☐ |
| 2 | 每条验收项有测什么、现状值、目标值、测法 | ☐ |
| 3 | 验收项能逐条回指第一段的问题，回指表附在验收文件里 | ☐ |
| 4 | 经营结果没有被写成承诺 | ☐ |
| 5 | 体验流里有多几步、少几步的算术 | ☐ |
| 6 | 承诺范围之外的事写清了归谁 | ☐ |

## 第六段 · 多少钱、分几期

报价是独立的一份文件，不写在这本手册里。这一段只写报价要吃的那几样东西。

### 6.1 报价的三个来源

| 来源 | 从哪来 |
|---|---|
| 开发 | 第四段「能做的清单」，按模块拆 |
| 运行 | 复核、返工、模型调用、人工兜底 |
| 防出事 | 第二段 2.5 的设防表，逐项 |

三样分开列，不给一个总数。按「不做会怎样」分层报，客户可以挑哪一部分不做。

### 6.2 分期

- 先做数据依赖的，后做判断能力
- 每一期至少有一个能测的过程量验收点
- 没有能测验收点的，不单独立一期

| 期 | 做什么 | 验收点 | 依赖什么 |
|---|---|---|---|
| | | | |

### 6.3 出口

报价与分期由 PM 据此填写，范围与验收一律引本手册的版本，不另写。

## 依据指针

全篇每个判断后面挂一个出处，并标确认状态。

| 段 | 挂什么 | 状态 |
|---|---|---|
| 第一段 | 谁的哪句话、哪份单据、哪次导出、哪次看到 | 已确认／待确认 |
| 力 | 哪类痕迹、证据在哪 | 已取证／取证不足 |
| 第二段 | 去掉会怎样的推演、回指哪条力 | 已判／待判 |
| 第三段 | 三列的编号、对应第一段的哪一项 | 已对照／待对照 |
| 第四段 | 三个检查项的结论、假设和测法 | 已验证／待验证 |
| 第五段 | 验收项回指哪条损失 | 已闭合／待闭合 |

确认状态单独一栏，不写进正文。审的时候先看这一栏：全都「已确认」而依据栏是空的，说明是填的；一堆「待确认」而第四段已经通过，说明没真检。

**指针断掉的地方就是没想清的地方。**

---

## 五份「我们不管」的清单

六段之间不是等价转换，每一段都筛掉东西。筛掉的必须写下来，否则范围会在交付里自己长大。

| 段与段之间 | 筛掉了什么 | 写到哪 |
|---|---|---|
| 现状 → 必须有什么 | 有痕迹但客户不认的事 | 待核清单，下次进场再问 |
| 必须有什么 → 差在哪 | 问题不在结构上的（人、流程、市场） | 写明不属本项目范围 |
| 差在哪 → 能不能做 | 结构合理但手段做不到的改动 | 做不了清单，交客户或排二期 |
| 能不能做 → 承诺什么 | 做得到但不承诺的 | 写明在承诺范围外 |
| 承诺什么 → 多少钱 | 承诺了但这一期不做的 | 分期表 |

五份合起来是一份「我们不管什么」。项目最常见的失败，不是做不出来，是边界从来没写下来，最后每一件都成了我们的事。

# 第二部分 · 对外两件从哪里取材

对外两件是[对外架构图](对外架构图.md)与[解决方案](解决方案.md)。两件都由架构师从本手册摘出，PM 核对范围与验收口径；不另写一套与架构设计冲突的判断。

| 本手册位置 | 对外架构图取什么 | 解决方案取什么 |
|---|---|---|
| 第一段 · 现状 | 业务主线、涉及角色、问题发生在哪 | 客户现状、问题、证据与影响 |
| 第二段 · 必须有什么 | 必需能力、业务边界、人工确认位置 | 目标、功能、设防与责任边界 |
| 第三段 · 差在哪 | 改哪里、不改哪里 | 本期改动、排除项与价值依据 |
| 第四段 · 能不能做 | 主要组成、可行条件与限制 | AI 与工程分工、验证状态和限制 |
| 第五段 · 承诺什么 | 客户得到什么结果、怎样交接 | 功能承诺、体验、验收项与配合条件 |
| 第六段 · 多少钱、分几期 | 分期位置（金额不强塞进图） | 分期口径；具体金额见报价附件 |

**两件共同纪律**：版本与本手册一致；不承诺无依据的经营结果；设防、限制、范围与验收不能藏。对外架构图控制在 1–2 页，解决方案保留客户核对所需的完整文字。

spec 由 FDE 在审核通过后按项目需要编写，不送审，不要求一次写齐九份。取材对照：

# 送审与审核清单

## 送审要交什么

| 件 | 要求 |
|---|---|
| 开发计划 | 按验收项和流程排期，追到本手册的具体节 |
| 架构设计（含架构图） | 即本手册填写版；六段填完，架构图清楚，依据指针带状态 |
| 解决方案 | 从本手册摘出，与本手册及对外架构图同版 |

范围报价作附件。三件同版，一次提交；缺一不得送审。

## 审核看什么

| # | 看什么 | 在手册哪 |
|---|---|---|
| 1 | 现状是不是真的 | 第一段：业务流能复述、每条力有四项核对有痕迹、七层逐层判过 |
| 2 | 该有的有没有 | 第二段：必需清单有推演、设防表无空行、关键业务无断头 |
| 3 | 方案有没有越界 | 第三段：三列有界、三笔价值分开、不动清单在 |
| 4 | 做不做得出来 | 第四段：三个检查项结论、做不了清单 |
| 5 | 承诺能不能核 | 第五段：功能与设防两轴、验收项可回指 |
| 6 | 前后一致不一致 | 全篇：编号对得上、版本对得上、报价与计划的引用对得上 |

**一票退回的三条**：力清单里有条目既无痕迹又无「现在靠什么撑住」；设防表有空行；验收项回指不到任何问题。

# 审核通过后

1. 冻结版本，记版本号与审核结论
2. 按第三部分和项目需要编写 spec
3. 开发中发现架构缺东西，回补本手册并升版本，列出改了哪几处
4. 涉及已审核过的判断，送总架构师复核
5. 报价与开发计划跟着升版本，以本手册为准改它们，不能反过来放宽本手册
